# Botのパフォーマンス改善（2026-09-05）

13,200サーバーでの運用を想定し、投稿数に伴って増えるキャッシュ、設定読み込みの重複、単一DB接続の待ち行列、外部通信の無期限待機を改善した。変更はローカルで検証済み。本番環境への反映と、直近のクラッシュ原因の特定は未実施。

## 再現試験

Windows / Node.js v24.15.0。Discordへのログイン・実DBへの接続を行わない試験。速度は10万件を5回処理した中央値。既存の振り分け処理（mainの3639c9d）と、今回の処理を同一プロセス内で比較した。外部API応答・Discord送信時間・DB実行時間は含まない。

測定出力: [performance-benchmark.json](./performance-benchmark.json)

| 測定対象 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 一般会話10万件のURL振り分け | 1,656.3 ms | 3.7 ms |
| 一般会話90%・URLあり10%の振り分け | 1,694.6 ms | 15.1 ms |
| 10万件受信後の追加ヒープ | 265.5 MiB | 3.2 MiB |
| キャッシュ内の履歴メッセージ | 100,000件 | 0件 |
| キャッシュ内のメンバー | 100,500件 | 1,000件 |
| キャッシュ内のユーザー | 100,001件 | 1,000件 |

メモリは500サーバー×1チャンネル×200投稿者の合成データを、インストール済みdiscord.jsの実際のClient/Managerへ投入し、GC後に測定。変更前後を別プロセスで実行した。Bot全体のRSS、動画転送中のメモリ、本番13,200サーバーでの使用量を表す値ではない。

同じサーバー・プロバイダに対する100件の同時設定読み込みでは、読み込みを1回に共有することを確認した。テスト専用メモリ保存を無効化した統合テストでも、設定の11 SELECT＋無効化チェック1回になり、設定変更後は新しい値を読み直した。実MySQLに対する速度測定は行っていない。

再実行:

```powershell
node --expose-gc scripts/benchmark_performance.js
npm test
npm run typecheck
npm run lint
```

## 変更内容

- Discordの履歴メッセージを常駐させず、ユーザーを全体で1,000件、メンバーを各サーバーで2件に制限。Bot自身のメンバー情報を保持する。処理中のメッセージには受信時のメンバー参照を保持し、キャッシュ退避後もロールによる無効化・センシティブ制御を維持する。ボタン操作はDiscordから届く元メッセージを使用する。
- 一般会話をPromise生成や全プロバイダの正規表現検査より前に除外。正規表現を再利用し、`<URL>`・`||URL||`による展開抑制を維持する。
- 設定を2,048件・30秒の期限付きキャッシュに保存。取得中のPromiseも共有し、失敗は再取得可能にする。無効化された古い取得結果が新しいキャッシュを上書きしない。
- MySQLを1接続から既定8接続のプールに変更。3種類の設定リスト更新と設定一括保存は、トランザクション専用接続を使用する。ロールバック失敗時には接続を破棄し、不確かな状態の接続を再利用しない。
- 埋め込みメッセージの同時処理・待機数を制限。処理中の仕事が終了するまでスロットを保持する。最近処理したメッセージIDのみ最大10,000件・5分保持し、Gatewayの重複配信による再展開を抑制する。
- 全12プロバイダのメタデータ取得に通信期限を設定。期限にはレスポンス本文の取得とリダイレクトを含め、AbortSignalで実際の通信を中止する。Twitterは15秒・応答最大4 MiB。
- 同一メトリクスの加算が保存対象の行に反映されない不具合を修正。100回×3の加算を300として保存する回帰テストを追加。
- 起動後、毎分`[performance]`にRSS・ヒープ・外部メモリ・イベントループ遅延p99・処理中/待機/拒否数を出力する。ユーザー数の統計表示は、実際の値に合わせて「キャッシュ中のユーザー数」とした。
- このmainブランチに欠けていた既存のNode移行コミット379edc3の6ファイルを取り込み、標準起動をNodeに統一。Bunによる本番起動を拒否する。過去の移行と今回の性能改善は別の変更であり、本番の現在の起動状態は確認していない。

## 上限と過負荷時の動作

| 環境変数 | 既定値 | 内容 |
| --- | ---: | --- |
| `BOT_DB_CONNECTION_LIMIT` | 8 | BotのDB接続数。ダッシュボードの接続プールとは別 |
| `BOT_DB_QUEUE_LIMIT` | 512 | 接続を待つDB処理の最大件数 |
| `BOT_DB_QUERY_TIMEOUT_MS` | 30000 | DBクエリの期限（ms） |
| `BOT_MESSAGE_CONCURRENCY` | 32 | 同時に設定取得・展開・送信するメッセージ数 |
| `BOT_MESSAGE_QUEUE_LIMIT` | 512 | 展開開始を待つ最大メッセージ数 |
| `BOT_MESSAGE_QUEUE_WAIT_MS` | 30000 | 展開開始前の最大待ち時間（ms） |
| `BOT_PROVIDER_TIMEOUT_MS` | 30000 | プロバイダ通信の既定期限（ms）。Twitterは個別に15秒 |

展開待ちが512件を超えた場合、または待ち時間が30秒を超えた場合、そのメッセージは展開せず、拒否メトリクスと警告を記録する。待機数を無制限に増やしてメモリを使い切ることを避けるための動作であり、永続的な再試行キューではない。進行中の処理を見かけだけタイムアウトさせて次の処理を追加することはしない。

DBの待機上限到達・タイムアウトは呼び出し元へエラーを返す。書き込みを自動再試行しない。DDLもDBクエリ期限の対象なので、既存の大規模マイグレーションを実行する環境では起動前に期限を確認する。

## 検証と本番での確認

変更前413件・変更後435件のNodeテストがすべて成功。型チェック成功。ESLintはエラー0件、変更前からあるAmazonプロバイダの未使用関数の警告1件。

回帰テストで、実際のDiscordキャッシュ・ロール保持・キャッシュにない過去メッセージのボタン操作、返信構築時にメンバーが退避された場合の再取得、重複配信、設定の同時取得・無効化、DBトランザクション分離・ロールバック失敗、過負荷・待機期限切れ・失敗後の処理継続を確認した。通信期限はlocalhostのHTTPサーバーで、ヘッダーが届かないケースと本文が途中で止まるケースを再現し、接続が閉じることを確認した。

本番反映時は既存のサーバー側コミット・作業ファイルを保持し、今回の変更だけを適用する。Node移行分が既に入っている本番環境へ、この古いmain全体を上書きしない。今回、サーバーの更新・再起動・DB変更は行っていない。

反映後は同程度の受信量で`[performance]`のRSS/ヒープの推移、イベントループ遅延、待機件数・拒否件数と、既存の`provider_extract`の所要時間を比較する。成功率低下や拒否の継続があれば、通信先の遅延・DB待ち・重いプロバイダを切り分けて調整する。今回の合成試験だけで、本番全体の高速化倍率やクラッシュ解消を断定しない。
