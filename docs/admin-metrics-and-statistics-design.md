# 管理ダッシュボードの指標・集計・画面の詳細設計

2026-09-05。ユーザーの指定に従い、今回の対象は詳細設計まで。Bot・ダッシュボード・DBの実装変更と本番検証は未実施。

[サポート設計](admin-support-console-design.md)と[管理分析デーモン設計](admin-analysis-daemon-design.md)に共通する指標契約を定める。通常ダッシュボードと独立管理Webが同じ定義・値・根拠を使う。自動診断は定義済みのルールで行い、LLMは使用しない。

## 1. 何を判断する画面にするか

| 管理者の疑問 | 最初に見る指標 | 次に開くもの |
| --- | --- | --- |
| 今、ユーザーに影響する問題があるか | 問題のある要求数、未完了・結果不明、影響サーバー、観測状態 | 該当要求と進行中障害 |
| 意図したDiscord出力処理が完了したか | 要求単位の結果内訳、完全成功を確認できた割合 | 取得・判定・送信・後処理の経過 |
| 遅いのはどこか | 完了時間の分布、待機中の経過時間、段階別の時間 | 遅い要求とqueue/HTTP/DB/送信 |
| どの機能が使われているか | ユーザーが行った操作数、利用者・サーバー数、機能別内訳 | コマンド・ボタン・サービス・対象投稿 |
| 設定や更新の前後で何が変わったか | 同条件の件数・率・時間の前後差 | 適用した設定版、コード版、個別事象 |
| 外部の投稿にはどんな特徴があるか | 重複排除したコンテンツと取得時点の外部指標 | 外部指標の原値・取得元・観測時刻 |
| この統計を信用できるか | 対象期間、分母、記録の完全性、集計遅延、定義版 | 欠落区間と集計検証結果 |

画面は「稼働・影響」「利用状況」「コンテンツ」「変更前後」「計測状態」の用途で整理する。サポートの検索条件と行き来できるようにし、下位の原文・数値を隠さない。

### 1.1 Discord APIで観測できる範囲の精査

2026-09-05に公開Bot APIのMessage、Gateway Events、Components、Interactionsの公式仕様と現在の受信実装を照合した。このBotが扱う通常のサーバーメッセージでは、閲覧数、閲覧者、既読、本文/Embed内のURLクリック、添付の閲覧・再生・端末保存をBot APIから取得する機能は提供されていない。

| 情報 | 取得可否・取得元 | 本設計での扱い |
| --- | --- | --- |
| メッセージの閲覧数・閲覧者・既読 | 公開Bot APIでは提供されない | 採用指標から除外。取得可能だが未実装という意味の「未計測」と混同しない |
| 本文/EmbedのURLクリック | 公開Bot APIからクリックeventを受信できない | CTR・リンククリック数を算出しない |
| Linkスタイルのボタン | クリックしてもアプリへinteractionを送らない | ボタン操作件数・操作率の対象に含めない |
| 自アプリのcustom_id付き非リンクボタン | Message Component interactionとして受信可能 | 「受信したボタン操作件数」。受信時に保存し、実行成功/拒否/失敗を別記録 |
| 自アプリのコマンド・select・modal submit | 対応するinteractionを受信可能 | 種類別の受信操作と処理結果。閲覧やURLクリックの代用にしない |
| 絵文字リアクション | 公開APIのmessage/reaction情報とGatewayの追加/削除eventがある。権限・intents等が前提 | 現コードのintent/handlerには専用の収集がないため現行指標としない。追加する場合も絵文字反応として別定義 |
| メッセージ作成・送信結果 | REST応答やMessage Create等で確認可能 | Discord側の受付・作成とBot処理の成否。人の画面表示・読了は確認できない |
| 元メッセージ本文 | Message Content intent等とアクセス可能範囲に依存 | ソースでのintent指定と実環境の利用可否を区別。取得不能を本文なしと誤判定しない |
| 自前ダウンロードURLへのアクセス | 自前HTTPサーバーのrequestから計測可能 | Discord APIのクリックではない。サーバーへの要求件数/転送状態として表示 |
| X/YouTube等のviews/likes | 各取得元が提供する外部サービスの観測値 | Discord内の閲覧・反応として表示しない。利用可能性はprovider別に確認 |

Messageの公開フィールドとGateway eventの確認範囲は[Message仕様](https://docs.discord.com/developers/resources/message)と[Gateway Events仕様](https://docs.discord.com/developers/events/gateway-events)。Linkボタンがinteractionを送らないことは[Components仕様](https://docs.discord.com/developers/components/reference)、custom_id・component_type等は[Interactions仕様](https://docs.discord.com/developers/interactions/receiving-and-responding)に基づく。

現コードではsrc/components/_buttons.jsの翻訳・削除・表示形式変更がcustom_id付きボタンで、src/handlers/messageComponents.jsがinteractionを記録する。src/providers/_output_controls.jsの元URLボタン、src/components/downloadYouTubeVideo.jsとdownloadNiconicoVideo.jsが返すダウンロードリンクはLinkスタイル。

したがって「ダウンロード準備を要求した操作」「準備処理の結果」「完成したURLへのHTTP要求」は三つの別の事実である。リンクボタンが押された回数、実際に端末へ保存できた回数は、それらから確定できない。

さらにdownloadYouTubeVideo.jsは準備失敗をcatchして案内を返すため、呼出元のmessageComponents.jsではhandlerの正常returnからcomponent_successを記録する経路がある。現行のcomponent_successだけでダウンロード準備の成功率を計算しない。操作受信、処理結果、案内送信に明示的な結果契約を追加する。

自前HTTP要求にはproxy、キャッシュ、プレビュー取得、Range要求、再試行、リンク転送等の影響があり、1要求=1人のクリックではない。発行したURLを元の要求へ関連付けても、そのURLのアクセス者が元の操作ユーザーと同一とは保証しない。外部URLのクリック計測用リダイレクトや閲覧計測は今回の設計に追加しない。

サーバー側で観測できる転送の終了も端末の受信完了を証明しない。Node.jsのHTTP responseのfinishはOSへの引き渡し完了であり、クライアントの受信を保証しない。[Node.jsのHTTP仕様](https://nodejs.org/api/http.html#event-finish_2) ファイルstreamのendはさらに手前の読込終了である。Next.js等の配信adapterが実際に観測できる段階だけを記録し、最終転送状態が取れない場合は未取得とする。

## 3. 集計する事実の単位

一つの数字で異なる単位を兼用しない。

| 単位 | 一件の定義 | 重複排除・親子関係 |
| --- | --- | --- |
| 受信入力 | Botが受信した投稿・コマンド・ボタン等の一入力 | Gateway再配送は同一ID、投稿編集は入力版を分ける |
| 展開要求 | 入力内のURL出現とproviderに対応する一つの根要求 | 引用先・HTTP再試行は子処理。別入力で同じURLなら別要求 |
| 取得処理 | 一つの対象コンテンツを得るための処理 | primary/fallbackのHTTP試行を子に持つ |
| HTTP試行 | 実際に一回の接続・要求を開始したもの | 再試行は別attempt、同じ取得処理へ関連付け |
| 送信ステップ | 意図した一つのDiscord出力 | 添付失敗後の代替は同じstepの別attempt |
| ユーザー操作 | 人が行ったコマンド、ボタン等の一操作 | 内部の取得・送信・補足情報取得を利用回数に加算しない |
| コンテンツ | 外部サービスの一つの投稿/動画/作品等 | provider+content_id。ID不明時は版管理したcanonical URL |
| 外部指標の観測 | ある対象・取得元・時刻の一指標値 | 一つのコンテンツに複数観測がある |
| 障害 | 管理デーモンが関連付けた一incident | エラーevent数・影響要求数・修復回数とは別 |
| 設定変更 | 一つの変更action/revision | 個別キー差分は子。複数キーを変えても一つのactionを重複計上しない |

すべての要求・操作にtrigger_typeを持つ。human_message、human_command、human_component、automation、admin_operation、diagnostic等を区別する。既定の利用状況は人の実利用、稼働状況は自動実行も含む本番処理とし、画面に対象を明示する。診断・プレビューは通常の利用件数に入れず、発生させた実際の資源負荷は技術指標に残す。

autoextractの登録者を、その実行ごとの「操作した人」として数えない。メディアHTTP要求も、人の操作か識別できない場合は配信要求であり、利用者数や閲覧者数に変換しない。

adminのURL実行検証ページで行った外部取得・設定比較・テスト送信はdiagnosticに分類する。通常利用の要求数・利用者数・成功率から除外し、診断によるAPI要求・資源負荷・実行結果は専用の技術指標へ記録する。

サーバーID・チャンネルIDを指定する通常のサポート送信はadmin_operationに分類し、診断用の送信はdiagnosticとする。一般利用者の利用数へ混ぜず、実際のDiscord送信attemptと結果は目的別に技術集計する。元要求の復旧対応は別actionとして関連付け、過去の結果会計を改変しない。

## 4. 要求の結果と主指標

### 4.1 結果の会計

一つの根要求はsnapshot時点で次のどれか一つに属する。

- F：完全成功。Discord側で確認できる意図した出力の作成と必須後処理が完了。
- D：代替成功。指定された出力の代替を実施し、Discord側の作成を確認。
- P：部分成功。必要な出力や後処理の一部が失敗。
- E：処理失敗。技術的な失敗が確認された。
- U：取得対象の制約。取得元が提供不能等を示す。具体的理由は証拠の範囲で表示。
- S：設定等による見送り。一致するルールと根拠がある。
- C：明示的な取消。取消の主体・時刻・理由がある。
- I：実行中。待機・処理中であり、完了結果をまだ持たない。
- X：結果不明。記録途絶・送信成否不明等。確認済み失敗とは区別。

要求総数R=F+D+P+E+U+S+C+I+Xを常に検証する。元の受信eventの重複は受付側の重複件数にし、同じ根要求を増やさない。未認識URLは受付の認識結果として残し、存在しないproviderの要求を捏造しない。

期待する出力は当時の有効設定と仕様に基づいて確定する。設定どおりの省略・表示形式は正常な出力であり、障害による代替Dとは区別する。途中まで送信してから取消された要求をCだけで隠さず、残った出力と未達の範囲からP等へ分類する。必要な出力の成否が不明ならXを優先し、補助処理の不明だけでは要求全体をXへ変えない。

失敗案内を送信できても、元のコンテンツ取得失敗はEまたはUのままにする。案内送信の成功は別の出力結果。追加の分析情報取得だけが失敗し、必要な出力のDiscord側での作成を確認できた場合はFを維持し、補助処理失敗を併記する。

「完全成功」はBotが行うべき処理の完了であり、メッセージの閲覧、端末での正常な描画、メディア再生、読了を意味しない。Discordから正常応答を得たことと、実際の閲覧を分けて定義する。

### 4.2 管理概要の固定する主指標

| 指標 | 定義 | 表示・使い道 |
| --- | --- | --- |
| 展開要求数 | 期間内に受付した根要求R | 負荷・利用の規模。投稿件数と区別 |
| 完全成功を確認できた割合 | F / (F+D+P+E+U+X) | 分子/分母とS/C/Iを同時表示。Xを成功からも分母からも都合よく消さない |
| 問題のある要求数 | D+P+E+U+X | 各結果の内訳を表示。個別調査への入口 |
| 設定による見送り | S | 利用者の「反応しない」を調べる入口 |
| 影響サーバー数 | D/P/E/U/Xの根要求のguild_idのdistinct | サポート影響の範囲。guild不明は別件数 |
| 完了時間P50/P95 | 受付から最終結果確定まで。結果別に分布を分ける | 平均だけで遅い要求を隠さない。未完了の経過時間も併記 |

「完全成功を確認できた割合」はXを失敗だと確定する指標ではない。結果不明を含む評価対象のうち完全成功が確認できた割合である。式とラベルをセットで使う。未観測の要求はRに入れられないため、記録のcoverageと停止時間の資料を常に併記する。

保留Iが多い時間帯では率だけで品質を判断できない。「実行中」「最古の待ち時間」「結果不明」「統計の時点」を近くに置く。分母が0なら「対象なし」。記録自体が足りなければ「未計測/資料不足」。0%とは区別する。

### 4.3 数値例

R=120、F=80、D=5、P=3、E=7、U=3、S=10、C=3、I=7、X=2なら、完全成功を確認できた割合は80/100=80%。問題のある要求は20件、見送り10件、取消3件、実行中7件。内訳の合計は120件となる。

これを抽出・送信・補助処理の成功eventを足した「成功率」で置き換えない。Fだけをコンテンツ取得件数から推測しない。

## 5. 技術指標のカタログ

| 指標 | 単位・計算 | 集計上の条件 |
| --- | --- | --- |
| 受付から処理開始までの待ち時間 | 根要求ごとのqueue待ちms | 待機中のageと拒否件数を別表示 |
| キュー拒否数 | 満杯/期限切れの根要求distinct | 再配送された同じ拒否は増やさない |
| 取得結果内訳 | 取得処理単位の取得成功/対象制約/失敗/不明 | HTTP 200と有効なコンテンツ取得を区別 |
| 取得元別HTTP結果 | HTTP試行数を2xx/3xx/4xx/5xx/応答前失敗等に分類 | 実際のホスト、経路、attempt番号で集計 |
| 再試行を伴う取得割合 | attemptが2以上の取得処理 / HTTPを開始した取得処理 | attempt数とlogical処理数を分ける |
| 別取得元への切り替え割合 | fallbackした取得処理 / HTTPを開始した取得処理 | 対象がないときは率を作らない |
| キャッシュ利用割合 | cacheを照会しhitした取得処理 / cacheを照会した取得処理 | cache非対象をmissにしない |
| 解析失敗数 | 対応する解析処理の失敗数 | content/HTTP attemptに結び、raw例外件数とは別 |
| 送信ステップの結果 | 意図したstep単位の成功/代替/失敗/不明 | 一つのstepのretryを複数の成功要求にしない |
| HTTP送信試行の結果 | 実送信attempt単位の結果 | 内部原因の診断用。ユーザー成功率に流用しない |
| 後処理の失敗 | 元投稿削除・埋め込み抑制等のoperation数 | 送信の成否と独立して表示 |
| コマンド/ボタンの完了率 | 操作種別ごとの成功 / (成功+失敗+結果不明) | 対象外/拒否/取消/実行中を併記。異種操作の単純平均なし |
| 自前HTTP転送の状態 | HTTP要求受付、応答開始、サーバー側の送出終了、失敗、観測できた切断 | 端末での受信完了・保存完了・再生完了を意味しない |
| 補助情報取得の成功率 | enrichmentのlogical job単位で同様に定義 | Bot出力の成功とは分け、再試行数を別表示 |
| 設定反映時間 | DB保存時刻からBotの該当revision ACKまで | 未反映はageを表示。保存成功だけで完了にしない |
| 機能確認の成功割合 | 成功した機能プローブ / 結果を得た予定プローブ | 予定未実行・観測不能を併記。プローブ種別ごとに表示 |
| 修復後の確認結果 | 修復を試みたincidentごとの検証済み復旧/未復旧/確認中 | actionの成功とincident復旧を混ぜない |

稼働監視は要求量、エラー、遅延、資源待ちを基本にする。失敗が早く返るため平均時間だけ良く見える状況を避け、成功/失敗の時間を区別する。[Google SREの監視の考え方](https://sre.google/sre-book/monitoring-distributed-systems/)

CPU、RSS、swap、PSI、FD、DB待ち等は原因調査の技術指標として残す。独自の「健康度」に圧縮して実値を見えなくしない。

## 6. 利用状況のカタログ

| 指標 | 定義 | 呼ばない名称 |
| --- | --- | --- |
| 利用ユーザー数 | 期間内に意味のある人の要求/操作を行ったユーザーのdistinct | 閲覧者、視聴者、リーチ |
| 利用サーバー数 | 同じ利用事実のguild distinct | Bot参加サーバー総数との混同 |

| URL共有投稿数 | 対応URLを含む人の入力message distinct | 送信数、閲覧数 |
| 展開要求数 | 入力内の対象URLごとの根要求 | message数 |
| 機能別操作数 | コマンド/ボタン等のlogical操作数 | analytics全eventの合計 |
| 共有コンテンツ数 | 期間内の根要求に現れた外部content identityのdistinct | content event行数 |
| コンテンツ別共有回数 | そのcontentに対する根要求数 | 外部再生数 |
| コンテンツ別共有者数 | そのcontentを要求した人のdistinct | 見た人の数 |

## 7. 外部サービスの数値

### 7.1 型を定義する

| 指標の種類 | 例 | 集計 |
| --- | --- | --- |
| 対象の累積値 | 投稿のlikes、動画views、repository stars | 対象ごとのas-of観測を一つ選ぶ。観測eventを全部SUMしない |
| 時点の状態量 | live viewers、在庫、同時視聴者 | 対象・観測時刻ごとに表示。同時刻でない値を現在の合計にしない |
| 価格 | 商品価格 | 通貨・商品variant・税等の条件ごとに分ける |
| 評価値 | rating、評価比率 | 評価尺度と対象集合を明示。投稿件数で意図せず重み付けしない |
| 内容の属性 | 動画時間、画像枚数 | コンテンツ集合で平均するのか共有回数で重み付けするのか明記 |
| 分類 | tag、language、content type | 複数分類なら重複ありと表示。構成比合計100%を要求しない |

外部指標の観測はcontent identity、metric key、値、単位、取得元、計測版、観測時刻、適用可能性、取得成否、raw値を持つ。別providerのviewsが同じ測定定義だとは扱わず、全サービス共通の「反応合計」へ足し合わせない。

数値文字列はproviderごとに形式を定義して解析する。例えば1.2Kや1.2万を対応する形式で解釈し、未知の書式から数字だけを抜き出さない。0、null、取得失敗、対象外を区別する。評価尺度、通貨、秒/ミリ秒、整数範囲、負値の可否も検証する。

### 7.2 対象と観測時刻

「この期間に共有されたユニーク投稿の、取得時点の累積いいね数」という名前なら、その集合の各投稿について指定as-of以前の有効な観測を一つ選ぶ。選択順は観測時刻、取得元の優先規則、観測ID等で決定し、最大値を選ぶことで減少や修正を隠さない。

例：同じ投稿を3回取得して100、100、110いいねを観測したとき、最後の観測値は110。合計310を「いいね合計」としない。別の投稿が50なら、2投稿の観測値合計は160。ただし観測時刻が異なるなら、その時刻の範囲と鮮度を表示し、同時点の厳密な総数とは呼ばない。

増分は同じ対象・同じ定義・比較可能な二つの観測の差としてのみ表示する。観測区間が期間境界と一致しなければ「観測間の変化」とする。十分な観測がないのに「今週増えたいいね」を作らない。負の差を0へ丸めず、訂正・減少・取得元変更等の状態を表示する。

これらの外部指標をBotが生んだ成果やDiscord内の反応と解釈しない。Botによる効果を測るには別の観測・比較設計が必要であり、現在の値から補完しない。

## 8. 率・平均・分位点・ユニークの共通規則

1. 率は対象集合を揃えた分子/分母から計算する。分母0はnullと理由を返す。
2. 複数群の率をまとめる場合は分子合計/分母合計。割合の単純平均を使わない。
3. 例：1/2と100/100をまとめると101/102=約99.02%。50%と100%の平均75%ではない。
4. 平均は有効値のsum/count。0msが正しい観測なら含め、nullを0へ変換しない。
5. event一行にcount>1がある場合、その意味を登録する。代表時間をcount倍して個別時間の分布が復元できたとは扱わない。
6. unique users/guilds/contentは期間全体の集合を求める。日別・時間別のdistinctを足し算しない。
7. 複数タグやサービスを使うユーザーなど、重複する内訳の合計は全体uniqueと一致しない。加算できない指標を明示する。
8. 比率の分子が分母の部分集合であるはずなのに100%を超えた場合は、丸めて隠さず整合性エラーを出す。回数/出力などの強度は「回/件」として別定義にする。
9. 上位N件を選ぶ前に全体の分母を確定する。表示件数を変えても全体率・構成比・対象の値は変えない。
10. rawとaggregateは同じmetric definitionを使用する。UIで重みや補正値を独自に追加しない。

P50/P95等は対象のduration分布から求める。各時間帯のP95を平均して日次P95にしない。分布は互換なhistogramで集約できるが、その分位点は推定であり誤差幅を持つ。[Prometheusの分布・分位点の説明](https://prometheus.io/docs/practices/histograms/)

本設計では、常時の監視には版付きhistogramを保持して「P95推定」と表示し、詳細調査では保持期間内のraw durationから全対象の値を使う正確なnearest-rank分位点を分析workerで求められるようにする。件数・結果率・期限以内の件数は正確に計算する。rawがない期間に正確な分位点を再計算できるとは扱わない。

時間は受付基準の要求cohortで取り、遅延eventを同じ要求へ結ぶ。完了した要求だけが分布の対象になるため、結果別分布、未完了数、未完了のage、期限超過数を併記する。

## 9. 処理の経過とボタン操作の観測割合

計測する流れは「要求受付→取得/解析→Discord側の出力作成→自アプリのボタンinteraction受信」とする。メッセージが人に表示・閲覧された段階は観測できないため、この流れに閲覧を含めない。

- 要求ファネルはroot requestを単位にし、各段階へ到達したrequestのdistinctを数える。HTTP/送信の複数stepで人数や要求数を増やさない。
- 設定による見送り、取得対象の制約、技術失敗、未完了は枝分かれとして表示する。すべてを一つの離脱率にまとめない。
- 公開する率の名称は「ボタン操作を観測した送信メッセージの割合」とする。分母は追跡期間を満たし、自アプリの有効なcustom_id付き非リンクボタンを実際に含む、Discord側で作成確認済みのメッセージ集合。
- 分子は、その集合のうち追跡期間内に対象ボタンのinteractionを1回以上受信したmessage IDのdistinct。component_typeも確認し、selectやmodalをボタンとして数えない。
- Link/Premiumスタイル、disabled、非表示のボタンだけの出力は分母にしない。観測範囲の欠落、途中のcomponent変更・削除、追跡期間未満は適格性とcoverageに明示する。
- 出力の作成時刻をcohort起点とし、追跡期間が終了していない出力は未成熟と表示する。単に同じ暦日の送信数と操作数を割らない。
- 操作の受信と処理成功は別指標。受信後の権限拒否や処理失敗も、受信した操作がなかったことにはしない。
- 元出力不明・関連付け不能の操作は別件数にする。個々のinteraction IDで重複排除する。
- 分母は閲覧人数・閲覧回数ではないため、CTRや閲覧者の反応率とは呼ばない。割合の高低から、見た人の興味やクリック意欲を判断しない。

例：条件を満たす送信メッセージ10件のうち2件について、対象ボタンのinteractionを合計5件受信した場合、観測割合は2/10=20%、受信操作は5件。リンクボタンのクリック数や閲覧者数を計算したものではない。

SLOを設定する場合は、対象要求、起点、期限、完全成功の条件、除外条件、観測可能性を指標辞書へ登録する。判定期限がまだ来ていない要求を達成/未達に混ぜず、十分に追跡できるcohortで評価する。具体的な目標秒数・目標率は現状の実測と用途に基づいて決め、根拠なく95%等を正常境界にしない。

## 10. 継続利用・時間帯・変更前後

継続利用は人のlogical利用事実から計算する。サービス全体、特定guild、特定providerなどscopeを明示し、初観測の判定にも同じscopeを使う。記録開始以前やデータ欠落がある場合は初観測の保証範囲を表示する。

週次cohortはJST月曜00:00を起点とし、初観測週のユーザー集合を分母にする。W1等の対象週が完全に終了し、記録が揃ったセルだけを確定値として表示する。将来週・未成熟週は0%にしない。成熟していて再利用0人なら0/n=0%を表示する。

時間帯・曜日・日別・週別は同じtimezoneで集計する。保存時刻はUTCでも、表示ラベルだけ9時間ずらして曜日や期間境界を据え置かない。期間は開始を含み終了を含まない。途中の「今日」と完成した「昨日」を、そのまま同じ長さの期間と比較しない。

設定変更の比較は「変更前後の観測差」とする。変更単位はaction/revision、実際の適用時刻を基準とし、前後の期間長・曜日構成・対象guild/provider・trigger・build・coverageを揃える。後期間がまだ揃っていない場合は暫定値とし、十分な期間の比較を待てるようにする。

変更の重なり、同時デプロイ、provider障害、対象数の増減を併記する。同じ事実が複数の変更窓に入る場合、変更ごとの比較には使えても「全変更による増加件数」として重複加算しない。前0件→後12件はそのまま表示し、増加率を0%や無限大にしない。

相関・併用・前後差から「反応を伸ばしている要因」「設定が効いた」「需要がある」と断定する文言は除く。基礎となる件数・集合・比率・差分と元事象を保持する。

## 11. 指標辞書とAPI契約

すべての公開指標に以下を定義し、共通の版付き指標辞書を正本にする。

| フィールド | 内容 |
| --- | --- |
| metric_id / version | 意味が変われば版を上げる識別子 |
| label / purpose | 日本語名と、この値で判断すること |
| fact_grain / unit | 要求、操作、送信step、content等と、件/人/ms/%等 |
| population / inclusions / exclusions | 対象集合、trigger、見送り・取消・診断等の扱い |
| numerator / denominator | 率の場合の集合と式 |
| aggregation / distinct_key | sum、count、union、latest、quantile等とキー |
| time_basis / timezone / window / followup | 受付/完了/観測等の時刻、期間と追跡条件 |
| allowed_dimensions | guild/provider/host/user/content等の対応する切り口 |
| null_policy / applicability | 0、対象なし、対象外、欠測、取得失敗の区別 |
| observability / collection_status | APIで取得可能・自前計測・公開API非提供等と、実装/記録/取得の状態を別々に定義 |
| source / schema / recording_start | 必要な事実、計測版、計測開始 |
| comparison_policy | 比較できる期間・版・集合と必要な成熟条件 |
| drilldown_contract | 値の根拠となるID集合を取得する条件 |
| validation | 値の範囲、分子包含、会計等の検証 |
| precision | 正確値/推定値、推定法、誤差・原データの保持範囲 |

APIはvalueだけでなく、分子/分母、unit、definition_version、scope、window、as_of、watermark、read_status、coverage、precision、drilldownを返す。表示画面と自動診断ルールは同じ指標ID・版を参照する。単なるプロパティ名のsuccess_rateを横断して同じ意味とみなさない。

公開Bot APIで非提供の閲覧・リンククリックはobservability=not_exposed、value=nullとし、取得処理の未実装を意味するnot_instrumentedと分ける。通常のKPIや自動診断ルールの入力に置かず、指標辞書で取得できない理由を確認可能にする。

フィルターが指標に適用できない場合は対象外として説明する。例えば外部HTTPホストで絞った値を、投稿者の全体利用数へ無条件に適用しない。サービス全体の値でアカウント別の未計測を補わない。

## 12. 新しい画面の具体仕様

### 12.1 最初の画面

上部は共通の期間、JST、対象サーバー/サービス、trigger、比較期間。直下にデータの時点・未完了・記録欠落を表示する。

主指標は4.2の6項目。要求結果の積み上げグラフと、問題の多いサービス/影響サーバーを並べる。各色は結果分類に固定し、利用が多いだけで「正常」の緑にしない。

「何を見るべきか」は、影響が確認されたincident、問題のある要求、期限超過、記録不足の順に根拠付きで提示する。独自の機会・価値スコアで優先度を付けず、重大度、影響範囲、継続時間、実件数、policyの順序を公開する。

## 14. 保存・集計の実装方針

構成は、採用済みの証拠event、冪等に作る単位別fact、検証、増分集計、版付きsnapshot、両管理画面とする。指標辞書を集計API・分析worker・診断ルール・UIで共有し、表示側で意味を変える計算を行わない。

factは少なくともrequest、fetch、HTTP attempt、delivery step/attempt、human action、content identity、metric observation、setting change、incidentを区別する。すべてを一つのevent表へ入れる場合も、型と親子関係からこれらの論理単位を確定できる必要がある。

遅延event・結果訂正・再取り込みは同じID/版に適用し、旧結果の寄与を取り消して新結果を加える。F→P等の変更で総数が増えないようにする。重複取り込み、部分保存、初期とenrichmentの二重観測も検証する。

多対多のfacetをJOINしてから要求数をCOUNTしない。根要求の集合を確定し、別の粒度の表は必要な単位まで集約して結合する。URL・ID・版の正規化ルールは原値とともに保持し、意味のあるquery parameterを一律に消して別コンテンツを結合しない。

期間・scope・definition版・watermarkをsnapshot keyに含め、表とカード、掘り下げ先の時点を揃える。欠落のある入力から作ったsnapshotは完全な統計として公開しない。過去snapshotの条件で資料が残っていない場合は、再取得不能と説明する。

大量のrawデータの全走査を毎回行わず、加算可能なfactを増分更新する。distinctの集合・分布・外部観測のlatestは、それぞれに適した保存・索引を用意する。MySQLの実計画と導入先のI/Oを測り、分析workerへの移動だけで集計コストが解消したとは扱わない。

## 15. 旧データと比較の移行

現行の記録から算出可能なのは、旧定義のevent件数や対象別の一部統計。最終送信結果や親子関係がないものから新しい完全成功率・操作率を作らない。

旧データはlegacy_recordingとして、計算可能範囲と定義を表示する。新旧の値を同じ線で連続表示して改善/悪化と解釈させない。計測開始線・指標版・比較不可の区間を表示する。

まず新しいfactの記録を開始して旧集計と並行検証し、異なる値がどの定義変更によるものかを説明する。自動診断の閾値は新指標で校正し、旧success_rateやscoreの閾値をそのまま流用しない。

指標変更は履歴と影響する画面・alert ruleを管理する。匿名化解除、日時検索、全操作Web化、LLMなし、独立デーモンとの連携という受け入れ済み方針を維持する。
