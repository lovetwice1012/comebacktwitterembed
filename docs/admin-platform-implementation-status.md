# Adminサポート基盤の実装・検証状況

2026-09-05。管理画面を先に使える状態にするという依頼に合わせ、通常のNext.js admin、独立管理Web、操作workerをローカルで起動して検証した。本体ホストの公開経路とSSHが応答しなくなったため、本番サービスの切り替えは完了していない。

## 実装した入口

- `/admin`：要求単位の稼働・影響、サーバーIDと時間帯からの調査、原文・設定・処理段階・API試行への移動。
- `/admin/url-inspector`：実プロバイダーでのURL取得、展開プレビュー、HTTP応答・エラー、保存応答の再解析、同じ応答での設定比較。
- `/admin/send-message`：サーバー・チャンネル解決、宛先と送信内容の確認、実際の送信結果・メッセージID・成否不明の区別。宛先照合で個別の送信権限までは確定せず、実際の送信APIの応答を根拠とする。
- `/admin/support-console`：設定確認・変更・コピー・リセット、保存・自動展開・上限・アクセス管理、診断・監視方針・操作履歴。
- 独立Go管理Web：上記と同じ証拠・操作APIを利用。Bot、Next.js、Discord OAuth、MySQLの稼働を管理Webの起動条件にしない。既存の証拠と完了済みレポートは独立したSQLiteに保存する。

指標は根要求を重複排除して集計し、分母、期間、定義版、記録の有無を返す。通常メッセージの閲覧・既読・リンククリックは集計しない。新しい計測の開始以前の記録を、取得できたものとして復元しない。

## 実環境で確認した範囲

- ローカルのNext admin → Go管理コア → 別Node workerを経由して、公開GitHub URLを実際に展開した。展開結果と5件のHTTP 200応答、本文・ヘッダー・処理経過を画面で確認した。
- 実際のHTTP 404応答で、プロバイダーが本文を読まず終了してもエラーJSON全文が保存・表示されることを確認した。保存上限と取得期限は維持し、部分保存と取得失敗を明示する。
- 保存されたHTTP応答による再解析と、同じ受付キーに対する同一操作IDの返却を確認した。
- 許可されたテスト先へのDiscord送信はHTTP 200で成功し、後続の読み取りでもBot投稿・メッセージID・本文の一致を確認した。追加の再送は行っていない。
- 通常のNext APIへの未認証アクセスは401。ローカル検証用入口への外部Origin・不一致Hostは403。製品のOAuth・管理者判定は変更していない。
- OCIの外部監視サービスは有効化・起動済み。公開経路の障害を検出し、通知サービスからの受付を確認した。通知が人に読まれたことまでは示さない。

ローカル検証は本番MySQLの完全レポート生成、Linuxの特権操作、ホスト再起動後の復旧を確認したものではない。

基盤実装時の自動検証はNodeテスト515件成功、独立Webの表示モデル4件成功、Goの`test`・`vet`成功、ルートとdashboardの型チェック成功。ESLintはエラー0件（ルートに既存の未使用関数警告1件）。Nextの本番用ビルドも成功した。

その後、未生成レポートの構造化エラーをReactへ直接表示してadmin全体が落ちる不具合を修正した。4種類のレポートで未生成・生成中・失敗・前回完成済みを検証する9件の再発テストを追加し、関連15件とビルドが成功。エラー原文を保持しつつ、表示例外をレポート内に限定する。ローカル起動スクリプトにも専用レポートworker（34191番）を追加した。実際の再生成はworkerまで到達し、ローカルMySQL未接続によるエラーを記録した。本番DBへの接続と完全な集計結果の確認は引き続き必要である。

## 本番反映の状態

基盤実装はローカルのコミット `85286c1` として保存・push済み。本体ホストの既存履歴を維持してcherry-pickしたコミットは `25a17a3`。確認できたのはソース反映までであり、管理サービスの起動・nginx経路変更・Botの新コードへの切り替えは未確認。

OCIの監視対象は一時的に既存の公開ルートを使用している。本体側の独立管理Webを配備・確認した後、`/ops/healthz` に切り替える。

本体への接続回復後に残る作業は以下のとおり。

1. 現在の負荷、各サービスの状態、前回起動を含む実ログを読み、接続不能の原因を確認する。
2. Goバイナリの転送・ハッシュ照合、独立workerの実行環境と保護された設定ファイルを配置する。
3. Linux上でNextをビルドし、管理コア・分析・レポート・executorを起動する。
4. 既存の公開ポートを維持して、通常Nextと`/ops/`の独立管理Webへ振り分ける。
5. 本番MySQLで完全レポート、Botの新計測、認証、障害時の履歴読み取り、再起動後の状態保持を検証する。

## ローカルで再起動する方法

Nodeのルート依存、dashboard依存、ローカル用Goバイナリが必要。Goバイナリは`admin-agent`で`go build`して作成する。環境変数にはその実際の絶対パスを設定する。

```powershell
$env:CBTE_ADMIN_TEST_BINARY = 'C:\実際の配置先\cbte-admin.exe'
$env:CBTE_LOCAL_DASHBOARD = '1'
node scripts/run-admin-platform-local.cjs
```

通常adminは`http://127.0.0.1:34187/admin`、独立管理Webは`http://127.0.0.1:34188/`。Nextの上流、Go、workerはすべてloopbackで待ち受ける。通常adminの検証入口は、その起動限りの秘密鍵で署名したローカルセッションを付ける。本番認証の代わりには使わない。

独立Webの検証専用パスワードは起動スクリプト内の`password`定数に記載してある。これは本番の初期パスワードではない。起動時は読み取りのみを行うが、画面から選択した送信・設定変更等は実際の操作になる。

状態と診断ログは起動ごとの一時ディレクトリに残る。同じ検証状態を再利用したい場合だけ、`CBTE_ADMIN_LOCAL_STATE_DIR`に前回のディレクトリを指定する。停止は起動したターミナルでCtrl+Cを使う。
