# 切断中に保存済み通知を処理するための設計案

## 目的と現状

受信済みの暗号化通知がデータベースに残っていても、現行の定期処理は稼働中の受信セッションが持つ lease を使う。そのため、ネットワーク接続が戻らない期間にバッチの確認時刻が到来すると、次の受信 lease を取得するまで処理されない。通知内容を再取得したり、受信済みと推測したりせず、既存 inbox に保存された通知だけを対象とする。

現行の処理モード、契約プラン、確認間隔、利用資格、監視設定と重複排除をそのまま使う。ユーザーが設定した通知の送り先や通常通知の登録動作は変更しない。未到達の通知、FCMまたはWNS側が既に失った通知の復元を、この機構で保証しない。

## 既存データと競合

`automation_x_push_receivers` の lease は接続用と処理用を区別しておらず、`claim` は接続状態を `connecting` に変更する。`recordRetry` は有効な lease があると書き込みを見送る。切断の直後に別の worker がこの lease を処理用に取得すると、接続失敗の retry 時刻が永続化されず、再起動後の再接続抑制が失われる可能性がある。接続用 `claim` をそのまま流用してはならない。

接続結果の遅い callback が、新しい接続に対して古い retry を記録することも防ぐ必要がある。lease token を処理用と接続用で共有するだけでは、この世代関係を識別できない。単に `worker_id` の文字列接頭辞を信頼する方式は、永続的な所有権の根拠にしない。

## 採用前に決める境界

候補は、既存 receiver 行に目的と接続世代を識別する情報を追加する方法、または接続用と処理用の所有権を別の永続的なフェンスで表す方法である。いずれも次を満たす必要がある。

1. 接続結果の retry 更新は、対応する接続世代だけに適用する。処理用 lease の有無で接続結果が失われず、古い接続結果が新しい成功を上書きしない。
2. 処理用と接続用は同じ subscription に同時に有効にならない。取得・更新・解放は owner → subscription → receiver の順にロックし、token・revision・期限を検証する。
3. 処理用 lease の取得・解放は `state`、`reason_code`、`retry_at_ms`、`retry_attempt`、`last_connected_at_ms` を接続状態として偽装しない。接続失敗の表示と再接続方針を保つ。
4. 処理用 lease は保存済み通知の処理だけに使い、ブラウザーや通知サーバーへ接続しない。資格が失われた owner や削除・無効化された監視には処理を開始せず、サーバー側のトランザクションでも再確認する。
5. `requires_reenrollment` の receiver で通知を送るかどうかは、既存の利用停止ポリシーと整合を確認するまで変更しない。勝手に登録や購読を再作成しない。
6. スキーマを拡張する場合、既存の有効 lease は接続用として安全に扱い、旧 worker と新版が同時に動く期間を定義する。旧版へのロールバックで新しい所有権を誤認しないことを確認する。

`retry_at_ms` が未来の切断済み receiver だけに限定すれば、retry 記録前の競合を避ける暫定方式は可能である。ただし、プロセス異常終了で retry が記録されず、接続枠も満杯のケースでは保存済み通知が滞留するため、これだけで本要件の完成とはしない。

## 候補の検索と実行

- 既存 subscription / receiver と、`automation_x_push_inbox` の `(subscription_id,status,id)` インデックスを使って、現在のrevisionに処理可能な保存済み行がある切断中の候補を検索する。通常の通知取得を新設せず、所有者ごとに紐付いた有効な監視が存在することを確認する。
- 接続候補とは別のキーセットcursorを使い、1巡回の候補数と処理開始数を既存の `pageSize` 以下、並列DB処理を既存の `drainConcurrency` 以下に制限する。接続の開始・更新と処理候補の双方が継続的に進むようにする。
- 取得した処理用 lease を既存の `drain` に渡す。バッチは既存の `beginProcessing` と現在の契約プランの間隔に従い、リアルタイムは監視ごとの現在の資格と設定に従う。枠の種類によって処理品質を変えない。
- 期限前なら `dueAtMs` を使って再確認を控える。キャッシュは上限付き・再起動で消えてよい補助情報とし、DB上のウィンドウ・cursorを唯一の根拠とする。設定変更を検知したら該当する補助待機を解除し、資格と間隔を再評価する。
- 処理中は必要に応じてleaseを更新し、更新失敗・停止・権限失効・revision変更時には処理用signalを止める。タイムアウト後に始まる遅いcallbackは書き込み前に停止し、すでに送信されたDB COMMITの結果は不確実として扱う。receiver行のロックでlease交代・変更と直列化し、後の重複排除で再処理を安全にする。
- 障害時はciphertextと既存cursorを残す。ユーザーや監視、別のsubscriptionのデータを探索・復号・破棄しない。失敗理由には通知本文、鍵、token、接続先を出さない。

## 必須の検証

1. 切断後のバッチ通知が期限より前には送られず、期限到来後は接続が復帰しなくても処理される。現在のプラン間隔、優先度、送信枠、処理済みcursorが維持される。
2. 対象プランのリアルタイム通知は保存後に処理され、対象外・設定変更・資格失効時は既存ポリシーを守る。別の監視やユーザーの優先度と枠は変わらない。
3. 接続用claimと処理用claimの同時実行、処理中のlease更新・期限切れ・削除・revision変更で、同じreceiverの二重所有や古いtokenの書き込みが起こらない。
4. 切断結果のretry記録と処理用claimの順序を入れ替え、成功した新しい接続を古い失敗が上書きせず、backoffが消えない。旧版混在・異常終了後・再起動後も検証する。
5. 処理用leaseの取得・解放や失敗で、接続状態、理由、retry時刻・回数、最終接続時刻を失わない。`requires_reenrollment` は現行の停止ポリシーを維持する。
6. DB障害、期限切れ、signal停止、COMMIT前後の競合で、再送済みイベント・ジョブが二重作成されない。所有権が失われた後に開始するcallbackは書き込まず、COMMIT送信済みの不確実な結果は重複排除で回復する。
7. 受信済み件数が1ページを超える場合のcursor、途中停止、再起動、pending状態、未対応形式と、別ユーザーの同一Xアカウントを検証する。
8. 1000件以上の候補でページング、同時接続・処理の公平性、DBプールの最大同時使用数、空きなし・大量エラー・プラン変更を検証する。10000接続の実運用能力は、別途実測するまで保証しない。
9. Chrome・Brave・Firefox・Edgeの既存受信、通常通知、管理画面、移行とロールバックを回帰確認する。実X・Discordの確認は利用者が後日行う方針を維持し、本番DBや本番設定には試験を書き込まない。

この文書は設計案であり、処理専用leaseの実装や上記試験の成功を意味しない。

## 試験中の実装と運用上の制約

接続用 lease とは別の処理用 lease と接続世代を追加し、保存済み inbox の処理候補を独立した cursor で走査する試験実装を追加した。1 回の走査は最大 100 件、処理の並列数は既存の drainConcurrency 以下に制限する。通常セッションの drain と処理用 drain は別々に制限されるため、合算すると最大でそれぞれの設定数に達し得る。これは全 DB 接続数の保証ではなく、実運用の負荷測定が必要である。

処理用 scheduler は現行 runtime には接続されておらず、環境変数や verifier の指定だけでは有効化できない。今後の接続には、両 pool が同一の書き込み DB を使用することと、旧 receiver がすべて停止したことを証明する仕組みが必要である。どちらも未実装であり、本番有効化はできない。権限・プランは処理時に再確認し、停止中や確認間隔の変更を特別な固定値で上書きしない。

### マイグレーションと戻し方

新規列の `20261112_add_x_push_processing_lease.sql` は既存行を削除しない準備である。適用前にバックアップ、対象 DB と適用履歴を確認し、既存のマイグレーション手順で一度だけ適用する。途中失敗時は列ごとに存在を調べてから復旧し、SQL ファイル全体の再実行が無条件に安全だとは見なさない。処理用機能が無効なら追加列は残したまま旧版に戻す方法を優先する。

処理用機能を使用した後に旧版へ戻す場合は、先に機能を停止し、すべての新 worker を停止して処理中 transaction の終了を確認する。旧 worker の開始前に、処理用 lease が解放済みまたは期限切れであることを DB 上で確認する。移行・削除する inbox や登録データはない。列の削除は不要だが、やむを得ず削除するなら別途バックアップと停止時間を確保し、上記確認の後に実施する。処理用 lease が有効な状態で旧 worker を開始すると旧版はその存在を認識しないため禁止する。

期限・中断の通知と DB COMMIT の間に競合は残る。既に送信された COMMIT が中断後に成功するかは保証できないが、receiver 行ロックと重複排除で別の所有者による更新と直列化する。未受信の通知や接続先が失った通知の復元はできない。実 DB の移行・障害・停止・再接続の検証、実機の X 通知、fleet 互換性証明の実装を終えるまで、この機能を本番用として扱わない。

バッチ待機を示す `dueAtMs` は最大 2,000 件の補助キャッシュに保持する。候補走査のたび現在のプラン間隔と、その subscription に結び付いた有効監視の realtime/batch 状態を読み直し、値が変わった場合は期限を待たず再評価する。期限到来・停止・上限超過でも削除され、再起動後は DB の処理窓に基づいて復元する。監視やプランの変更から反映までの時間は独立 cursor の巡回時間と DB 応答時間に依存する。保存済みリアルタイム監視がある場合はこの待機を適用しない。

通常の受信接続は処理専用 lease に優先する。受信できる候補は同一 worker で先に開始し、別 worker に処理 lease がある場合も receiver 行のロック内で処理 token を失効させ、新しい接続 token を保存する。処理側は次の書き込み時に token が一致せず停止する。すでに DB transaction 内で処理中なら接続側がロック待ちし、その commit 後に切り替わる。再接続が retry 期限前、再登録待ち、または別の接続が使用中の場合は処理 lease を取り消さない。

互換性 verifier は非ブロッキングなローカル証拠だけを参照し、同期的に `true` または `false` を返す。非同期結果は失敗として扱い、DB ロック中に fleet 検査の完了を待たない。ただし同期コード自身が event loop を占有する場合を JavaScript 内から強制停止することはできず、verifier の実装と運用側で保証する必要がある。

処理専用の SQL は、明示した 1〜4 接続の新しい pool と、その pool に束縛した store・gateway・router・queue・graph store を使用する。共通 pool の接続数を処理専用 read が占有しないようにするためであり、DB サーバー全体に追加接続の余裕があることまでは保証しない。構築した pool の停止・close は生成した呼び出し側の責任である。待機中の SQL が解除されない場合、pool close が待ち続ける可能性もある。既存 runtime の環境設定だけから新 pool を生成・有効化することはない。

上記の構成部品は現行 runtime には接続していない。別 pool の credentials が同じ論理 DB と同じ書き込み系を指すことは、factory が返すオブジェクトだけでは証明できないためである。たとえ同名 schema でも異なるサーバーや書き込み先に接続すると、lease と重複排除が分断される。将来の接続時は、信頼できる deployment 設定と DB 側の一意で持続する識別子を使い、両 pool の同一書き込み先を検証し、failover 時も再確認する必要がある。split-brain・proxy・復旧後などの異常試験を通すまで利用しない。

## 同じ接続内での一時的な所有権に関する調査

同じDB接続のトランザクション内でだけ既存の接続用 token を一時的に設定し、保存済み通知を処理してから token を消して commit する案を調べた。トランザクション外に token を公開しないため、旧 worker の接続取得と retry 更新は行ロック待ちとなり、終了後に処理できる。通常 pool の同じ接続上で完結すれば、異なる書き込み先にある別 pool による所有権の分断も避けられる可能性がある。この案は現行 worker に接続していない。

隔離 MariaDB 11.4.10 と、Git の `4a6d082` にある旧 store 実装を使った合成試験では、旧 claim / retry の待機、外部に誤った接続状態が見えないこと、失敗時の rollback、暗号化 inbox から既存 gateway / router / queue へのバッチ処理、キュー投入後の例外と内側の例外捕捉時の rollback、遅れて再開した処理の SQL 拒否を確認した。これは1件の合成通知と限定的な競合試験であり、本番利用の根拠ではない。

**この案には未解決の障害がある。** トランザクション中に `SELECT SLEEP(4)` を実行し、クライアント側で250ms後に接続を破棄しても、MariaDB は実行中の問い合わせが終わるまで行ロックを保持した。旧 worker が接続を取得できたのは接続破棄から約3.75秒後だった。JavaScript のタイムアウトと socket 破棄だけでは、DB側の処理中断・ロック解放時間を保証できない。実行用 adapter と再現試験は `experiments/chrome-push` に研究用として置き、通常起動経路には接続しない。

MariaDB のサーバー側 `max_statement_time` は中断の確認点に依存し、すべての操作を厳密な時間内に中断する保証ではない。また MySQL の同種機能は適用範囲が異なる。[MariaDB の説明](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/query-optimizations/aborting-statements) を参照。別接続からの `KILL` も、対象セッションと同一の書き込みサーバーを確実に識別できないままでは、別の接続を停止する危険がある。DBの種類、プロキシや切替経路、権限、サーバー側中断と実際のロック解放を検証しないまま導入しない。

同じ隔離環境の比較では、その接続の `max_statement_time` を0.5秒に設定すると `SLEEP(4)` は中断され、接続破棄の約251〜258ms後に旧 worker の claim が完了した。ただしこれは単一の人工的な問い合わせであり、実際の全SQL、ストレージ処理、COMMITの時間上限の証明にはならない。別の試験で、このセッション設定は commit 後に同じ pool 接続を再利用しても残った。共通 pool に無条件で設定すると既存通知など別の処理へ影響するため、セッションの復元・失敗時の接続破棄を含む設計が必要である。いずれも本番設定は変更していない。

再現試験は `experiments/chrome-push/atomic-legacy-transaction-experiment.test.cjs` で、`4a6d082` の Git object と明示された非本番 loopback MariaDB を必要とする。毎回ランダム名の試験専用 schema を作成・削除し、最後にテスト用接続を閉じる。上記の隔離 MariaDB では10件成功し、このうち「接続破棄後もロックが残る」ことを確認する試験の成功は問題解決ではなく、問題を再現できたことを意味する。テスト用 adapter の動作を模擬接続で調べる単体試験は `scripts/test/x-push-atomic-db.test.js` にある。
