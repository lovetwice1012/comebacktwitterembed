# Windows Edge の合成通知試験

2026年11月11日に、使い捨ての Edge プロフィール、ローカルの試験用購読、試験用 MariaDB を使い、実際の WNS と受信ワーカーを接続した。X や普段使うブラウザーのプロフィールは使用していない。試験用サイトの origin は、X 専用経路を通すため試験時だけ置き換えている。

合成通知について、購読情報と鍵の照合、受信、試験用 DB への保存と復号を確認した。設定用 Edge を開き直して受信を抑制した状態でも、ワーカーが通知を受け取り、ブラウザー側ではその通知を受け取らなかった。サーバー側で更新されたトークンは設定ファイルの再登録後も維持され、再登録後の合成通知も受信できた。

同じ試験に、配布用 `EdgeSnapshot.ps1` のコピーと片付けを接続し、使い捨てEdgeプロフィールからのロック付きコピーと一時コピー削除を確認した。さらに配布ZIPを展開し、コピーした合成プロフィールを使ってパッケージ内のファイル保存処理を直接呼び、作成したファイルを読み戻してワーカーに登録した。その後のWNS受信と再登録後の受信も成功した。取得用のローカル試験originは読み取り試験用に書き換え、他サイト通知の同意は試験用引数で与えている。配布画面の操作、実際のX購読、利用者によるアップロードを通す試験ではない。

合成ストアにX以外のoriginだけ、分類できないレコードだけ、両方を追加した3通りで、明示同意なしでは保存処理が拒否され、出力ファイルが作られないことを確認した。両方がある状態でも明示同意ありでは保存し、そのファイルで受信できた。確認ダイアログの実操作は含まない。

先行セッションを正常に閉じてから別のNodeプロセスを起動し、試験用DBに保存された更新後トークンでWNSへ接続して、新しい合成通知を受信できた。試験用の秘密鍵は親子間のIPCだけで渡し、ログには出さない。先行セッションは試験を制御する親プロセス内で動かしており、親プロセスの終了や強制終了からの復旧を検証したものではない。

別途、WNS接続の確立後に試験用子プロセスを強制終了した。終了直後はリースが残り、他のワーカーが取得できないことを確認した。通常の30秒リースが自然に失効するまで待ち、試験側で取得・解放してから新しい子プロセスを起動し、保存済みトークンによる再接続と新しい合成通知の受信を確認した。

追加試験では子プロセスを強制終了した直後、新しい受信プロセスを起動する前に、別の識別内容を持つ合成通知をTTL 300秒で1件送信した。リースの自然失効を待って新しい子プロセスを起動したところ、その通知を受信できた。保存・ACKの途中での強制終了、長時間の停止やOS再起動は検証していない。

同じ停止期間に識別内容の異なる合成通知を3件送った試験は、2回とも**30秒の再接続後確認で1件しかDBに現れず、失敗**した。対照として、同じ3件を再接続完了後に送ると、3件がそれぞれ1件ずつDBに保存され、その後3秒の観測でも重複はなかった。試験側は通知内容自体を出力せず、受信件数だけを診断する。これは停止中の欠落が起こりうる証拠であり、Edgeの公開前に解決すべき問題である。`X_NOTIFICATION_EDGE_ENABLED` は既定で無効にしておく。

[MicrosoftのWNS raw通知の説明](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/push-notifications/raw-notification-overview)では、オフライン時にキャッシュされるraw通知は最大1件とされる。今回の結果と整合するが、この試験だけではEdgeのWeb Pushがその制約に該当したと断定できず、欠落箇所も特定できていない。Web Pushの受け渡しと復旧可能な元データを調査し、3件すべてを停止後に復旧できる方式を検証するまで、停止中の通知を保持できると案内しない。

切断直後の通信状態を区別するため、子プロセスの強制終了から5秒待って3件を送る試験も2回行った。いずれも再接続後に3件すべてを確認できず、2回目の識別結果では最後の3件目だけがDBに保存された。3件の送信要求はいずれもHTTP 2xxで受け付けられている（試験で使用するWeb Pushライブラリはそれ以外をエラーにする）。送信受付は全件配送の保証ではなく、この結果もWNSの1件保持という説明と整合するが、正確な欠落箇所は引き続き未確定である。

送信側が各通知に異なるWeb Pushの `Topic` を設定できたとしても改善するか、合成サイトで3件に別々の値を付けて同じ停止試験を1回行った。送信要求は3件とも受け付けられたが、再接続後にDBで確認できたのは最後の1件だった。この結果はXがどのヘッダーを使うかを示さず、送信側ヘッダーの変更による解決を証明するものではない。

停止時間をなくすため同じ購読のWNS接続を重ねる候補も、別々の使い捨てEdgeプロフィールで2回試した。先行接続で合成通知を受け取った後に2本目を接続すると、通知送信前に先行接続が停止し、次の合成通知は2本目で受信・復号された。2本目の保存とトークン更新は試験用のメモリー処理であり、製品用の二重接続や自動切替ではない。この結果だけで停止原因やすべての接続条件を断定できないが、単に同一購読へ並行接続するだけでは安定した待機系を確保できない。

現在の移譲ファイルはPush受信情報だけを保持し、CookieやXの通知履歴は含まない。受信されなかった通知をそのファイルから再構成することはできない。[MicrosoftのEdge設定説明](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/forcebuiltinpushmessagingclient)ではWindows標準とEdge内蔵のどちらのクライアントもWNSへ接続するため、切り替えるだけでWNS上の保持問題が解消するとは確認できない。通常のブラウザー設定や管理ポリシーは変更していない。

抑制の試験は、ワーカーでの受信、ブラウザーでの非受信、ワーカーの継続をすべて成功条件とする。ワーカー受信後も3秒間、ブラウザー側の遅れた受信を観測する。この短時間の合成試験は、すべての遅延や環境で二重受信が起きないことを保証するものではない。

`scripts/native-test/edge-live-synthetic-runner.ps1` は明示的な `-TestOnly` と、指定名・イメージ・localhost ポートの試験用 DB を要求する。依存パッケージは本番用とは別の `artifacts/edge-fixture-deps-20261111/node_modules` に置き、起動した試験プロセスは Windows Job で管理する。`-Takeover -Reimport` で開き直しと再登録を試す。試験終了後、今回使用した DB コンテナーと Edge の試験プロセスが残っていないことを確認した。

この結果は合成通知の範囲に限る。実際の X 通知、Discord への配送、OS やサーバープロセスの再起動後の動作、負荷、macOS 実機での動作は確認していない。実 X での確認は利用者の意向により後で行う。

受信セッションが観測済みの接続版を明示的に扱えるようにし、従来どおり省略時は版1とした。使い捨てWindows Edgeプロフィールから取得した情報を使い、版2で実際の受信セッションの接続、更新トークン保存コールバック、再接続を確認した。通知配送やDB永続化はこの試験の対象外であり、Mac版の受付や本番有効化にも接続していない。停止中に複数通知が欠落する問題は未解決。

版2接続の追加試験では、テスト専用プロセスだけで受信セッションに版2を明示し、使い捨てEdgeプロフィールの合成購読から、配布ZIP内の保存処理、所有者に結び付けたDB登録、WNS経由の通知受信・復号・DB保存まで成功した。通常の受付形式と本番接続は変更していない。版2でのプロセス再起動後の受信と、停止中の複数通知保持はこの試験では未検証。

接続版2を観測した場合、その値を設定ファイルに保持し、暗号化保存・再登録・受信処理に引き継げるようにした。従来のファイルは版1のまま扱い、接続版の変更だけで別購読とは判定しない。版2の受付と受信はそれぞれ既定で無効な X_NOTIFICATION_EDGE_CONNECT_V2_ENABLED を必要とし、Edge自体の有効化も別途必要。合成DBでは旧形式からの再登録で新しいトークンと既存通知を保持し、無効時の接続拒否と有効時の版2使用を確認した。停止中の複数通知欠落や実X通知の確認が終わるまで有効化しない。

版2を保存・復元する通常のワーカー経路を、独立した試験フラグ付きの使い捨てDBと実WNSで再検証した。テスト側で旧形式の出力に版2を明示的に加え、DBへの暗号化登録後、実ワーカーが送信するCNT版2を確認し、合成通知の受信・復号・保存に成功した。Windows配布ツールが観測した版2を自動出力する部分と、停止中の通知欠落の解消は未完了。

Windows版の試験用配布ツールを更新し、専用プロフィールの認証済み接続から接続版とagent情報を取得して保存ファイルに反映するようにした。接続版1は旧形式のまま、版2は明示して保存し、未知の版は拒否する。使い捨てEdgeと実WNSで、版2の観測から配布ZIP内の出力、DB登録、ワーカーの版2接続、合成通知受信まで確認した。これはプレビュー10のソースであり、ダッシュボードから提供中の固定済み配布物は更新していない。実X通知と停止中の複数通知復旧は未確認。

版2を使う使い捨てプロフィールの試験で、設定用ブラウザーの再起動時も受信ワーカーが動作し、同じ購読の再登録後もサーバーの更新済みトークンを保持した。別プロセスへの引き継ぎと、受信中プロセスの強制終了後にリースが失効してからの再接続でも、それぞれ新しい合成通知を受信できた。各子プロセスが版2の接続要求を送ったことも確認した。停止中の複数通知を復旧する試験ではなく、その欠落問題は未解決。

同一Nodeプロセス内で1,000個のEdge受信セッションを作り、ローカルTCPの合成サーバーに64件ずつ間隔を置いて接続した。全接続を同時に維持してから通知を送ると、各利用者の受信と保存が混ざらず成功した。TLS・実WNS・実DBや長時間運用の容量試験ではない。対照として同時に1,000接続を開始したローカル試験では768件がECONNREFUSEDとなり、急激な接続集中に注意が必要である。実際の運用容量や失敗原因をこの試験だけで断定しない。

多数の設定が同時に更新された場合、更新待ちと通常の候補を合わせた1回のワーカー巡回での新規接続開始数を、既存のページサイズ以下に制限した。両方を交互に処理し、更新が集中しても新規登録が継続的に後回しにならないようにする。合成試験では開始件数の制限と全候補の処理を確認した。この制限は切断中にWNSで失われた通知を復旧するものではなく、実サービスの負荷限界も未確認。

接続直後の切断で、受信済みの認証応答と通知が保存されない経路を合成ソケットで再現し、bound接続に限って応答の検証と更新トークンの保存を終えた後に通知を保存するよう修正した。不正な応答、権限喪失、トークンの保存失敗や未認証の通知は保存しない。切断後の復旧中に保存が失敗した場合は通常の切断と区別してエラーを返す。関連する合成テスト83件が成功した。保存済みの通知は後続スキャンを待つ場合があり、配送完了は未検証。保存失敗時の未保存データの復旧も保証できない。この修正は停止中の複数通知が1件になる問題の原因特定や解消を意味しない。
