# 保存済み通知の処理並列数に関する実験

この文書と `experiments/chrome-push/bounded-receipt-scheduler.cjs` は研究用です。通常のワーカーには接続しておらず、公開設定や既存の確認間隔を変更していません。

現在のワーカーは、定期処理の並列数を制限していますが、受信直後の処理はその上限を共有しません。また、定期処理が長時間戻らないと、次の巡回自体が進まない場合があります。試作では購読ごとの受信・定期処理・切断時回復をまとめ、同時実行と保留件数を制限しています。通知本文や暗号鍵はキューに入れず、暗号化された受信箱を再確認する前提です。

実行中の作業は、deadline や停止 signal だけでは空き枠として扱いません。実際に処理が返ったときに枠を解放します。タイムアウト件数、使用中の数、最長実行時間を観察できますが、すべての作業が永久に戻らない場合に自力で回復する仕組みはありません。DB の処理や送信済み COMMIT が取り消されたと推測せず、呼出側は所有権の確認と重複排除を続ける必要があります。

定期走査の実験 scanner は購読 ID を回転し、queue が満杯になった位置から次回再開します。stale session や別 signal の上限は満杯と区別して先に進みます。回復要求は通常の保留領域が満杯でも別の上限付き領域で待ち、処理完了または lease の deadline signal を待ちます。通常 signal が2本ある場合にも回復 signal 用の枠を残します。回復待機領域の上限超過や同じ lease に対する別の回復要求は固定の失敗結果で返します。現在の gateway は回復 callback の失敗を握り潰すため、統合前に失敗を記録・通知する契約と lease の扱いを設計しなければなりません。

ランダムな token の文字列には新旧順序がありません。試作は信頼された `isCurrent` が現在の session と token を同期的に確認できることを必須とし、受付時と実行直前に確認します。実 DB の owner・subscription・receiver のロックと lease fence を代替するものではありません。session の終了時には対応する token だけを中断・削除する必要があります。

使い捨て MariaDB 11.4.10 を使用し、暗号化 inbox と既存の realtime `runtime.drain`・queue を接続した試験が成功しました。上限1・待機1で3件目の直接 wake を保留し、回転 scanner で後から再投入して、3件をそれぞれ1ジョブに処理しました。停止した回復の lease を解放して後継が取得し、遅延した旧 lease の処理が拒否されることも確認しました。別の試験では、8接続の試験 pool で2件の SQL を意図的に待機させても、別の単純な SELECT が実行できました。これは特定の合成負荷であり、通常業務全体や DB サーバー自体の停止に対する保証ではありません。

単体試験23件では1,000購読の保留上限、通常・即時作業の公平性、旧 token の遅延通知、回復 deadline、停止後の遅延 callback と失敗後の再走査を確認しました。同じ購読の wake が1万回続いても、次の pump microtask を1個にまとめ、停滞中に繰り返す走査が同じ Promise の handler を増やし続けないことも確認しました。上記の隔離 MariaDB の結合試験2件は、最終試作で再実行しました。試作の scanner と scheduler は実ワーカーに接続していないため、この結果は現行 worker の自動再探索や実 FCM・X・Discord の成功を意味しません。

本番統合には、少なくとも次が必要です。

1. 全受信・定期処理・回復経路が同じ scheduler を通ること、満杯時の wake ID を永続 inbox から公平に再探索できること、各監視のリアルタイム設定と現在のプラン間隔を維持すること。
2. 回復 callback が完了・deadline・明示的な失敗まで所有 lease を保持し、満杯・中断・旧 worker の遅延 callback でも通知や重複排除を失わないこと。特に gateway が実験用の失敗結果を無視しないこと。
3. 接続が切れても SQL 実行中のサーバーロックが残る場合、送信済み COMMIT が成功する場合、DB pool や DB サーバー全体が止まる場合の運用と回復。枠を強制的に空けて同じ処理を無制限に再起動しないこと。
4. 現行の共通 pool は既定8接続、drain 上限は既定16です。単に16枠の scheduler を追加すると、他の通常機能の接続を確保できません。別 pool の同じ書き込み先の証明や、pool 全体の予約・容量予算が必要です。2/8 の合成試験だけで本番での保護を主張できません。
5. 複数 worker の移行・旧 worker 混在、長時間の切断、プラン変更、実 DB の同時負荷、プロセスの停止と再起動をテストすること。実 X 確認は利用者の希望どおり後日行います。

独立レビューでは、現行 gateway の通常受信 callback を scheduler の同じ未完了 Promise に何度も接続すると、gateway 側の待ち時間が切れても Promise 自体は解決されず、長時間の停滞中に handler が蓄積し得る点も指摘されました。通常受信の wake は、拒否しない固定結果を返す fire-and-forget 等として寿命を限定し、回復 callback は別途 deadline まで待つ設計と検証が必要です。試作の scanner が handler を増やさない試験は、現行 gateway との統合を証明するものではありません。
