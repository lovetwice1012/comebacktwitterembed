# Chrome Push 受信の検証メモ

Chrome用のWindows配布ツール、登録画面、暗号化保管、常駐受信ワーカーを実装しています。既定ではChromeの受付・受信は無効です。実際のXアカウントを使った通知とDiscordへの配信は、利用者の希望により後日確認します。

Chromeのログイン失敗後、現在の登録で有効な監視があり、受信機能が有効で再接続が予約されている場合は、登録画面と監視画面に「再接続待ち」と表示する。別の利用者の情報や内部エラーコードは返さず、古い登録版・停止中の監視・期限を過ぎた予約を再接続待ちとして表示しない。画面と隔離DBの試験でこれらの条件を確認した。表示は再接続の成功や通知の到着を保証するものではない。

## 確認したこと

Windowsで新規作成した一時Chromeプロファイルとローカル試験サイトを使用し、ChromeがWeb Pushの購読を作成して通知を受信できることを確認しました。Chromeを終了した後、試験用プロファイルのGCM情報と鍵を使ってMCSにログインし、その後に送信した別の試験通知を受信・復号できました。購読の公開鍵と認証情報は、保存された秘密鍵と一致することを検査しています。試験は実際のFCMを利用しますが、XやDiscordは使用しません。

Chromiumは製品のcategoryが登録時の値に一致する場合に限り、アプリ識別子としてsubtypeを信頼します。この条件と送信元の照合を両方満たすメッセージのみを対象とします。受信接続にはプロファイル共通の情報が必要なので、他のサイトの通知が到着する可能性があります。

配布ZIPを実際に展開し、専用Chromeで作成した試験購読からファイルを作成しました。登録画面と同じサーバー処理へ手動アップロード相当の操作を行い、暗号化保存、FCMからの受信、隔離MariaDBへの保存、既存ワーカーによる通知ジョブ作成まで確認しました。ローカルの試験サイトをXと同じoriginとして動かした合成データであり、実際のX購読・Discord配信の検証ではありません。ほかのサイトの通知がある場合、明示的な許可がなければファイルを作らないことも確認しました。

対象の暗号化データと再送IDは同時にDB保存し、その後に受信確認します。保存失敗とlease期限切れで両方がロールバックされること、再起動相当のストア再作成と他ユーザーの拒否を実DBで確認しています。送信失敗と再接続時のID引き継ぎはモックによる単体試験です。PCとスマートフォン幅の登録画面はローカルブラウザーで表示・操作を確認しています。

隔離した Alpine Linux 3.24.4・Node.js 24.22.1 では、MCSと端末確認の単体試験27件と、Linux MariaDB 11.8.9を使うワーカー試験12件が成功しました。さらに、Windowsの試験専用Chromeが作成した購読情報を標準入力だけでLinuxプロセスへ渡し、Googleへの端末確認、実FCMからの受信、隔離DBへの暗号化保存、実ワーカーによる通知ジョブ作成まで確認しました。5分のまとめ処理は試験用DBの時刻を調整して再現しています。実際のXやDiscord配送、本番DBは使用していません。

差分のセキュリティレビューでは、初期実装のChromeデバッグ用TCPポートに別プロセスが認証なしで接続できる問題を確認しました。配布版はChromeとの通信を継承されたパイプへ変更し、ローカルの仲介接続は専用フォルダー内で保護した使い捨ての認証情報と限定された操作だけを受け付けます。修正後、別プロセスによるデバッグ接続と任意コマンドを拒否しつつ、試験購読の取得とファイル作成ができることを確認しました。別Windowsユーザーを使った実証は行っていません。

## 未実装・未検証

常駐ワーカーの再接続待機は、期限が過ぎたローカル記録を定期的に消去します。削除済み購読などが再接続されなくても期限切れ記録が残り続けず、期限前の待機やDB上の再試行期限は維持します。大量接続時の実負荷試験や長期間のメモリー使用量の測定は別途必要です。

- Chromium の端末確認は実装済みで、試験専用プロファイルを使いGoogleへの実接続を確認しました。次回間隔と確認時刻の引き継ぎ、認証拒否時に既存購読を保存したまま再登録待ちとする動作も隔離DBで試験済みです。数日以上の連続稼働による長期維持は未確認です。参照: https://github.com/chromium/chromium/blob/main/google_apis/gcm/engine/checkin_request.cc
- 試験用Chromeの再起動時には古いサーバー接続が表示上は接続中のまま通知を受け取れないケースを再現しました。専用ChromeのMCS受信接続先の制限と名前解決の制限を併用した後は、初回購読とファイル作成ができ、Chromeを開いたままサーバーで通知を受信し、ブラウザー側では受信しないことを試験サイトと実FCMで確認しました。二つ目の名前解決制限だけでも同じ試験を通過しています。同じファイルの再登録によって該当接続が再確立し、次の通知を受信・処理することも確認しています。接続情報の長期的な失効、長時間運用、および複数のChrome版での実機検証は残っています。
- 実際のX購読・通知・Discord配送。利用者の実アカウントや既存Chromeプロファイルは検証に使用していません。
- 本番移行前の承認、マイグレーション実施、支援者限定の設定と稼働確認。実行手順は `docs/operations/chrome-x-notifications.md` を参照してください。

`20261110` のChrome関連マイグレーションと未接続のEdge保存準備は、2026年11月11日に本番MySQLへ適用しました。隔離MySQLとMariaDBでは既存Firefoxデータを保持したまま繰り返し適用し、途中停止からの再開も検証しています。

## 試験

2026年11月11日に現行ブランチで再実行し、Chrome・BraveのMCS受信、所有者・lease、暗号文とACKの保存、再接続、移行、スナップショットを含む68件が成功した。登録画面・受付・既存監視の関連試験159件も成功した。DBを使う試験は `127.0.0.1:33621` の使い捨てMariaDBを使用し、スキップはなかった。これらは合成入力・模擬通信を含む自動テストであり、実際のX通知やDiscord配送、本番環境での確認ではない。

同日、Windows上の配布ZIP試験6件とFirefox従来ツールの試験55件が成功した。Chrome・Braveの専用プロフィール、パッケージ改変と既存出力の保護、日本語や記号を含むパスでの起動、Edge側のプロフィール分離と画面の基本表示、Firefox側の同意ダイアログを含む。Chromeの試験は固定済み `chrome-preview.7` ZIP、Edgeの試験は現行ソースから構築したZIPを使用した。通常のブラウザープロフィールや実際のX購読は使用していない。

受信確認の返答が遅れた場合の上限について、隔離MariaDBで未確認IDを100件まで保存し、101件目の通知とサービス制御通知が部分保存されず拒否されることを確認しました。既存IDの重複は処理でき、別ワーカーが100件を引き継いで確認後に次を保存できます。模擬サーバーを使いセッションとDBを組み合わせた試験でも、101件目に確認応答を送らずセッションを停止し、再接続で100件を確認した後、同じ101件目を処理できました。101件目の実FCMからの再送はこの試験では確認していません。

その後、Chrome・Braveそれぞれの使い捨て購読と実FCMで上限到達を再現しました。試験コードがローカルの確認記録の削除を意図的に遅らせて100件を蓄積し、次の通知を確認せず接続を閉じた後、再接続で未保存の通知を受信しました。保存した全通知を復号し、送信した各合成内容が重複なく揃っていることも確認しています。実サーバーの確認処理が実際に遅延した状況や、実X・Discordへの配送を再現したものではありません。

`scripts/test/chrome-mcs-*.test.js` と `scripts/test/chrome-x-transfer.test.js` はGoogleの通知サーバーに接続しない単体試験です。接続を伴う検証は `experiments/chrome-push/controlled-fixture.cjs` と `packaged-e2e.cjs` を使います。後者はWindows、Chrome、ビルド済み `packages/angelic-angel/dist`、使い捨てMariaDB、および試験用の `web-push`、`chrome-remote-interface` が必要です。試験用の新規プロファイルのみを作り、既存プロファイルにアクセスしません。

Linuxワーカーまで確認する場合は、名前が `cbte-chrome-compat-20261110` の使い捨てWSL環境に、依存関係とビルド済み `packages/angelic-angel/dist` を含む検証用コピーを `/tmp/cbte-linux-worker` に用意し、同環境のループバック `33621` に使い捨てMariaDBを起動します。`CHROME_FIXTURE_LINUX=1` と `CHROME_FIXTURE_LINUX_DB=1` を指定すると、`linux-worker-fixture.cjs` は試験用スキーマを作成し、終了時にそのスキーマを削除します。購読情報は試験用Chromeから標準入力で渡され、ログやコマンド引数には出しません。実ユーザーのプロファイルや本番DBを指定してはいけません。

固定済みWindows版プレビュー7と現行ソースを照合したところ、起動補助のChromeBroker.cjsが変わっていたため、同じ版番号を再利用せず、未公開プレビュー8を作成した。ZIPは35,928,371バイト、SHA-256は902a52e869b7071eceed76712f0d8cf172beb4d4b205bee0ecb32475dcf2cda0。固定済み版と候補版の両方について専用プロフィール、改変拒否、既存ファイルの保護、日本語を含むパスからのChrome・Brave起動を検証した。画面側は引き続きプレビュー7を参照し、新版は本番に公開していない。実X通知・Discord配送は未確認。

未公開Windowsプレビュー8で、専用Chromeを開き直したまま合成通知を送る試験を行った。実FCMからサーバー側の受信箱へ届き、設定用ブラウザーには5秒の観測中に届かなかった。設定ファイルを再作成・再登録した際には同じ購読を保持して接続を更新し、その後の合成通知も受信・ジョブ化できた。隔離DBの時刻を調整した試験であり、長時間の停止・実際のX投稿・実Discord配送の保証ではない。

Windowsプレビュー8由来の実FCM合成購読ファイルを、ブラウザーで表示した登録画面に渡し、ファイル選択・確認・登録と隔離DBへの暗号化保存を通した。ブラウザー画面やローカル保存領域に秘密鍵が表示されないこと、外部への画面リクエストと画面エラーがないこと、表示幅を超える横スクロールがないことも確認した。購読作成にはローカル試験サイトへの接続のため展開した候補の補助コードを試験用に変更しており、画面のダウンロードリンクは固定済みプレビュー7を使用した。実X・本番環境での確認ではない。

プレビュー9でも、使い捨てChromeプロフィールとローカルの合成サイトから作成したファイルを、隔離DBを使う登録画面で選択・確認・登録した。画面のダウンロードリンクは同じプレビュー9の固定ZIPを返し、暗号化保存、画面とローカル保存領域への秘密鍵非表示、外部画面リクエスト0件、画面エラー0件、表示幅の確認が成功した。Firefox・Chrome・Braveの画面を操作したが、実サイトや実ユーザーのアップロードではない。

MCSの受信キューは8件または128KiBで読み取りを一時停止し、最大1040件・448KiBに制限する。停止直前のキューに最大64KiBの部分フレームと最大256KiBの単一読み取りが続く境界を合成試験で確認した。上限超過時は接続を止め、保持できた完結済みフレームだけを認証・リース確認のうえで保存し、超過分の復旧を保証しない。キューのデータ部分だけでも、1000接続が同時に上限へ達すると約437.5MiB、設定上の最大10000接続では約4.27GiBとなり、フレームのオブジェクト、解析中のデータ、ソケット等はこれに加わる。これは理論上限であり、実際の常駐負荷や10000接続の運用可能性を示すものではない。

切断後の回復では、未確認IDが100件に達している場合も、ACKせずに受信済み暗号文を受信箱へ保存する。同じIDの異なる暗号文・ヘッダー、別利用者、失効したリースや権限を拒否し、後の再送は重複処理する。公式ハッシュを確認した一時MariaDB 11.4.10で、130件の回復、制御通知との衝突、DB障害、リース失効、再接続を含む30件のSQLテストが成功した。試験用DBプロセスは終了済み。実FCMの再送や、上記のキュー上限を超えたデータの復旧はこのSQL試験では保証しない。

合成端末で実サービスへのチェックインが走らないよう試験用応答を明示した再実行でも、Windowsの一時MariaDBで30件が成功した。Apple Siliconの使い捨てMacと一時MariaDBでも同じ30件が成功し、別の合成ファイルの保存・受付から通知ジョブまでの結合試験も成功した（Actions run 43173436578）。実X・Discordの配送や、障害後の長時間運用は含まない。

接続断後に回収できた通知は、所有中のリースと現在の契約設定を確認して、既存の処理間隔・リアルタイム条件に従う回復処理を起こす。停止・権限変更・リース交代時には処理の中断とDB内のフェンスを確認し、既にCOMMITへ進んだ場合もリース交代との直列化と重複排除を使う。一時MariaDBで既存の通知処理回帰を含む43件が成功した。既に送信したCOMMITを期限到達で必ず取り消せるわけではない。バッチ通知の期限が接続断の後に到来し、その後も再接続できない場合の処理は引き続き未保証。

Apple Siliconの一時MariaDBでも、回復のリース・中断・資格変更を含む42件のSQLテストが成功した（Actions run 43175851211）。同じ実行の実FCMを使う合成送信は初回410のため失敗であり、SQLの成功を実X通知の安定性として扱わない。

2026年11月12日のMac Chrome試験では、合成購読の初回送信に失敗した。実行 43180186237（b6a6aa3）の使い捨て MariaDB では SQL 55件と別の合成DB試験2件が成功したが、続く実FCM送信は購読直後に410を返した。同じ購読は約0.2秒・0.5秒後も410で、約1.3秒後に受理され、Service Workerに届いた。その後、合成ファイルの保存、暗号化した受信記録のDB保存、受信確認前のcommit、通知ジョブ1件を確認した。ただし初回の失敗を残し、run 全体は失敗として扱う。先行の成功 run 43178891032（6aeb086）では初回から受理され、同じ合成DB経路が成功した。両commit間でMac Chrome共通試験部品に加わった変更は診断文生成関数であり、受信処理の変更は確認されていない。初回410のGoogle側の原因は特定できず、再確認で受理されたことだけでは原因や実Xへの影響を断定できない。

別の run 43180186292（b6a6aa3）でも両CPUの初回合成送信が410となった。Apple Siliconでは約0.4秒後に同じ購読が受理された一方、Intelでは約5.6秒まで410が続き、その後の遅延確認で受理された。別に作成した合成購読も410となり、両環境とも後続の主受信試験は完了せず、失敗である。Apple Siliconの独立したプロフィール・署名関連の試験は30件成功した。Intelの同試験では2件が署名検証で失敗し、検証中のChrome Framework Currentの切替と、その後の厳格な署名検証の成功を観測した。更新との競合に整合するが、更新主体と失敗の完全な原因は未特定である。いずれも隔離ランナー、ローカルorigin、合成購読の結果で、実際のX通知やDiscordへの配送は検証していない。

Windowsの署名済みBrave 157.1.99.56と候補ZIP `chrome-setup-0.1.0-chrome-preview.9.zip`（SHA-256 `9276517742cebeb75a95b7ad4b535ff67ee050a858e280c9d84dd3a1059582e8`）で、専用の一時プロフィール、ローカルの合成サイト、使い捨てMariaDB 33623を使う結合試験が成功した。ZIP内の保存処理から合成設定ファイルを作成し、隔離DBへの登録、実FCMによる受信、通常runtimeでの通知ジョブ1件、模擬Discord DMの1件送信と重複なしを確認した。実Discordへのリクエストは0件。試験後はDBリスナーと、試験プロフィールを使うBrave・補助プロセスが停止していることを確認した。実Xや実Discordへの配送、実利用者による画面からのアップロード、および本番公開はこの試験に含まれない。

同じ候補9のWindows Chrome結合試験も、専用プロフィール、実FCM、隔離DBと模擬Discordを使う範囲で成功した。最初の試験は、合成のバッチ処理時刻を進める際に受信リースの期限も進んでしまい失敗した。使い捨てDBのバッチ基準時刻だけを調整するよう試験を修正してから再実行し、通知ジョブと模擬Discordへの配送を確認した。これは実Xや実Discordへの配送を確認した結果ではない。

多数の受信設定を扱う巡回では、設定変更、資格確認の再試行、通常の新規候補を一つの順番で交互に確認する。資格確認が失敗した場合は接続せず、上限のある補助リストに残し、既存の接続再試行と同じ指数バックオフで再確認する。照会回数も各巡回のページサイズ以内に制限し、まだ確認していない通常候補より先にcursorを進めない。資格を失った候補は次の通常走査でも再評価し、購読や枠を削除・移動しない。停止やguardianの権限失効が資格確認中または接続直前に起きた場合、新しい接続を開始しない。

一時MariaDBで、候補取得後の購読削除、所有者変更、支援資格失効を実gatewayに渡し、別利用者への接続が起きないことを確認した。資格の復帰後は既存購読と監視を維持したまま再接続できた。claim直前の資格失効では、既存のlease確認・資格確認を購読の初回復号前にも行い、vaultの呼び出しとsocket接続がいずれも0であることを別に確認した。これはDBで資格確認を終えた直後から同期復号までのより狭い競合を原子的に排除するものではない。既存Firefox・Chrome・Brave、ownerフェンスと復旧を含む隔離DB回帰50件、最終race試験4件、およびruntime・MCSの単体回帰82件が成功した。

一つのNodeプロセスで1000本のlocalhost TCP接続を段階的に作り、それぞれにMCS transport/sessionを使用する合成試験を行った。各接続の識別、受信とACKが混ざらないことを確認し、ある実行では約716ms、RSS増分約65MBだった。TLS、FCM、実DB、ブラウザー、長時間稼働は含まず、本番の接続容量や速度を示さない。受信直後の処理は定期巡回の並列上限を共有しておらず、定期drainが戻らない場合に候補巡回が止まり得る問題も未解決である。これらの制限と実DB・FCMを含む容量は、負荷測定と安全な処理待ち設計の検証が必要である。

通常ワーカーでは、候補の取得後にも、owner lock下で同じ利用者・購読に有効な監視が残ることを確認する。最後の監視が無効になった場合は接続を停止し、別の有効な監視が残る場合は受信を続ける。監視の設定や枠は変更せず、再有効化後は通常の候補走査で再接続する。guardianの許可も資格照会の前後、claim、初回の購読情報読み取り、各受信保存や認証送信の前に再確認する。同期guardianの判定はDB書込み後・commit前にも再確認し、期限切れclaimの遅いtransactionには中断signalを伝える。自分のleaseを停止・解放する操作は従来どおり残す。

最終コードを使う隔離MariaDBの76件が成功した。実際の監視更新APIによる最後の監視無効化、別の監視が残る場合、再有効化と通知設定・枠の維持、受信保存後の無効化によるACK抑止を含む。guardian失効は資格照会・claim後・HELLO応答待ち・INSERT中・commit後ACK前で確認し、Chromeのcheck-in拒否とFirefoxのUAID不一致は、有効な監視では既存の再登録要求を維持し、無効化や失権時には誤って再登録要求を残さないことを確認した。送信直前のguardian失効はFirefox・Chrome・Edgeの合成transportでも確認した。正常受信・再送・復旧を含む単体試験109件も成功し、実際のプロバイダーや本番DBには接続していない。

これらはDB確認と外部socket操作を原子的にするものではない。DB確認commit直後の監視変更・資格失効や、guardian確認直後の復号・送信との狭い競合、既に送信したDB commitやACKの結果は完全に取り消せない。新着payloadはguardianの同期確認後に復号するが、monitorやdonorのDB確認はその後の保存前であり、取消後に一時的な復号が起こり得る。この順序の変更は追加DB往復と大量接続時の負荷を含め未決定である。claim timeout後もサーバー側の長時間SQLとロックが直ちに解放される保証はない。これらを含む実DB高負荷・実FCMでの運用容量は未検証。
