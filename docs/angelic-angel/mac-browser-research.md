# Mac向けブラウザー通知の調査

MacでもFirefox・Chrome・Brave・Edge・Safariの利用者が設定用ファイルを作り、画面から自分でアップロードできることを目標とする。専用Chromiumは同梱しない。現在のWindows用ツールはWindowsのアクセス権、プロセス管理、DPAPI、Windows Formsを使うため、Macでそのまま動作するものではない。

2026年11月11日、[macOSの合成試験](https://github.com/lovetwice1012/comebacktwitterembed/actions/runs/42975177060)でApple SiliconとIntelの各16件が成功した。署名を確認したFirefoxと使い捨ての合成プロファイルを使用し、読み取り用プロセスへの標準入力、通知情報の照合、保存確認、ローカルファイル作成、終了確認と一時データの片付けを通している。アップロードは行っていない。

これは試験用の内部経路であり、利用者向けの画面や配布物には接続していない。`sandbox-exec` は非推奨で、試験したプロセス生成・ネットワークの制約やプロセスグループの終了確認は、同一ユーザーの全操作や分離した子孫に対する完全な安全性の証明ではない。実際のX通知、サーバー受信、署名済み配布物の動作は未検証であり、これらを確認するまでは有効化しない。

Chromeの試験用起動処理は、プロセスの `exit` から入出力が閉じる `close` まで専用プロフィールのロックを保持する。起動途中の失敗時も、起動したプロセスの終了を確認するまでロックを解放しない。[macOSの合成試験](https://github.com/lovetwice1012/comebacktwitterembed/actions/runs/42976233075)では、Apple SiliconとIntelそれぞれ12件が成功した。実際のLevelDBロックと合成プロファイルを使い、排他、スナップショット、片付けも確認している。ブラウザーの署名・起動とKeychainは模擬しており、実Chromeによる通知受信や分離した子孫の終了は確認していない。配布アプリへの接続は引き続き未完了。

追加の[macOS試験](https://github.com/lovetwice1012/comebacktwitterembed/actions/runs/42977024183)では、両CPUで実際のGoogle署名済みChromeを専用の使い捨てプロフィールで起動し、限定した匿名パイプでバージョンを取得して終了した。各13件が成功した。試験環境に最初から入っていたChromeの一部に付いたFinder情報が厳格な署名検証を妨げたため、使い捨てのGitHubランナー上だけで拡張属性を除去し、その後も署名と識別子を検証した。利用者の環境では属性の除去を行わない。ローカル試験ページへの起動であり、購読の作成、Keychain、通知受信、実X、配布アプリは検証していない。

さらに[試験用購読の作成と取得](https://github.com/lovetwice1012/comebacktwitterembed/actions/runs/42978559629)を実行した。Apple Siliconではローカル試験サイトでGoogleのPush購読を作り、ブラウザー再起動後に専用パイプ経由で同じ購読を取得できた。Intelでは直前のブラウザー起動試験は成功したが、その後の厳格な署名検証でChrome内部フレームワークの資源の整合性エラーが発生し、購読試験を開始できなかった。Chrome本体の署名者情報はGoogleだったが、エラー原因は未確定。検証を省略せず調査する。通知情報の抽出、Keychain、サーバーでの受信、実XとDiscordへの配送はこの試験に含まれない。

追加の[構成観測](https://github.com/lovetwice1012/comebacktwitterembed/actions/runs/42979287358)では、Intel環境のフレームワークに、正常な初回起動後から署名エラーまでの間に新バージョンのディレクトリが加わった。更新との競合を示唆するが、更新プロセスを特定したわけではない。署名検証中と起動前後にアプリ・実行ファイル・設定ファイルの識別情報が変わった場合は処理を中止するようにした。同試験ではApple Siliconの一時プロフィール削除が親プロセス終了後に競合する例も観測した。全子孫プロセスの終了確認は未解決であり、配布アプリに接続しない。

Chromeを専用プロセスグループで起動し、親の終了後もグループが残る場合や状態を確認できない場合はプロフィールのロックを保持する処理を追加した。[macOS試験](https://github.com/lovetwice1012/comebacktwitterembed/actions/runs/42980544506)では両CPUでそれぞれ15件が成功し、実Chromeによる試験用Push購読の作成・再取得も通過した。この試験で確認したのはプロセスグループの消滅までであり、グループを離れた子孫が存在しないことの証明ではない。更新競合が起きない保証もない。実X、Keychain、サーバー受信、配布アプリは未検証である。

[追加試験](https://github.com/lovetwice1012/comebacktwitterembed/actions/runs/42981690055)では、両CPUで実Chromeの試験用購読と隔離コピーした通知ストアの鍵が一致し、試験用Keychainの鍵による端末トークンの復号に成功した。無人ランナー上では通常のKeychain許可ダイアログに応答できないため、試験用のKeychainと既知の試験鍵をランナー内に作成している。利用者のKeychain、アクセス許可画面、実Xのデータを使った確認ではない。同じ実行のIntel側は別の起動試験で10秒のパイプ待ちに失敗したため、Macの待ち時間を30秒に調整した。[再試験](https://github.com/lovetwice1012/comebacktwitterembed/actions/runs/42982284729)ではApple Siliconが成功し、IntelはChromeの更新中とみられる署名検証エラーで停止した。Intelの全試験成功は未確認。

[実通知サーバーを使った追加試験](https://github.com/lovetwice1012/comebacktwitterembed/actions/runs/42983613388)では、Apple Siliconの使い捨てChromeで作成したローカル試験サイトの購読を使い、ブラウザー終了後にMCSセッションで試験通知を受信・復号した。試験用Keychainとインメモリーの受信記録を使っており、DB永続化、サーバーの常駐運用、実XやDiscord配送の証明ではない。別の実行ではMCSログイン失敗が発生しており原因は未確定。この実行でも別のChrome終了試験はプロセスグループ消滅を確認できず、Intelでは署名検証エラーで停止したため、全体として試験失敗である。

[後続試験](https://github.com/lovetwice1012/comebacktwitterembed/actions/runs/42984923388)では、受信試験を他の起動試験より先に実行し、Apple Silicon・Intelの両方で試験通知の初回ログイン、受信と復号、および残りのプロファイル・ロック試験が成功した。ログイン拒否時の端末確認と再試行を試験コードに用意したが、この実行では拒否されず、その経路は実行されていない。過去の断続的なログイン失敗とChrome更新時の署名エラーが解消したという証拠ではなく、DB永続化・利用者のKeychain同意・実X・Discord配送も未検証。

## 調査で確認した範囲

- FirefoxのMac版はプロファイルを `~/Library/Application Support/Firefox/Profiles/` 以下に置く。これは既定の一般プロファイルの場所であり、専用プロファイルの安全な作成・読み取りを証明するものではない。[Mozillaのプロファイル案内](https://support.mozilla.org/en-US/kb/profiles-where-firefox-stores-user-data)
- ChromiumのmacOS向け暗号処理にはKeychainとWindowsとは異なる暗号化実装がある。[Chromiumの実装](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/os_crypt/async/browser/keychain_key_provider.mm) は実装の一例であり、現行版のChrome・Braveの通知情報が必ず同じ経路を使うという証明ではない。実機で使い捨てプロファイルを作り、対象レコード・鍵の保護形式・更新時の挙動をそれぞれ確認する。
- Microsoftの組み込みWNSクライアントのポリシーはWindows向けで、macOSではサポート対象外とされている。[Microsoftのポリシー説明](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/forcebuiltinpushmessagingclient) からMac版Edgeがどの通知基盤を使うかは確定できない。WindowsのEdge処理をMacに流用せず、実機で別途調査する。
- SafariのWeb PushはAPNsとWebKitの `webpushd` を利用する。[WebKitの説明](https://webkit.org/blog/12945/meet-web-push/) と [AppleのWeb Push案内](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) は、サイト運営者が通知を送るための公開方式を説明している。これだけでは、既存Safari購読の受信権限を別サーバーへ安全に移せることは証明できない。AppleはSafariで不可視のPushをサポートせず、通知表示を求めているため、設定用ブラウザーの受信を止める方式との関係も確認する。

### Mac版Edgeの静的調査

Microsoftの[配布情報API](https://edgeupdates.microsoft.com/api/products?view=enterprise)に掲載されたMac版Edge 157.0.4341.46のインストーラーを、一時コンテナ内でSHA-256 `71c48e8f6b559c52744771606c8bce4c30e9fab71692c563fdfa69b2ef3c8d20` と照合した。取り出した公開バイナリーのフレームワーク（SHA-256 `c46c439714319fe6fab91ceacc82f3ad502a218b29f2f4be7b4de408a962fe97`）には、IntelとApple Siliconの両方でWNS接続先、組み込みWNSクライアント、Windows版で観測した通知ストア名、EdgeのSafe Storage名が含まれていた。文字列の存在は、実際にMac上でそのコードが選択されること、ストア形式、鍵の保護方式、サーバー側への移行が可能なことを証明しない。実機の使い捨てプロファイルで確かめるまで、Windows版の方式をMac版として有効化しない。

Mac向けに、Chromeとは別の専用Edgeプロファイルを作成・照合し、観測したストア名のLevelDBを1個だけロックする試験用処理を追加した。ロック中に通知ストアだけを一時コピーし、既存のEdge用リーダーで読み取った後に片付ける処理も接続した。Linuxの使い捨てLevelDBで、別ブラウザーのプロファイルを拒否し、ロック競合、購読情報の選択、不明な通知の検出、Cookie等の除外と一時コピーの削除を確認した。Mac版Edgeが実際にこのストアを使うこと、格納形式、通知の取得・受信は未確認であり、配布用の起動経路やサーバー受付には接続していない。

インストール済みEdgeの署名と専用プロファイルを検証し、既存の取得用ブローカーを起動する試験用部品を追加した。署名識別子とTeam IDは[Appleの公開ブラウザー情報](https://github.com/apple/password-manager-resources/blob/main/quirks/web-browser-extension-distribution-information.json)を参照した。停止済みプロファイル内の購読情報を確認し、Xの既存購読がある場合に受信抑制を指定する処理を接続した。プロファイルの排他ロックは確認からブラウザー終了まで保持し、起動失敗後も子プロセスの終了前には解放しない。Linuxの合成ストアと模擬ブラウザーで、初回・既存X・他サイトのみ、検査から起動までの競合、起動失敗時を検証した。Mac上の署名・受信・初回購読と異常終了時の復旧は未検証のため、この部品を配布ツールから呼び出さない。

接続メタデータを固定値で推測しないため、既存の隔離キャリブレーション処理をMacのブラウザー実行名とプロセス起動時刻に対応させた。[Appleのプロセス情報構造](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info.h)の秒・マイクロ秒を使い、起動元・所有者・実行ファイルを検査する小さなMac用補助プログラムも追加した。さらに、そのEdgeプロセスと子孫のPID・起動時刻・ローカルソケットの両端を照合する試験用部品を追加した。両CPU向けのクロスコンパイルと、OSの応答を模擬した正常・異常系を確認した。補助プログラムのハッシュ確認と署名済みEdgeの検証を経て、この確認を隔離キャリブレーションへ渡す内部経路も追加し、模擬OS応答で異常値・タイムアウトを拒否することを確認した。実際のmacOSでの権限、プロセス構成、ソケット情報の取得と競合時の安全性、署名、実通知は未検証。これらの検証が済むまで、この処理を有効化しない。

試験用接続に必要な短期証明書をメモリー内に生成し、システムの証明書ストアやディスクへ保存せずにキャリブレーションへ渡す処理を追加した。証明書とPKCS#12の生成には `node-forge` を使用する。ローカルTLSで証明書の名前・有効期限・信頼検証と、成功時・失敗時の受け渡しバッファーの消去を確認した。JavaScriptの文字列やライブラリー内部のコピーを確実に消去できるという保証はない。Mac実機のブラウザー接続は未検証。

Chromiumの現行公開ソースでは、[Macの鍵導出](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/os_crypt/async/browser/keychain_key_provider.mm)と[暗号処理](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/os_crypt/async/common/encryptor.cc)が `v10` のAES-CBC方式を実装し、[GCMストア](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/google_apis/gcm/engine/gcm_store_impl.cc)が端末トークンの暗号化を利用している。通知用トークンに限定した復号部品と隔離スナップショットの読み取りを接続し、Windows上の合成値と一時LevelDBで確認した。CBCには改ざん検出がなく、数字として復号できることだけでは鍵や出所の正しさを証明できない。親プロセスからパイプで呼ぶMac用読み取り入口も合成データで検証したが、配布ツール本体は未実装で、Keychain操作は実機未検証。親プロセス側には専用プロファイルの所有確認、停止、保護したスナップショットと出力、他サイト通知の説明・確認が必要。ブラウザーごとの識別子、Keychain権限、実プロファイルでの形式とサーバー受信は、使い捨てMac環境で検証する。

[ChromiumのKeychain実装](https://chromium.googlesource.com/chromium/src/+/HEAD/components/os_crypt/common/keychain_password_mac.mm)が指定するChrome用の固定項目について、利用者の確認後にMac標準 `security` コマンドで取得し、処理後に受け渡し用バッファーを消去する部品を追加した。シェルやコマンド引数に秘密値を渡さず、標準エラーを記録しない。Keychain・ユーザー操作を模擬したテストのみで、実Macでの権限ダイアログや配布ツールへの接続は未確認。この鍵は通常のChromeと共有され得るため、設定画面でアクセスの意味を明示し、専用プロファイルの通知トークン以外には使用しない。鍵自体は出力ファイルへ含めない。

[Chromiumのカテゴリ生成](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/browser/gcm/gcm_product_util.cc)は製品名とOS名を使い、[OS名の定義](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/base/version_info/version_info.h)はMacを `Mac OS X` とする。Chromiumの[設定名のコメント](https://github.com/chromium/chromium/blob/main/chrome/common/pref_names.h)もChromeのカテゴリ例として `com.chrome.macosx` を示す。ただし既存設定の値は維持されるため、実機で取得値を照合する。定期確認の[プロトコル定義](https://chromium.googlesource.com/chromium/chromium/+/trunk/google_apis/gcm/protocol/android_checkin.proto)はWindowsを1、Macを2と定める。Macの受付と受信側は独立した `X_NOTIFICATION_CHROME_MAC_ENABLED=1` と既存のChrome設定の両方が必要で、既定では無効。隔離MariaDBと合成通知では暗号化保存・所有者制限・Mac値での定期確認・受信を検証した。本番では有効化していない。現在のWindows用データは従来どおりWindows値を使う。

Mac版Edgeの試験用キャリブレーションは、署名確認済みアプリの `Info.plist` からバージョンを取得し、起動したEdgeの応答と照合するようにした。実行前後にも署名済みアプリのバージョンを確認し、更新・差し替えや不正な値があれば結果を返さない。Microsoftの[macOSアプリ情報の案内](https://learn.microsoft.com/en-us/intune/intune-service/apps/macos-unmanaged-pkg)では同項目がアプリバンドルの `Info.plist` に置かれるとしている。合成のOS応答で署名エラー・バージョン不一致・実行中の変更を検証したが、Mac版Edgeの実際の値や署名、プロセスとの結び付きは未検証。

Mac版Edgeの起動処理は、プロセスの `exit` だけでなく入出力が閉じる `close` まで専用プロフィールのロックを保持するよう修正した。起動失敗時も同様に待ち、確認できるまでは次の操作を開始しない。キャリブレーションでも起動した各プロセスの `close` を待ち、時間内に確認できなければ結果を返さない。模擬プロセスで `exit` と `close` の間の競合と終了待ちの失敗を検証した。ただし、親の `close` だけで分離した全子孫の終了を証明できるわけではなく、macOS実機のプロセス構成・完全な終了確認・一時領域削除は引き続き未検証。

Windowsの署名済みEdgeを、通常のプロフィールやXを使わない一時プロフィールで起動し、合成購読の接続を調べたところ、接続要求の `connect` バージョンは `2` だった。候補の解析処理を `1` と `2` に対応させ、取得値をキャリブレーション結果に残す。現在のサーバー側送信処理は `1` を生成するため、`2` を観測した場合に黙って `1` に変換して登録ファイルを作らないよう、Mac版の試験用出力を停止する。バージョン差が実際の互換性に与える影響や、Mac版Edgeの値は未検証である。試験はWindows Jobで起動した専用プロセスとローカル合成プロフィールだけを使用し、接続情報の値や鍵はログへ出さない。

Windows Edgeの専用合成プロフィールで観測したagent情報を使い、資格情報やX購読を送らずにWNSへ別々のTLS接続を作成して、接続要求 `CNT` のバージョン `1` と `2` を試した。今回の試験では両方とも最初の `CNT` 応答を受け付けた。これは認証前の一段階のみの結果であり、後続の認証、再接続、通知受信、Macのagent情報との互換性を証明しない。試験用プログラムは成功・失敗の識別子だけを記録し、agentの具体値や通知資格情報を出力しない。Mac版で `2` が観測された場合の安全な扱いは、引き続き確認する。

さらに、バージョン `1` と `2` のそれぞれについて別々の使い捨てWindows Edgeプロフィールを作り、そのプロフィールが発行した合成接続情報でWNSへの `CNT`、`ATH`、`BND` を実行した。どちらも認証と接続確立まで成功した。試験は接続情報を標準出力やログに出さず、通知の受信・送信は行わない。値の保持を試せるバージョン指定付き接続フレーム生成部品を追加したが、既存のサーバー受信処理・受付形式には接続していない。macOS由来の接続情報、切断後の再接続、通知受信とトークン更新の永続化はこの試験では確認していない。

使い捨てWindows Edgeプロフィールの合成接続情報を使い、`CNT` バージョン `1` と `2` のそれぞれで、WNSから返された更新後トークンを使う再接続に成功した。別途、既存の受信セッション実装（バージョン `1`）をそのまま使い、更新後トークンの保存コールバックを経て新しいセッションで再接続できることを2回確認した。保存先は試験用のメモリーであり、DB永続化やプロセス再起動を伴わない。X通知や実ユーザーの購読情報は使わず、通知の取得も行っていない。macOS由来の情報と実際の通知配送は未確認。
