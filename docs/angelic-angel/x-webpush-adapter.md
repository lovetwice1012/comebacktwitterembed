# X通知の公式形式と投稿リンクの確認

2026-10-14（日本時間）に、認証を使用せず [Xの公式Service Worker](https://x.com/sw.js) を読み取り、通知JSONの形式を確認した。ユーザーのFirefoxプロファイル・Cookie・購読情報は使用していない。

取得したソースは33777バイト、SHA-256は `240e739c25026bea9e3b616117ef073c5711e4685075975d43dfca414141a361`。Web配信の公開JavaScriptを読んだ証拠であり、実際のX Push受信を記録したものではない。

公式ソースは、Pushイベントの `data.json()` を `title`、`body`、`tag`、`icon`、`timestamp`、`data` の通知として読み取る。内部の `data` には `tweet_id`、`uri`、`user_id`、`type` などのフィールドを宣言している。従来の試験用 `notificationType`・`author`・`url` とは形式が異なるため、投稿リンク候補を検査する関数 `inspectXWebPushPostCandidate` を追加した。この検査関数は現在の配送経路から呼び出さない。

## 投稿リンク候補の確認条件

- `data.uri` が `https://x.com/{handle}/status/{id}` または同じ相対パスである。
- `data.tweet_id` がURI内の投稿IDと完全に一致する文字列である。
- 通知の形式と文字列サイズが検証を通る。
- DM、通話、X Chat、ログイン・アカウント・システムに分類された通知、表示しない通知（`silent:true`）は候補から除外する。

候補内の投稿者名はURIの `{handle}` を使う。`data.user_id` が投稿者IDを意味することは公開ソースから確認できていないため、これを投稿者として扱わない。今後この形式を配送へ接続する場合も、数字IDだけが登録されている監視に対し、このフィールドから投稿者を推測しない。

タイトルと本文は通知に付いている文字列を使う。通知のアイコンURL、その他のURL、認証情報にアクセスする処理は追加していない。`timestamp` は投稿時刻として使わない。リンクからアカウントの公開・非公開状態や通知の正確な種別を推測しない。

## 現在の確認範囲

公式ソースは `data.type` の具体的な投稿用列挙値を公開していない。いいね・返信などの通知にも投稿リンクを含められるため、リンクだけでは「新しい投稿の通知」を確定できない。候補の結果には配送用 `event` や `kind:new` を作らない。

配送経路の `normalizeXNotification` は既存の内部形式だけを採用する。公式形式の入力は、`data.type` が `tweet`、`new_tweet`、未設定であっても、確認済みの意味が揃うまで `X_NOTIFICATION_UNSUPPORTED` として扱う。受信した暗号文の保持・隔離は既存の処理に従う。

実購読の通知で正確な種別、URI、投稿者情報を確認し、その証拠に基づいたアダプターを配送へ接続することが、実利用開始に必要な受入項目となる。

`scripts/test/automation-x-webpush-adapter.test.js` は公式ソースの形式に沿った合成データで、投稿ID一致、投稿者を受信者IDから推測しないこと、私的な通知の除外、不正形式を検証する。未確認の種別や投稿リンク候補が、監視データ参照・キュー投入を行わないことも検証する。既存の内部形式の互換性テストも維持する。

支援者限定の登録・受信・配送認可、プラン間隔、枠、DB保存、送信制限は既存のサーバー検査を通す。今回の公式ソース確認と候補検査は、実X通知の到着や本番配送の証拠とは区別する。
