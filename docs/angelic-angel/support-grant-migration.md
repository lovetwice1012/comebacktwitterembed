# 支援者追加枠の台帳・移行手順

2026-10-14 JST。ローカルのdisposable MariaDBで検証済み。本番DBの読み取り・変更、移行実行、決済受付の有効化は行っていない。

## 保持する値

旧商品の500〜2500円という価格から枠数を計算しない。`users.additional_auto_extract_slots` の信頼できる既存付与数をそのまま使用する。旧Squareの `automation_square_donation_unit_grants.extra_slots` も記録済みの追加数を移行時点で保全する。同テーブルの `purchase_units` と `payment_count` は別の値であり、いずれも古い商品価格を500円で割った購入回数に読み替えない。

新しく検証された完了済みJPY決済は、1件ごとに `floor(amount / 500)` 枠を付与する。500円未満の複数決済を合算して新規枠に変換しない。付与数には有効期限・月額契約との結び付きを設けない。決済受付の停止や月額解約で台帳を削除しない。Squareの既存寄付APIが返す累積額・期限・返金後の口数は従来の計算を維持し、永久保有数とは分ける。

`getSupporterHolding` の `canonicalSquareSlots` は旧Square保全数＋未反映の確認済み過去付与＋新規永久付与であり、`users.additional_auto_extract_slots` を含まない。`totalSupporterSlots` はその合計に現在の手動付与カウンターを加える。新X登録の個人上限は現在プラン基本数＋この保有数を使う。通常通知の旧Square倍率・期限による従来枠数と二重に加算しない。

## 追加する台帳

|テーブル|用途|
|---|---|
|`automation_push_support_owner_snapshots`|初回移行時の手動付与数・支援者フラグの保全記録|
|`automation_push_support_scope_snapshots`|利用者・環境・merchantごとの旧Square付与数と既存口数／決済件数|
|`automation_push_support_legacy_attempts`|初回移行時点で既に検証されていた決済の識別。旧決済の再送を新価格制度で再付与しない|
|`automation_push_support_grants`|新決済・確認済み過去付与・明示的な手動カウンター変更の永続記録|

新決済の出所は環境・merchant・payment IDで一意にする。管理者の履歴登録は安定した `idempotencyKey` を使い、同一キーの同一操作は再付与せず、所有者・枠数・根拠が違う再利用は拒否する。独立した `automation_audit` の `x.support.grant` も同じトランザクションで保存する。監査には台帳ID・所有者・付与数・出所種別を記録し、カード情報・メール・生payment ID・merchant・要求本文を入れない。

## 移行境界

`migrateLegacyGrants(query, userId, { now, scope })` は呼び出し元の `withDatabaseTransaction` 内で利用する。利用者行をロックし、初回だけ旧値を保存する。既存設定・課金・通常通知の行を置き換えない。同じ利用者・環境・merchantで再実行しても保全数を再計算しない。

通常のGET・上限参照は移行を実行しない。未移行なら既存カウンターを読み取り専用で参照し、`migrationRequired` を返す。新たな決済の検証経路は既存のREST照合／署名検証済みWebhook処理に限定し、`applyObservation` が検証状態を更新する前に旧値を保全し、更新後に `applyVerifiedDonationGrant` を呼ぶ。

現在処理している未検証決済は移行分類から明示的に除外する。初回以前の未検証QUOTED行には付与の証拠がないため、他の新規見積もりと一緒に旧付与済み扱いにしない。未完了・不明な旧決済は運用者が切り替え時に一覧確認し、実際の購入記録を照合する。根拠が不明な付与数を推定しない。

本番での手順は次の順序とする。

1. 本番操作の許可を取得し、既存の手動カウンター・旧Square付与行・決済検証状態をバックアップする。
2. 既存の商品購入回数による付与数と、Square集計による付与数を確認する。値の出所や重複が不明ならその利用者の切り替えを停止する。
3. 決済観測処理の旧版／新版が同時に旧集計を書き換えない切り替え境界を用意する。受付停止中なら停止したままにする。
4. 対象利用者をトランザクション単位で `migrateLegacyGrants` に渡し、移行前後の手動数・旧Square保全数が同じであることを検証する。
5. 同一決済再送、旧2500円商品が新5枠へ変わらないこと、新500／1000／2500円決済が1／2／5枠になること、監査失敗時の全体ロールバックを確認する。
6. 新X提供の技術ゲート・有効化許可は別途確認する。台帳移行だけで受信・登録・決済を有効化しない。

支払いの環境・merchantは台帳の分離境界として保持する。設定が一時的に不完全でも、同じ環境・merchantが確認できれば既存永久数を参照できる。sandboxの試験記録をproductionへ混ぜない。merchantの変更を伴う運営移管では、旧記録を消さず、別途監査済みの継承方針を決める。

## 確認済み過去付与と手動変更

`recordHistoricalSupportGrant` は実管理者だけが使える。旧購入の金額ではなく、照合済みの正確な付与数と根拠を指定する。既存カウンターに含まれている購入の履歴だけを補う場合は `alreadyIncludedInLegacy: true` とし、記録は保存するが追加枠をもう一度足さない。未反映の購入を追加する場合だけfalseにする。

旧Discordの `additionalautoextractslot` はギルド・チャンネル・操作担当者・権限の条件を維持する。指定された枠数へ設定する挙動も維持する。実interaction IDから `discord:<id>` を作り、`explicitAdminAdjustment` と支援者フラグ更新を同じトランザクションで実行する。再送は付与・監査を増やさず、異なるinteractionによる変更は変更前後を残す。元の保全記録は上書きしない。

返金による永久枠の失効ルールは未指定である。検証された返金額を単調に記録し、履歴に `financialReviewRequired` を返す。初回観測ですでに返金されていても、その金融情報を隠さず記録する。永久付与数を自動的に取り消す処理は入れない。返金後の失効・再付与については、明示的な制度決定と監査可能な操作を用意してから適用する。

## 切り戻し

旧カウンター・旧Square記録・台帳・監査を削除しない。X受信／新規登録を止める場合も永久保有数の参照を残す。台帳を読めない旧版へ単純に戻すと新しい購入済み枠を表示・計数できなくなるため、その版を権利保持の切り戻し先として使わない。復旧時は保全記録と監査を照合し、同じ出所IDによる再実行で二重付与を防ぐ。
