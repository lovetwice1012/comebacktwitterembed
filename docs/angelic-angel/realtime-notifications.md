# X通知のタイミングを選ぶ

更新: 2026-10-14 JST。受信後、プランの確認間隔を待たずに通知する選択を追加する。

## 利用者と管理者の設定

利用者は「X通知のタイミング」で「プランの間隔でまとめて通知」または「リアルタイムで通知」を選び、保存する。本人の全X監視登録に共通の設定となる。初期設定はまとめて通知する方式。

管理者は既存の通知プラン管理にあるX用設定で、プランごとのリアルタイム通知を有効にできる。
判定には現在の有料契約と `automation_push_plan_policy.realtime_enabled` を使う。
プラン名・価格・優先順位・名前末尾の「＋」から資格を推測しない。
実際に提供するプランの指定は管理者の設定で行う。
新しい商品や課金処理は作成しない。

確認間隔・特殊枠数の未設定値は保持する。リアルタイムを有効にした対象者は、まとめて通知するための間隔が未設定でもリアルタイムを選べる。まとめて通知する方式は、間隔の設定を待って受信記録を保持する。既存の利用者別間隔と明示的な互換設定も保持する。

## 処理と資格変更

Push受信後の暗号化記録とCOMMIT後のACKは両方式で共通。リアルタイムでは受信時に処理を開始し、再起動で残った受信記録も回収する。まとめて通知する場合は現在の契約プランの確認間隔で処理する。

送信数上限、優先度、ルール、通知先認可、支援者限定の提供判定を引き続き適用する。リアルタイムの選択で登録上限や消費枠は変わらない。枠の自動移動も行わない。

契約変更や管理者による提供設定の変更時は、現在の資格を再検査する。リアルタイムの希望設定は保存し、対象外になった間は現在のプランのまとめ通知へ切り替わる。受信記録・購読・処理途中の位置を保持する。利用者は対象外になった後もまとめ通知へ戻せる。

## APIと移行

`GET /api/automation/x-processing-settings` は希望方式、実効方式、利用資格、プラン、確認間隔、設定待ちの理由を返す。
`PUT` は `{mode, expectedMode}` を受け付ける。
所有者行のロックと比較更新により競合を検知し、変更と監査ログを同一トランザクションで保存する。
資格のない新しいリアルタイム選択は403、競合は409。

`20261014_add_x_realtime_processing.sql` は次を追加する。

- `users.x_notification_processing_mode`（既定 `batch`）
- `automation_push_plan_policy.realtime_enabled`（既定0）
- `automation_x_push_receivers.process_window_mode`（NULL許可、既存処理窓はbatch扱い）

移行は既存の契約・登録・支援履歴を保持する。初回配備は公開受付を閉じた状態で新Bot・Dashboardを起動し、lease・revision・全シャードを確認してから支援者の受付を開く。受付を開いた後はXの個人枠を理解するリリースを保持する。Xに未対応の旧版は、通常登録の照合でXの個人枠を解放するおそれがあるため、追加表を残すだけで安全な切り戻しとは扱わない。

受付公開後に問題が起きた場合は、新規受付を閉じ、X対応のコード・暗号化受信記録・鍵・割当を保持して修復する。データの復旧が必要な場合はサービスを停止し、対象テーブルの検証済みバックアップから復旧する。稼働中に古いスナップショットを上書きしない。

## 検証の区別

設定API、DB競合・障害・ロールバック、受信処理、画面の自動試験を実施する。実X通知の形式と実配送は、利用者自身が行う登録・通知試験で別途確認する。合成通知の成功を実X通知の成功として扱わない。

ローカルの最終試験は61ファイル・824件が全件成功した。
結果とコミット済みソースのハッシュは `realtime-validation.json`、
試験原本は `realtime-acceptance-tests.xml` に記録する。
最初の一式は823件成功・1件失敗で、SQLの内容比較がWindowsのCRLFとLFを区別していたことが原因だった。
比較時の改行だけを揃え、実DDLのLF版・CRLF版と既存データ保持を単独8件で確認してから、一式を再実行した。
初回原本も `realtime-acceptance-initial-tests.xml` に保持する。
