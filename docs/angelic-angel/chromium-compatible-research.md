# Chromium 系ブラウザーの通知基盤

Windows上の使い捨てプロファイルとローカルの試験サイトだけを使用しました。利用者の通常プロファイルや実際のXアカウントは使用していません。

- Brave 157.1.99.55 は、専用プロファイルでGoogleのプッシュ通知サービスを有効にすると、FCMの購読を作成しました。登録カテゴリは `com.brave.windows` で、Google Chromeとは異なります。試験用購読の鍵と通知を使い、Brave終了後のMCS受信・復号、サーバー確認応答を検証しました。ブラウザー自身の版とChromiumエンジンの版は別の値です。
- Microsoft Edge 157.0.4341.42 は、試験用購読にWindows通知サービスのエンドポイントを使用しました。GoogleのMCS用ストアは確認できませんでした。Microsoftの[説明](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/forcebuiltinpushmessagingclient)でも、EdgeのWindows向けプッシュ受信はWindows通知サービスを使用しています。ChromeやBrave向けのファイルをEdge用として扱う実装はできません。

Edge の使い捨てプロファイルで、内蔵クライアントと通知サービス間の接続、試験通知の受信・応答、ブラウザー再起動後の再接続を確認しました。試験用プロファイル内の保存情報と再接続時の情報には対応関係がありましたが、再接続時の署名の生成方法、移譲後の更新・失効、サーバー側での受信と応答は未検証です。試験では一時的なローカル中継を使い、通常の Edge プロファイルや Windows の設定は変更していません。認証情報や通知内容は記録しません。

再接続の試験では、前回サーバーが返した値と今回の接続側の値を組み合わせた限定的な候補も、保存済みの試験用鍵で照合しましたが、観測した署名とは一致しませんでした。これは調べた候補についての否定結果であり、認証方式そのものを特定したものではありません。

追加試験では、上記の使い捨てプロファイルを Edge の終了後に同じ Windows ユーザー内の別ディレクトリへ複製しました。複製先の Edge は同じ試験用購読を認識し、再接続後に送信した試験通知を受信しました。これは Edge 本体と同じ端末・ユーザーが利用可能な条件での結果です。プロファイルから必要最小限の情報だけを取り出せること、別の端末や Linux ワーカーに移せること、サーバーが Edge の代わりに受信できることは確認していません。

以前の複製範囲を絞った試験には、後述の受信確認コードの不備がありました。修正後、機能や接続先を変更しない試験用ヘッドレス Edge でも、同じWindowsユーザー内では Service Worker と Push 保存領域だけの複製で同じ購読の合成通知を受信できました。保存領域全体を配布ファイルに含める設計ではありません。Service Worker にはサイトのデータが含まれ得るため、必要な情報の特定と選別が別途必要です。

ローカルの異なる2サイトで購読を作成した別の試験では、Edge 157 の内蔵プッシュ保存領域に各サイトの購読先・認証データ・公開鍵を含む別々の記録があり、それぞれの記録内の秘密鍵が該当する公開鍵に一致しました。照合には試験時に生成した鍵だけを使い、鍵や購読先は出力していません。この結果はサイト別選別の可能性を示しますが、実際のXや他の Edge バージョンでの形式、OS標準クライアントとの違い、安全な抽出方法を保証するものではありません。

2サイトの試験記録では、サイト識別子は記録の直下ではなく、名前と値の組として格納されていました。試験では識別子を完全一致で照合し、各サイトにつき1記録だけが対応すること、通知先・認証データ・送信側公開鍵と受信側秘密鍵がその購読と一致することを確認しています。部分文字列が偶然含まれるだけの記録を採用する実装は行っていません。

この結果を受け、ローカルの合成サイトに限った調査用セレクターを追加しました。サイト識別子の完全一致、重複、鍵の形式、通知先の形式を確認し、不正な対象記録は拒否します。実際に試験用 Edge が作成した2サイトの記録でも照合できました。このセレクターは `localhost` と `127.0.0.1` の試験用購読しか受け付けず、実際の X や通常の利用者プロファイルを抽出する機能ではありません。

同じ試験では、2サイトそれぞれの合成購読向けに作成した `aes128gcm` 通知を、該当する保存記録の鍵と既存の Node.js 復号処理で復号できました。もう一方のサイトの記録では復号できないことも確認しました。暗号文はローカルで生成したものであり、サーバー側で WNS の接続や通知受信に成功したことを意味しません。

さらに、試験用の通知を実際に WNS へ送り、Edge がローカル中継経由で受信した暗号文をメモリ内で照合し、Edge 終了後に試験用の保存記録から取り出した鍵と既存の Node.js 処理で復号できました。鍵・暗号文・本文は記録せず、成否だけを出力しています。保存記録の別フィールドには購読者の公開鍵ではなく試験サイトの送信用公開鍵が含まれるため、両者を取り違えない検証が必要です。この接続は Edge の内蔵クライアントが行ったもので、Node.js ワーカーからの接続、実際の X 通知、別端末での移譲を証明するものではありません。

この受信データは、事前に暗号文を知っていることに依存せず、試験用に実装した長さ・ヘッダーの読み取りから取り出して復号できました。通信を任意の位置で分割した場合や、途中で切れたデータ・大きすぎるデータ・重複ヘッダーも試験しています。この読み取りコードは調査専用であり、WNS の完全な仕様や不正な通信に対する本番向けの実装としては検証していません。

別の試験では、Edge が開始した接続をローカル中継で保持し、試験用 Edge の終了後に送信した2件目の通知を同じ接続で受信・復号できました。中継側から受信確認は送っていません。この方法は、すでに存在する接続を一時的に保持したもので、Windows 上の接続をサーバーへ移したり、Node.js が新たに認証して再接続したりする方法ではありません。

受信確認については、試験用の同じ接続で Edge が送った確認の項目を観察し、Edge 終了後に中継側が合成通知に対する確認を書き込むケースと、書き込まないケースを比較しました。どちらも後続通知は到着しました。接続を切って試験用 Edge を再起動した後、未確認の通知は10秒の観測中には再配信されず、新たに送った通知は届きました。各ケース2回の限定的な観測であり、WNS が再送しないと一般化することも、試験用の確認が受理されたと判断することもできません。少なくとも受信確認の不送信だけで通知が再送されると仮定した実装は採用できず、受信データの永続化と障害時の取り扱いを別途検証する必要があります。

この内蔵クライアントの観測を、一般的な Windows の動作と同一視しないでください。中継を使った上記の試験では `msPushWinrt` を明示的に無効化していました。Microsoft の上記ポリシー説明では、既定は Windows OS のクライアントで、内蔵クライアントを使う設定もあります。

追加試験では、使い捨てのヘッドレス Edge プロファイルで `msPushWinrt` の無効化と通知接続先の変更をどちらも指定せず、WNSの購読と合成通知の受信を確認しました。この環境でも専用プロファイル内に `EdgePushStorageWithConnectTokenAndKey` が作成されました。続いて、同じWindowsユーザー内で Local State・Preferences・Service Worker・Push 保存領域を複製したプロファイルは同じ購読を認識し、合成通知を受信しました。Push 保存領域を省いた対照では同じ購読を復元できませんでした。各条件の限定試験であり、OS側クライアントの利用有無、通常の画面操作、別端末への移譲や更新・失効は証明していません。

この再試験の準備中、複製後の試験通知を受信確認に数えない試験コード上の不備を発見し、修正しました。上記の複製後の受信結果は修正後に再確認したものです。通知種類と試験側の受信確認先が対応することを自動テストに追加しています。

接続先だけを試験用ローカル中継に変えた対照試験では、元の試験用 Push 保存領域を複製した場合に同じ購読で再受信できました。別の使い捨てプロファイルで、接続情報の保存記録内にある32バイトの鍵相当値だけを別の合成値に置き換えてから複製すると、同じ購読は復元されず、再接続時には元のトークンが送られました。通常のEdgeプロファイルや実際のXは触っていません。各1回の観測であり、変更値が署名鍵であることやWNS側がどの理由で接続を拒否したかはまだ確定できません。保存値、トークン、署名、通知内容は出力していません。

この対照を別の使い捨てプロファイルで再実行し、受信した完全な接続フレームの種類だけを照合しました。変更なしでは再接続時に `BND` 応答が観測され、合成通知も届きました。鍵相当値を変更した場合は、同じ購読を復元できず、観測範囲内に `BND` 応答がありませんでした。これは一対の限定的な結果で、応答がなかった理由やタイムアウト後の挙動を示しません。解析器は合成試験専用で、接続先に渡せる認証情報を作成するものではありません。

追加調査では、試験用の接続情報から計算した再接続署名が、別々に作成した3件の試験用プロファイルで Edge の署名と一致しました。さらに、ローカル中継で乱数と署名を同時に作り直したところ、WNSから応答があり、その接続で合成通知を受信できました。

続いて Edge を終了した後、Node.js 自身が WNS に新しいTLS接続を開き、再接続署名と接続ごとの購読確認応答を作成しました。別々の試験用プロファイル3件で、WNSから暗号化された合成通知を受信し、送信した暗号文との一致と復号を確認しています。接続の雛形は試験用Edgeの通信をメモリー内で取得し、購読確認に必要な製品固有値もインストール済みEdgeの一致確認済みバイナリから試験中にだけ読みました。いずれも出力・保存・配布していません。

この結果は移譲ファイルだけで接続できることを示すものではありません。本番向けメッセージ生成、製品固有値の扱い、サイト別情報の安全な抽出、保存情報の更新・失効、受信確認と障害時の再送、Linux・実Xでの動作は未検証です。調査コードは本番ワーカーに接続しておらず、Edge向けの受付も有効化していません。購読確認候補の検討には、[Pidginの公開実装](https://lists.pidgin.im/commits/2008-June/009003.html)を参照しました。

さらに、別々に作成した3つの試験用プロファイルで、接続に必要な識別子とプロトコル版が一致することを値を出力せずに確認しました。その2項目を使い、4件目の試験用プロファイルでは通信雛形を使わず全メッセージを Node.js で生成して合成通知を受信・復号できました。クライアント名と版は試験用の別値です。一方、識別子やプロトコル版を仮値にすると拒否されたため、固定値を推測して本番コードに組み込むことはできません。比較は同一Windows端末・同一Edge版に限られ、他端末や更新後との互換性、製品固有値の安全な扱いは未検証です。

追加の合成試験では、Node.jsが受信・復号した通知に確認応答を送った後、同じ接続で次の通知も受信・復号できました。確認応答の書き込みと後続通知の到着は確認しましたが、WNSが確認を永続化したことや障害時に再送することは証明していません。本番向けには、暗号文の耐久保存と受信確認の順序を別途実装・検証する必要があります。

また、接続応答で返る再接続トークンは、試験では元の値と異なっていました。更新値をメモリー内で引き継ぐと、Node.jsが再度接続して別の合成通知を受信・復号できました。別の1回の対照試験では、更新前の値でも直後の再接続が成功しました。旧値の有効期間や更新失敗後の挙動は分からないため、これを長期的な保証として扱ってはいけません。更新値の安全な永続化と複数ワーカー間の整合性は未実装です。

切断と再配信の追加試験では、試験用Edgeの中継接続とNode.jsの接続が閉じた後に、有効期限60秒の合成通知を送信し、更新トークンで再接続しました。新たな通知を送る前の10秒間に、切断中に送った通知は5回とも観測されました。一方、切断直前に受信した通知は、確認応答を送らない3回・確認応答を書き込んだ2回のどちらでも、その10秒間に再配信されませんでした。これは短時間・各1件の合成試験で、遅延後の再送や実際のXの配信条件を一般化できません。受信してから耐久保存するまでにプロセスが停止した場合、確認応答の有無だけに依存して復旧できるとは判断できず、Edge公開前の未解決事項です。[MicrosoftのWNS説明](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/push-notifications/push-request-response-headers)ではraw通知のオフライン時の扱いが送信側の設定に依存しますが、その説明だけでXのWeb Push設定を推測することはできません。

保存後の障害については、ローカルサイト専用の調査アダプターで既存の所有者・lease付き受信箱を使用し、対象外の合成通知を保存せず、対象通知の暗号文を確認応答より前に保存する経路を試しました。実WNSから受信した対象通知を保存直後に意図的に中断し、実時間で30秒のlease期限を待ってから後継のleaseで復号・既存キューへ投入し、受信行と通知ジョブが各1件であることを確認しました。所有権の試験には既存形式のダミー受信設定を使い、復号には試験用Edgeの鍵を使用しています。別の実WNS試験ではSQL挿入を失敗させ、対象通知の復号・確認応答を行わず挿入がロールバックされることも確認しました。DB障害・lease期限切れ・重複IDの衝突・他ユーザー拒否のSQL試験も成功しています。これらは調査用アダプターであり、実X、実Discord、本番WNSワーカーの実装を示しません。また、保存前に停止した通知をWNSが再送する保証は依然ありません。

さらに、実WNSの合成通知を受信する試験用Node.jsプロセスを、暗号文のDBコミット直後かつ対象通知の確認応答前に強制終了しました。別のNode.jsプロセスが実時間で30秒のlease期限を待って取得し、保存済み通知を復号して既存キューに1件のジョブを作ることを、異なるプロセスIDを確認して2回検証しています。対象外サイトの通知はDBに保存されず、古いleaseも拒否されました。後継プロセスの起動は試験側が行っており、自動監督やWNSへの再接続、更新トークンの耐久保存、実X・Discordを証明するものではありません。

更新トークンの耐久保存は、使い捨てスキーマだけの調査用テーブルと試験鍵で試作しました。トークンをハイブリッド暗号で保管し、所有者・受信設定の版・更新番号に結び付け、leaseと更新番号をトランザクション内で検証します。実WNSの合成試験では、先行プロセスが更新トークンと通知暗号文を保存した後に強制終了し、30秒のlease期限を経て別プロセスがトークンを復号してWNSへ再接続、保存済み通知と新着通知を各1ジョブにできました。対象外サイトの通知は保存されませんでした。別々の試験用プロファイルで2回確認しています。SQL競合、期限切れ、更新失敗時のロールバック、暗号文と更新番号の改ざん、読み取り失敗時の秘密値消去も試験しています。

さらに、調査用テーブルの代わりに通常ワーカー用の暗号化保管処理と受信設定行を使い、使い捨てMySQL・試験鍵・実WNSで同じ強制終了と引き継ぎを確認しました。後継プロセスは更新トークンを復号して再接続し、次の更新を世代2として保存し、通知2件を各1ジョブにしました。対象外サイトの通知は保存されませんでした。最初の試験は、後継側の検証コードが旧調査用テーブルを参照したため失敗し、参照先を修正して再実行しています。この試験も実利用者データや本番DBは使っていません。

追加で、既存ワーカーのRSA鍵を使い、受信設定行に暗号化した更新トークンを保存する未接続の基盤を実装しました。所有者・設定の版・更新番号を暗号で結び付け、DB内のleaseと更新番号を検証します。保存用のNULL許容列はChrome公開時の2026年11月11日に本番へ追加しましたが、Edgeの登録画面や受信処理にはまだ接続していません。試験では専用DBで競合、更新失敗、lease期限切れ、鍵の切り替え、既存Firefoxデータの維持を確認しました。後継プロセスの起動は試験側が行っており、自動監督、実X、Linux、保存前停止時の再送は未検証です。購読確認に必要な製品固有値の運用方法も未確定です。

新しい列を撤回する場合は、Edge受信を有効化していないことを確認し、事前にバックアップした上で `wns_token_sealed_json`、`wns_token_revision`、`wns_token_generation` の3列のみを削除します。保存したEdge接続情報は失われます。Firefox・Chromeの既存受信データは対象外です。この手順は本番で実行していません。

別のローカル2サイト試験では、1つの試験用 Edge プロファイルと1本のWNS接続で各サイトに合成通知を2件ずつ送りました。各通知の `Channel` ヘッダーはそれぞれのサイトの試験用保存記録のフィールド1と完全一致し、サイト間で異なり、同じサイトの2件では一致しました。対象サイトの記録とヘッダーを復号前に比較し、一致した通知だけを復号、もう一方の復号処理を呼ばないことを2つの使い捨てプロファイルで確認しています。境界・重複・不正なヘッダーの自動テストも追加しました。これはローカル中継と合成通知による限定試験であり、実際のX、他のEdge版、Node.jsワーカーの本番ルーティングや破棄・ACK処理を証明しません。

その後、2サイトを登録した使い捨てプロファイルから Node.js がWNSに直接再接続する試験も行いました。対象外サイトの合成通知を先に受信し、`Channel` の不一致で復号せず、確認応答を書き込んだ後、対象サイトの通知を受信・復号できました。接続メッセージを Node.js で生成したケースを含む別々の試験用プロファイル2件で確認しています。WNSが対象外通知の確認を永続化したこと、本番ワーカーによる安全な廃棄、実X通知は未検証です。

追加実装したフレーム分割・サイト判定処理を、2サイトの使い捨てプロファイルと実WNSで再確認しました。ブラウザー経由の試験で観測した通知先頭行は5項目でしたが、Node.jsの直接接続では4項目の形式も観測しました。旧調査コードは4項目の最後にある長さをチャンネル識別子と誤認して確認応答を組み立てていたため、以前の「書き込み成功」は正しい形式の確認やサーバー受理を示しません。両形式を区別して組み立てた候補を書き込んだ後の通知受信、および保存後のプロセス強制終了・別プロセスへの引き継ぎは合成データで確認しました。候補の確認応答をWNSが永続的に受理したこと、受信直後・DB保存前の停止時に通知が再配信されることは引き続き未確認です。Edgeの受付にはまだ接続していません。

受信処理の部品では、対象外サイトは暗号文を保存せず、対象の暗号文は所有者・lease・公開範囲を確認して保存後に候補の確認応答を送ります。重複IDの内容不一致、DB障害、権限失効、同時呼び出し時は応答を送らずセッションを停止します。隔離MySQLと合成通知による回帰試験、および実WNS・使い捨てプロファイルで保存直後にプロセスを強制終了し、別プロセスが保存済みデータと更新トークンを引き継ぐ試験を実施しました。受信部品はまだ通常ワーカーに接続しておらず、保存前停止時の欠落やWNSによる候補応答の受理を解決したことにはなりません。

固定されたWNS接続先にTLS証明書を検証して接続する通信部品も追加しました。受信キューを制限し、異常なフレームや同時操作では接続を閉じ、受信待ちの時間切れでは途中のデータを保持します。合成試験と実WNSへの試験接続で確認しましたが、通常ワーカーへの組み込みや大量接続・長時間維持は未検証です。

これらを接続・認証・通知受信の一つのセッションとしてつなぎ、更新トークンの保存コールバックが成功してから認証を進める処理を追加しました。使い捨てEdgeの2プロファイルと実WNSで、通常ワーカー用の暗号化保管処理と隔離MySQLを使い、接続、対象外サイトの破棄、対象通知の保存・復号、leaseを引き継いだ後のトークン復元を確認しています。このセッションはまだ通常ワーカーへ接続しておらず、自動再接続・実X・Discord配送を確認したものではありません。

さらに、leaseと公開資格を送信前にも検証する受信ゲートウェイ部品を追加し、実WNS・隔離MySQL・使い捨てEdgeの2プロファイルで、更新トークンの暗号化保存、対象外サイトの破棄、対象通知の保存、後継leaseでのトークン復元を確認しました。leaseの更新と停止指示は呼び出し元の責任です。通常ワーカーの起動・監視・自動再接続や実利用者データへの接続はまだ行っていません。

同じゲートウェイ部品を使い、暗号文の保存直後・確認応答前に試験用プロセスを強制終了する実WNS試験も実施しました。別プロセスが実時間のlease期限後に更新トークンを復元して再接続し、保存済み通知と新着通知をそれぞれ1件のジョブにできました。対象外サイトの通知は保存されていません。後継プロセスの起動は試験側が行っており、自動監督や保存前停止時の再送を証明するものではありません。

再接続署名・チャレンジ応答と接続メッセージ生成を独立した処理に分け、合成値の既知ベクトル、異常入力、実WNSへの試験接続で検証しました。接続用のクライアント情報は呼び出し元から明示的に受け取り、試験値を製品用の既定値として扱いません。再接続応答の解析も、要求番号と長さを照合し、重複要素・不正な構造・外部参照を拒否する方式に変更して、合成応答と実WNSの試験応答で確認しています。製品固有の識別子や鍵はこの処理に埋め込んでおらず、安全な取得・運用方法は引き続き未確定です。

4項目形式の候補確認応答を使って再接続を試験したところ、確認応答を書いた場合と書かなかった場合の各1回で、切断中に送った通知は再接続後に届きました。すでに受け取った通知は、どちらも再接続後10秒間には再配信されませんでした。これは限定観測で、確認応答の受理や、より長い期間を含む再送仕様の証明ではありません。

Xの購読候補を選ぶ独立した解析処理を追加し、対象のスコープ・エンドポイント・公開鍵・認証情報・送信側公開鍵をブラウザーで確認した値と照合する合成テストを追加しました。重複や不正な鍵は拒否し、別サイトの記録は出力しません。使い捨てEdgeが生成した2サイトの購読について、対象レコードのスコープだけをメモリー内でXに置き換え、ブラウザーから得た鍵・通知先との一致を2プロファイルで確認しました。置換したレコードはファイルへ保存していません。この解析処理はまだ配布ツールや登録画面へ接続しておらず、実際のX購読形式は未検証です。

以前の中継試験では、試験用Edgeに証明書エラーを広く無視する指定を使っていました。追加試験では、毎回作る中継用証明書の公開鍵だけを指定する方式に変更し、実WNSの合成通知を受信できる一方、別の自己署名証明書によるHTTPS接続が拒否されることを複数プロファイルで確認しました。同じ限定許可を使い、DB保存後の強制終了・別プロセスの再接続と、合成通知2件が2件のジョブになることも確認しています。これは使い捨てプロファイルと合成サイトによる検証であり、配布ツールへの実装や、他プロセスから中継鍵を保護できることを示すものではありません。[Chromiumの証明書指定に関する説明](https://chromium.googlesource.com/website/+/refs/heads/main/site/quic/playing-with-quic/index.md)

Windows の一般的な通知チャネルはアプリ・利用者・端末にひも付き、有効期限や更新があります（[Microsoft のチャネル説明](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/push-notifications/request-create-save-notification-channel)）。この説明だけから Edge の Web Push 購読に同じ有効期限が適用されるとは断定できませんが、ファイルを一度移すだけで長期運用できると決めつけず、実際の更新と失効も確認する必要があります。

Windows の公開APIでチャネルを作成する方法についても確認しました。[Microsoft の API 説明](https://learn.microsoft.com/en-us/uwp/api/windows.networking.pushnotifications.pushnotificationchannelmanager.createpushnotificationchannelforapplicationasync)では、呼び出し元アプリに結び付くチャネルを作り、別のアプリIDを指定する場合も同じパッケージ内のアプリに限定されます。そのため、別のセットアップツールがこの公開APIを呼ぶだけで、既存の Edge の購読をサーバーへ引き継げる根拠にはなりません。これは API の適用範囲に関する判断であり、Edge の内部接続や別の正式な拡張経路が存在しないことを示すものではありません。

Brave向けのGoogle通知設定はツール専用の新規プロファイルに限定し、利用者の通常プロファイルは読み書きしません。Edgeの直接受信と、その他のChromium系ブラウザーは未対応・調査中です。ブラウザーの系統だけで接続方式を推測せず、実際の通知基盤と鍵の形式を確認してから対応します。
