# Chromium 系ブラウザーの通知基盤

Windows上の使い捨てプロファイルとローカルの試験サイトだけを使用しました。利用者の通常プロファイルや実際のXアカウントは使用していません。

- Brave 157.1.99.55 は、専用プロファイルでGoogleのプッシュ通知サービスを有効にすると、FCMの購読を作成しました。登録カテゴリは `com.brave.windows` で、Google Chromeとは異なります。試験用購読の鍵と通知を使い、Brave終了後のMCS受信・復号、サーバー確認応答を検証しました。ブラウザー自身の版とChromiumエンジンの版は別の値です。
- Microsoft Edge 157.0.4341.42 は、試験用購読にWindows通知サービスのエンドポイントを使用しました。GoogleのMCS用ストアは確認できませんでした。Microsoftの[説明](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/forcebuiltinpushmessagingclient)でも、EdgeのWindows向けプッシュ受信はWindows通知サービスを使用しています。ChromeやBrave向けのファイルをEdge用として扱う実装はできません。

Edge の使い捨てプロファイルで、内蔵クライアントと通知サービス間の接続、試験通知の受信・応答、ブラウザー再起動後の再接続を確認しました。試験用プロファイル内の保存情報と再接続時の情報には対応関係がありましたが、再接続時の署名の生成方法、移譲後の更新・失効、サーバー側での受信と応答は未検証です。試験では一時的なローカル中継を使い、通常の Edge プロファイルや Windows の設定は変更していません。認証情報や通知内容は記録しません。

再接続の試験では、前回サーバーが返した値と今回の接続側の値を組み合わせた限定的な候補も、保存済みの試験用鍵で照合しましたが、観測した署名とは一致しませんでした。これは調べた候補についての否定結果であり、認証方式そのものを特定したものではありません。

追加試験では、上記の使い捨てプロファイルを Edge の終了後に同じ Windows ユーザー内の別ディレクトリへ複製しました。複製先の Edge は同じ試験用購読を認識し、再接続後に送信した試験通知を受信しました。これは Edge 本体と同じ端末・ユーザーが利用可能な条件での結果です。プロファイルから必要最小限の情報だけを取り出せること、別の端末や Linux ワーカーに移せること、サーバーが Edge の代わりに受信できることは確認していません。

以前の複製範囲を絞った試験には、後述の受信確認コードの不備がありました。修正後、機能や接続先を変更しない試験用ヘッドレス Edge でも、同じWindowsユーザー内では Service Worker と Push 保存領域だけの複製で同じ購読の合成通知を受信できました。保存領域全体を配布ファイルに含める設計ではありません。Service Worker にはサイトのデータが含まれ得るため、必要な情報の特定と選別が別途必要です。

ローカルの異なる2サイトで購読を作成した別の試験では、Edge 157 の内蔵プッシュ保存領域に各サイトの購読先・認証データ・公開鍵を含む別々の記録があり、それぞれの記録内の秘密鍵が該当する公開鍵に一致しました。照合には試験時に生成した鍵だけを使い、鍵や購読先は出力していません。この結果はサイト別選別の可能性を示しますが、実際のXや他の Edge バージョンでの形式、OS標準クライアントとの違い、安全な抽出方法を保証するものではありません。

2サイトの試験記録では、サイト識別子は記録の直下ではなく、名前と値の組として格納されていました。試験では識別子を完全一致で照合し、各サイトにつき1記録だけが対応すること、通知先・認証データ・送信側公開鍵と受信側秘密鍵がその購読と一致することを確認しています。部分文字列が偶然含まれるだけの記録を採用する実装は行っていません。

この結果を受け、ローカルの合成サイトに限った調査用セレクターを追加しました。サイト識別子の完全一致、重複、鍵の形式、通知先の形式を確認し、不正な対象記録は拒否します。実際に試験用 Edge が作成した2サイトの記録でも照合できました。このセレクターは `localhost` と `127.0.0.1` の試験用購読しか受け付けず、実際の X や通常の利用者プロファイルを抽出する機能ではありません。

同じ試験では、2サイトそれぞれの合成購読向けに作成した `aes128gcm` 通知を、該当する保存記録の鍵と既存の Node.js 復号処理で復号できました。もう一方のサイトの記録では復号できないことも確認しました。暗号文はローカルで生成したものであり、サーバー側で WNS の接続や通知受信に成功したことを意味しません。

さらに、試験用の通知を実際に WNS へ送り、Edge がローカル中継経由で受信した暗号文をメモリ内で照合し、Edge 終了後に試験用の保存記録から取り出した鍵と既存の Node.js 処理で復号できました。鍵・暗号文・本文は記録せず、成否だけを出力しています。保存記録の別フィールドには購読者の公開鍵ではなく試験サイトの送信用公開鍵が含まれるため、両者を取り違えない検証が必要です。この接続は Edge の内蔵クライアントが行ったもので、Node.js ワーカーからの接続、実際の X 通知、別端末での移譲を証明するものではありません。

この受信データは、事前に暗号文を知っていることに依存せず、試験用に実装した長さ・ヘッダーの読み取りから取り出して復号できました。通信を任意の位置で分割した場合や、途中で切れたデータ・大きすぎるデータ・重複ヘッダーも試験しています。この読み取りコードは調査専用であり、WNS の完全な仕様や不正な通信に対する本番向けの実装としては検証していません。

別の試験では、Edge が開始した接続をローカル中継で保持し、試験用 Edge の終了後に送信した2件目の通知を同じ接続で受信・復号できました。中継側から受信確認は送っていません。この方法は、すでに存在する接続を一時的に保持したもので、Windows 上の接続をサーバーへ移したり、Node.js が新たに認証して再接続したりする方法ではありません。

受信確認については、試験用の同じ接続で Edge が送った確認の項目を観察し、Edge 終了後に中継側が合成通知に対する確認を書き込むケースと、書き込まないケースを比較しました。どちらも後続通知は到着しました。接続を切って試験用 Edge を再起動した後、未確認の通知は10秒の観測中には再配信されず、新たに送った通知は届きました。各ケース2回の限定的な観測であり、WNS が再送しないと一般化することも、試験用の確認が受理されたと判断することもできません。少なくとも受信確認の不送信だけで通知が再送されると仮定した実装は採用できず、受信データの永続化と障害時の取り扱いを別途検証する必要があります。

この内蔵クライアントの観測を、一般的な Windows の動作と同一視しないでください。中継を使った上記の試験では `msPushWinrt` を明示的に無効化していました。Microsoft の上記ポリシー説明では、既定は Windows OS のクライアントで、内蔵クライアントを使う設定もあります。

追加試験では、使い捨てのヘッドレス Edge プロファイルで `msPushWinrt` の無効化と通知接続先の変更をどちらも指定せず、WNSの購読と合成通知の受信を確認しました。この環境でも専用プロファイル内に `EdgePushStorageWithConnectTokenAndKey` が作成されました。続いて、同じWindowsユーザー内で Local State・Preferences・Service Worker・Push 保存領域を複製したプロファイルは同じ購読を認識し、合成通知を受信しました。Push 保存領域を省いた対照では同じ購読を復元できませんでした。各条件の限定試験であり、OS側クライアントの利用有無、通常の画面操作、別端末への移譲や更新・失効は証明していません。

この再試験の準備中、複製後の試験通知を受信確認に数えない試験コード上の不備を発見し、修正しました。上記の複製後の受信結果は修正後に再確認したものです。通知種類と試験側の受信確認先が対応することを自動テストに追加しています。

接続先だけを試験用ローカル中継に変えた対照試験では、元の試験用 Push 保存領域を複製した場合に同じ購読で再受信できました。別の使い捨てプロファイルで、接続情報の保存記録内にある32バイトの鍵相当値だけを別の合成値に置き換えてから複製すると、同じ購読は復元されず、再接続時には元のトークンが送られました。通常のEdgeプロファイルや実際のXは触っていません。各1回の観測であり、変更値が署名鍵であることやWNS側がどの理由で接続を拒否したかはまだ確定できません。保存値、トークン、署名、通知内容は出力していません。

この対照を別の使い捨てプロファイルで再実行し、受信した完全な接続フレームの種類だけを照合しました。変更なしでは再接続時に `BND` 応答が観測され、合成通知も届きました。鍵相当値を変更した場合は、同じ購読を復元できず、観測範囲内に `BND` 応答がありませんでした。これは一対の限定的な結果で、応答がなかった理由やタイムアウト後の挙動を示しません。解析器は合成試験専用で、接続先に渡せる認証情報を作成するものではありません。

追加調査では、試験用の接続情報から計算した再接続署名が、別々に作成した3件の試験用プロファイルで Edge の署名と一致しました。さらに、ローカル中継で乱数と署名を同時に作り直したところ、WNSから応答があり、その接続で合成通知を受信できました。

続いて Edge を終了した後、Node.js 自身が WNS に新しいTLS接続を開き、再接続署名と接続ごとの購読確認応答を作成しました。別々の試験用プロファイル3件で、WNSから暗号化された合成通知を受信し、送信した暗号文との一致と復号を確認しています。接続の雛形は試験用Edgeの通信をメモリー内で取得し、購読確認に必要な製品固有値もインストール済みEdgeの一致確認済みバイナリから試験中にだけ読みました。いずれも出力・保存・配布していません。

この結果は移譲ファイルだけで接続できることを示すものではありません。接続雛形の自前生成、製品固有値の扱い、サイト別情報の安全な抽出、保存情報の更新・失効、受信確認と障害時の再送、Linux・実Xでの動作は未検証です。調査コードは本番ワーカーに接続しておらず、Edge向けの受付も有効化していません。購読確認候補の検討には、[Pidginの公開実装](https://lists.pidgin.im/commits/2008-June/009003.html)を参照しました。

Windows の一般的な通知チャネルはアプリ・利用者・端末にひも付き、有効期限や更新があります（[Microsoft のチャネル説明](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/push-notifications/request-create-save-notification-channel)）。この説明だけから Edge の Web Push 購読に同じ有効期限が適用されるとは断定できませんが、ファイルを一度移すだけで長期運用できると決めつけず、実際の更新と失効も確認する必要があります。

Windows の公開APIでチャネルを作成する方法についても確認しました。[Microsoft の API 説明](https://learn.microsoft.com/en-us/uwp/api/windows.networking.pushnotifications.pushnotificationchannelmanager.createpushnotificationchannelforapplicationasync)では、呼び出し元アプリに結び付くチャネルを作り、別のアプリIDを指定する場合も同じパッケージ内のアプリに限定されます。そのため、別のセットアップツールがこの公開APIを呼ぶだけで、既存の Edge の購読をサーバーへ引き継げる根拠にはなりません。これは API の適用範囲に関する判断であり、Edge の内部接続や別の正式な拡張経路が存在しないことを示すものではありません。

Brave向けのGoogle通知設定はツール専用の新規プロファイルに限定し、利用者の通常プロファイルは読み書きしません。Edgeの直接受信と、その他のChromium系ブラウザーは未対応・調査中です。ブラウザーの系統だけで接続方式を推測せず、実際の通知基盤と鍵の形式を確認してから対応します。
