# 通知管理画面の統合

2026-10-14 JST。合意仕様の全文は `x-auto-expansion-current-spec.txt`、
監視別の通知方法と切り戻しの条件は `realtime-notifications.md` を参照する。

## 導線

既存の新UIのDashboardShellに「通知を管理」「Xの接続」「利用状況とプラン」を配置する。利用者の旧UI／新UIの選択は保持する。月額プランと1回の支援は利用状況の下で分け、実際の通知プランとSquareの支払い契約を同一視しない。

通知管理は新着・価格・Xのタブと共通の「通知を追加」を持つ。Xタブの追加は監視フォームへ進む。新着・価格の対象入力でもXのプロフィールURLを検出し、Xの設定へ引き継ぐ。Xをサービスから選んだ場合は@ユーザー名を使える。既存のYouTubeの@ハンドル入力は保持する。既存登録の編集で種類を変更しない。

XのプロフィールURLはHTTPSのx.com/twitter.com（wwwを含む）の
プロフィールパスだけを受け付ける。
外部URLの取得、Xの数字IDの推測、非公開APIの呼び出しは行わない。
通常通知のpreview APIへX入力を送らない。

Xの既存下書きがある場合は保持して再開し、共通入口の新しい入力で上書きしない。通知先追加からの戻りも、呼び出した下書きだけに新しい通知先を選択する。保存直後の一覧再取得失敗は再作成を誘導しない。

## 表示

利用状況には登録件数・使用枠数・恒久追加・通知方法に使う追加枠を分けて表示する。Xを合計5個人枠で使う場合も、全体プールでは監視1件として数える。「追加できる監視」は1枠利用を前提とした件数と分かる表示にする。

旧owner設定は「Xの共通設定」と表示し、全監視の実効通知方法として表示しない。個別の希望・実効方式・必要枠数は監視ごとのサーバーDTOを使う。DTOが欠けた場合は推測して1枠や5枠を表示しない。

既存支援者が新規登録でリアルタイムを選んだ場合、資格と空きがあれば支援者優先枠の1枠見積もりを提示する。選択後に空きや資格が変わった場合は保存を止めて再確認を求め、別の枠や5枠消費へ切り替えない。通常の新規登録は従来の割当順とする。登録後も監視一覧の「通知方法を変更」から変更する。

利用状況とX監視の処理条件には、通常通知と同じ現在のプランを表示する。支援者プランの確認間隔が未設定の場合は設定待ちを表示し、無料プランの値へ置き換えない。

受信情報は接続・受信・監視との紐付け・送信結果を分ける。一覧が途中のページまでの場合、未表示の受信情報を未接続と断定しない。読み直しに失敗した値を0件や無料プランへ置き換えない。

## 文章の整理

`yomiyasu` と `stop-describing-ui` に沿って、重複する説明を省き、操作名と現在の状態を先に示す。料金、継続課金、枠の消費、削除の影響、他サイト通知の取得可能性と破棄方針は保持する。

| 変更前 | 変更後 |
|---|---|
| YOUR ACCOUNT／ご利用中の機能／機能説明の段落 | 利用状況 |
| 通知・接続・プランの各ナビに同じ内容の説明文 | アイコンと画面名 |
| X通知のタイミング（ownerの値を全件の実効値のように表示） | Xの共通設定／監視ごとの通知方法を選ぶ |
| 確認間隔の短縮に配分 | 通知方法に使う追加枠 |
| X監視を追加という別の入口 | 通知を追加 |

## 検証範囲

Reactの自動試験でタブのキーボード操作、非表示タブの読み取り抑止、下書き保持、プロフィール入力、個別RTの確認と競合、通知先への復帰、課金ページの文書遷移を検証する。課金ページへ出入りするナビはSquare用CSPを適用するため通常の文書遷移を使う。

`scripts/notification-experience-ui-harness.cjs` はループバックと使い捨てDBで実ページを組み立てる。Discord・決済・Xの外部I/Oは模擬で、実サービスへの配信を行わない。PCとスマートフォンの画面検証は、本番の認証・実XからDiscordへの配送検証と区別する。

実ブラウザーで共通入口からのX登録、監視別の特典1枠／合計5枠、明示保存、
通知先追加からの復帰を確認した。

文書全体の横はみ出しを解消した。
代表画像と模擬リクエストの記録は `notification-experience-browser/` に保存する。
実カード、実決済、実X投稿、実Discord配信はこの画面試験に含めない。

## 2026-10-15 通知の登録・編集の統合

2026-10-15 JST。利用者が承認した6項目と、X側の投稿通知設定に関する追加指示を反映する。
この文書は動作仕様で、テストと本番反映の結果は別の検証記録に残す。

### 登録と接続

新着・価格・Xの入口は共通の「通知を追加」とする。
対象、通知先、通知タイミングを主項目にし、言語・詳細ルールなどは詳細設定へ置く。
Xの接続が必要な場合は、登録中の画面内でPCでの準備とファイル登録へ進む。
接続を選んだ後は、同じ対象・通知先・タイミングの下書きへ戻す。
接続を選ぶだけで監視を保存したり、使用枠を増やしたりしない。

X監視の追加ごとに、追加用Firefoxで対象アカウントの投稿通知を有効にする手順を示す。
既に受信接続があっても、ブラウザー通知の許可と、その対象のプロフィールのベルを確認する。
Webでの登録とX側の通知設定は別の準備であり、Web登録がX側の設定を変更するとは案内しない。
本人の確認はサーバーによる検証とは区別し、対象を変更したら確認状態を見直す。
追加用Firefoxは設定後に閉じる。同時接続や再登録の注意は、操作する前に案内する。

ファイルと秘密鍵、他サイトの通知データの取り扱いに関する同意は維持する。
キャンセル・再選択・登録完了時には、一時的なファイルと登録セッションを消去する。
ファイル・鍵・Webhook URL・認証情報をブラウザーの永続ストレージへ保存しない。

### 監視ごとの編集

各通知の「通知設定」から対象・表示名・通知先・通知タイミングを編集する。
表示名だけの変更は一度の保存とし、送信条件や未送信通知を変えない。
送信先・対象・追加枠を変える場合は、影響を確認して保存する。
保存の競合や資格変更では下書きを保持し、現在の資格と必要枠を再確認する。

既存支援者が特典を使ってリアルタイム化する場合は、支援者優先枠への移動と
リアルタイムへの変更を、本人が確定する一つのトランザクションで保存する。
既存の監視本体が個人1枠を確保済みなら、個人の空きが0枠でも、
移動先の資格・保有数・全体容量を満たす1枠の変更を認める。
枠が埋まった場合や資格を失った場合は、別プールや5枠利用へ切り替えない。
空きの発生、プラン変更、通知方法の表示だけによる自動再配置は行わない。

表示名の保存も編集のrevisionを進め、監査を記録する。
未送信通知に対しては、同じ所有者と監視に属する、表示名だけの変更の
完全な監査チェーンを確認した場合に限り、以前のrevisionを互換として扱う。
設定変更・欠落・重複・別の所有者の履歴は互換として扱わない。

通常通知のルール割当・解除も、対象のrevisionと変更前のルールを確認する。
変更があれば、割当・revision・未送信取消・監査を同じトランザクションで保存する。
同一割当は状態を変えず、従来のAPIを使うクライアントも維持する。
別画面の変更を検出したら入力を保持し、本人の再取得・再確認を経て保存する。

### 状態と利用枠

一覧は、現在の状態・通知先・実際の通知タイミング・使用枠を先に表示する。
受信待ち、接続設定待ち、間隔設定待ち、停止中を区別する。
接続済み、通知データの受信、監視との照合、Discordへの送信を混同しない。
履歴が得られない場合は、送信成功や時刻を推測しない。
接続単位の受信日時は、その監視アカウントだけの受信時刻として表示しない。
各カードの「配信予定・履歴」で、その対象の配信情報を表示する。
最終送信確認は、送信済み・送信実績・DiscordメッセージIDのある記録を参照する。
複数対象をまとめる通知は、送信時の最終メンバーに含まれた対象だけへ紐づける。
一部送信・結果不明を送信成功として扱わず、別の所有者の私用履歴を表示しない。

リアルタイムに使わない確認間隔や、旧共通設定の未設定を、
リアルタイム監視全体の停止理由として表示しない。
旧共通設定は個別指定のない既存監視の初期設定として詳細へ残す。
プランの確認間隔は管理画面での設定を参照し、固定の無料間隔で補わない。

共用無料・支援者優先・有償特殊の内訳は利用状況へまとめる。
登録や編集では、その選択に必要な1枠または合計5枠を示す。
個人上限、全体満枠、資格失効はそれぞれの理由と操作先を示す。
新しい料金・プラン・決済条件・公開対象は、このUX変更では追加しない。

### スマートフォンと確認

編集画面を全画面で表示し、保存操作を下部に固定する。
停止・削除・枠の手動変更などの補助操作はメニューへまとめる。
フォーカス移動、Escape、入れ子の画面、スクロール固定、閉じた後の復帰を検証する。
追加の枠消費、チャンネルへの送信、削除、鍵の送信への確認を残す。
作成済みの通知先は再試行時に使い、同じWebhookを重複作成しない。

### 反映と切り戻し

この変更に新しいDDLや支援・契約データの書換えはない。
本番反映では支援者限定の公開設定、管理者が設定した間隔・枠数、鍵を維持する。
既存の作業用チェックアウトを保持し、mainの確定コミットから独立したリリースを作る。
旧UIと新バックエンドを組み合わせた互換版も準備し、
Workerの稼働確認後にWebを切り替える。
切り戻しは互換版へ行い、DBの復元や鍵の変更を自動実行しない。
バックアップ、ステージ検証、稼働中のrevision・lease・heartbeatを記録する。

## 2026-10-16 支援者向け監査への対応

監査は `762c2a44` と未コミット変更を含む作業ツリーを対象としていた。
修正は、通知管理画面の統合を反映した `a3637a19` を基準に行う。
元の監査結果を保持し、指摘と現在のコードを照合する。

### 配信と状態表示

| 指摘 | 対応 |
| --- | --- |
| R1 新着が確認間隔ごとに1件ずつ処理される | 同じ通知期間に配信可能だった候補を記録し、逐次取得や再起動でも続けて処理する |
| R2 429応答で試行回数が二重に増える | 送信開始で1回だけ加算する。送信開始前の準備失敗も1回として数える |
| R3 停止中のルールでも正常に見える | サーバーでルールと通知先の現在の状態を確認し、一覧と登録確認に反映する |
| R4 HTML応答や通信失敗の内部エラーが表示される | 安全な日本語と再読み込み・再ログイン操作を示し、下書きと項目別エラーを保持する |
| R5 Discordの削除失敗で内部情報が表示される | 既知のエラーコードに対応する固定文を返し、元の例外は内部診断へ記録する |
| R6 Discordの確認時刻が利用者別設定と異なる | 対象別の最終・次回確認時刻を返し、共通の取得時刻は別項目で保持する |

R1の記録は、通知期間を開いた時刻、その時点で処理対象だった配信IDの上限、
現在の確認間隔と枠設定からなる。対象のロック下で再確認し、
ルール実行の記録と同じトランザクションで保存する。
配信ごとの初期予定時刻は再試行時刻と分けて保持し、
障害による再試行で同じ通知期間から外れないようにする。
所属とID上限は初期予定で判定し、実行時は再試行の待機時間も守る。
後から見つかった新着は、現在の確認間隔に従う。
枠返却、契約変更、設定変更の後も、古い記録から優遇を引き継がない。
通常の1枠登録で従来の配信作成時に間隔を制御する経路は保持する。

429の既知の拒否は指定された待機時間を守り、再試行は10回までとする。
結果不明や一部送信済みの通知は、自動再送しない。
表示名の変更による未送信通知の維持と、機能変更時の取消も保持する。

ルールの未適用、停止、削除、確認待ちと、通知先の停止・削除を区別する。
ルール一覧の先頭ページに見つからないだけでは、正常稼働と判定しない。
通知枠、DMの表示内容、料金と支援枠の説明は、登録時の判断に必要な情報を残す。

新着の最終確認は、その監視対象の実績を使う。
共有取得元の過去時刻で補わず、初回の基準が未設定なら確認待ちとする。
対象ごとの確認予定と、共有取得元の取得予定は別項目で保持する。
画面とDiscordの「次回確認」は、対象の予定と取得制限の両方を満たす最短時刻に揃える。
対象自身の予定が未設定の場合は、共有取得元の予定だけで確定しない。

### 移行と切り戻し

`20261016_add_auto_watch_notification_window.sql` は、既存の
`auto_watch_targets` に `notification_window_json TEXT NULL`、
`auto_watch_deliveries` に `cadence_due_at_ms BIGINT NULL` を追加する。
通知・契約・支援履歴や既存の確認時刻を変更しない。
メモリー内の一時記録だけでは再起動後の残件を識別できないため、
通知期間と配信ごとの初期予定を、既存の2テーブルに各1列を追加して記録する。

既存のスキーマ移行処理を使い、列の存在確認と適用履歴で再適用を防ぐ。
NULLや不正な記録は、現在の確認間隔で安全に処理し、
次に正当な通知期間を開いたときに記録を更新する。
既存配信の初期予定がNULLなら、最初の有効なlease取得時に現在の予定を確定する。
過去の予定や設定を推測して再計算しない。
切り戻しでは列と記録を保持し、互換版のコードへ戻す。
旧コードは追加列を参照せず、従来の確認間隔の動作になる。
DB復元や列削除による切り戻しは行わない。

反映前に一貫したDBバックアップと、設定・鍵・実行環境の照合を行う。
Workerの稼働を確認してからWebを切り替える。
Discordのシャード数は起動時に自動決定されるため、過去の件数で固定しない。
同じWorkerの新しいheartbeatで、全シャードのready、IDの一意性、
件数の一致、停止・不明が0件であることを確認する。

### 確認する範囲

`scripts/run-supporter-readiness-acceptance.cjs` で、X/UI受入試験と、
通知・Discordコマンド・新着取得・価格取得の試験をまとめて実行する。
SQL試験は本番以外のポートを明示し、試験ごとの一時スキーマを使う。
初期化や停止に失敗した場合も、その試験のDB接続とスキーマを片付ける。

監査で挙がったP-256鍵の短い整数表現は、基準版で32バイトへ補完済みである。
短い固定値による再現試験を維持する。
数字IDが必須だったX登録と、観測済みのX通知形式への対応も基準版に含まれる。
新しい投稿・反応・私的通知の区別、所有者と監視対象の照合は引き続き検証する。

自動試験、ローカルのブラウザー確認、本番の稼働確認、
実際のX投稿からDiscord到着までの確認は、それぞれの証拠を分けて記録する。
実通知の確認には本人が登録した監視と通知先を使い、
本番へ試験用の監視・メッセージ・決済を追加しない。

## 2026-10-16 追加監査への対応

### 通知と編集の整合性

ルールの適用前には、そのルールを使う新着・価格・X監視を一緒に表示する。
適用要求には確認済みの対象一覧を識別するトークンを付け、
登録者、監視設定、割当先をロックした同じトランザクションで再確認する。
確認後に対象が増減した場合は、最新の一覧を確認してから適用する。
旧形式の割当操作も監視の版を進め、別の画面から古い割当を削除できないようにする。

使用中のルールを削除すると、そのルールを使う通知を停止し、割当を外す。
登録、通知先、購読、利用枠、送信済み・結果不明の記録を保持する。
通知の再開は利用者が明示的に行い、再開前に通知先と権限を確認する。
ルールを指定せずに再開した場合は、通常の通知方式を使う。

個人用ルールの複製は表示中の公開範囲を保持する。
異なる通知・履歴・部品ファイル・共有パッケージへ切り替えた後は、
前の非同期応答で編集対象や送信先を上書きしない。
同じXアカウントへの登録要求を再送したときは、指定内容が同じ場合だけ同じ登録を返す。
通知先や名前などが異なる場合は、既存登録の編集へ案内する。

### 取得・送信と再起動

検知済みの新着は本文を含めて既存の取得状態へ保存する。
次回の上流一覧から消えても、最初の観測時刻を保持して処理を続ける。
初回に過去分を通知しない条件と、再起動後の重複防止は維持する。
Steamの割引情報が不明な観測は、割引なしの観測と区別する。
BOOTHの未認識ページを空の商品一覧として基準化しない。

分割送信は毎通、送信先、登録者の権限、NSFW設定、安全停止を再確認する。
送信開始前と確認できる予約だけを回収し、送信済み・結果不明の利用実績を返却しない。
そのため既存の `automation_rate_reservations` に `job_id` と `lease_token` を追加する。
以前の予約で対応するジョブが不明なものは、推測で回収しない。

まとめ通知は期限切れの項目だけを外し、残る項目の期限と時刻条件を保持する。
期限を延長せず、利用者が手動指定した時刻より前へ送信を移さない。
ルールの除外・待機・期限切れは、利用者向けの処理履歴から確認できる。
監視を外した受信接続は終了し、別の監視が使っている接続と暗号化済み受信記録は保持する。

### 共有辞書の由来と移行

辞書の保存版ごとに配布元のパッケージID・版と、由来の確認状態を保持する。
既存の `automation_dictionary_revisions` に `source_package_id`、
`source_package_version`、`origin_reviewed` の3列を追加し、新しいテーブルは作らない。
公式の辞書・ルールパッケージの導入と更新で由来を記録し、
別ルールからの利用、名前変更、ローカル編集、過去版の復元後も安全停止を確認する。
通常のテキスト取込には、利用者が指定した配布元IDをそのまま採用しない。

移行は現在の導入記録と最初の保存版から、確実に分かる対応だけを引き継ぐ。
同じ辞書IDの派生版は配布元を保持し、元の版が不明なら版番号をNULLのまま残す。
過去の更新で失った辞書IDと配布元の対応を、名前、時刻、本文の一致から推測しない。

旧パッケージ導入者に由来を確認できない辞書が残る場合は、
`DB_MIGRATION_DICTIONARY_ORIGIN_REVIEW_REQUIRED` で、この移行のDDL実行前に停止する。
運用者はバックアップを保持し、表示された辞書IDを元の配布・導入資料と照合する。
確認できた配布元と版を記録するか、独立した辞書だと確認して `origin_reviewed=1` を記録してから再実行する。
確認資料がなければ移行を再開せず、元データを保持する。
この確認は移行時の操作であり、通常の辞書を一律に配信停止する処理ではない。

今回の本番読み取り確認（2026-10-16 08:28 JST）では、共有パッケージ・導入履歴は0件だった。
既存の通常辞書2件は、配布元を推測で追加せず保持する。
反映直前とWorker起動時にも、この移行前条件を確認する。

### 移行・切り戻しの手順

既存のスキーマ移行処理で、予約の対応2列と辞書の由来3列を追加する。
辞書の移行前確認は各DDLより先に行い、部分適用後の再実行も列の存在確認と記録で処理する。
本文、通知設定、契約、支援履歴、枠の割当を移行で変更しない。
既知の由来の補完は新しい列だけを更新する。

切り戻しでは追加列、由来、予約、受信記録を保持し、DBの復元や列削除を行わない。
旧コードは今回の問題を含むため、互換版への切り戻しは復旧の手段として扱う。
本反映では設定・Node・鍵を照合し、Worker、全シャード、Webの順に正常性を確認する。
