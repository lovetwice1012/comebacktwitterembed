# 共通 DB 接続枠を予約する実験

この実験は `experiments/chrome-push/reserved-db-experiment.cjs` に置いています。通常ワーカー、ダッシュボード、本番設定には接続していません。既存の DB pool を通常処理と通知処理の両方で使い、通知処理側が同時に取得できる接続数を pool 上限より少なくする案を検証しています。同じ pool を使う限り、別の pool が異なる DB を指す問題は起こりません。ただし proxy やフェイルオーバーの背後にある DB 全体の一貫性を、この実験だけで証明するものではありません。

待機の数は上限を設け、中断した待機は削除します。実行中の SQL は、中断要求だけで接続枠を空けず、DB ドライバーの応答を待ってから返します。トランザクションの途中で中断された場合は rollback を試み、失敗した場合は接続を破棄します。nested transaction のエラーを呼び出し側が捕捉しても、外側の transaction は commit しません。COMMIT の成否が不明な場合や fatal 通信エラーでは、その実験用の通知処理枠を再利用せず、運用上の停止・調査が必要な状態として残します。

合成 MariaDB 11.4.10 で、同じ 4 接続 pool のうち通知処理の SQL を3件待機させても、残る1接続で通常 SELECT が実行できました。通知側の4件目は有界待機し、中断できました。別の試験では、SQL の終了前に中断しても枠を返さず、SQL 終了後の rollback で途中の挿入が残らないことを確認しました。実際の暗号化 inbox と既存 gateway・router・queue をこの adapter に接続し、合成通知1件を1ジョブとして処理できました。いずれも使い捨て DB と試験データです。

実ドライバーの query timeout 後、MariaDB 側では `SLEEP` が引き続き実行中でした。実験 adapter はその不確かな枠を再利用せず、通常 SELECT が通ることを確認しました。単体7件と実 DB 4件が成功しましたが、これはサーバー側 SQL やロックがただちに消えることを意味しません。枠を永久に保留する方式は、新たな通知処理の能力を失い得ます。プロセスの再起動でローカル状態は失われるため、旧 SQL がサーバー側に残っていないことも別途確認しなければなりません。

通常処理の接続が他の操作で全て使われている場合や、pool 内部の FIFO 待機列に通知処理が先に入っている場合は、通常処理の応答時間を保証できません。pool の `getConnection` callback が無期限に返らない場合も、枠は占有されたままで、自動回復を保証しません。DB サーバーそのものの接続上限、ロックの競合、複数 worker の合算、送信済み COMMIT の結果も予約だけでは保証できません。設定変更・プラン間隔・realtime・全 wake 経路との統合、通知を失わない公平な再走査、旧 lease、停止時の回復、実負荷と障害復旧を検証し、同一 pool を通らない SQL がないことを確認するまでは本番へ接続しません。

同じ pool に複数の実験 adapter を作ると、それぞれが独立に上限を数えるため、通常処理に残すはずの接続まで消費できることを合成再現しました。実験 adapter は同一モジュール内で同じ pool の二重作成を拒否します。正常停止後、取得済み接続がすべて返却され、不確かな枠がなければ同じ pool に作り直せます。通信結果が不確かな枠がある場合は、停止後も同じ pool 上での作り直しを拒否します。別のモジュール実体や直接の pool 利用、複数 worker をこのガードだけで制限できるわけではありません。重複拒否、正常停止後の再作成、停止中の接続返却待ち、不確かな枠が残る場合の拒否を含む単体10件が成功しました。
