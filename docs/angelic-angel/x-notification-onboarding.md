# X通知のセットアップ画面・手動ファイル登録

更新: 2026-10-14 JST。ローカル実装。実X通知の受信・復号のG1、本番提供の受入とは分離する。

## 利用者の導線

`/dashboard/automation/x` は既存のDiscordログインが必要な個人用画面。自動通知のヘッダー、個人X監視パネルから開く。
サーバー共有画面からは個人用ページへのリンクを表示し、サーバーIDを付けたAPIへ秘密情報を送らない。

1. 「X通知データの保存ツール」をダウンロードし、ZIPをすべて展開する。
2. 「ダブルクリックで開始.cmd」を開き、専用Firefoxの準備を進める。
3. 本人が専用FirefoxでXへログインし、ブラウザー通知と対象アカウントの投稿通知を設定する。
4. 専用Firefoxを閉じ、ツールでJSONファイルをPCに保存する。ツールは外部へアップロードしない。
5. Web画面で取り扱いに同意し、そのJSONを選ぶ。「内容を確認」でサービスへ送信して形式を検証し、確認後に「この受信情報を登録」を押す。

ツールのファイルは平文の機密情報。Cookie・閲覧履歴・保存パスワードや通常プロファイル丸ごとは受け付けない。
他サイトの通知設定が混在する場合も、作成直前の明示確認後にX用の鍵だけを保存できる。他サイトの復号鍵・本文・origin一覧はファイルに含めない。
UAIDを共有するため他サイトの暗号化通知や識別情報もサーバーへ届く可能性があり、届いたデータは技術的に取得可能であることを、ローカル確認画面とWebの登録前説明・同意欄で明示する。
現在はX以外を利用・復号・永続保存せず、配送しないACKで破棄する。破棄後にFirefox等で受け取れない可能性も説明する。
登録への同意は他サイトの通知利用の許可を兼ねない。別途明確な許可を得るまで利用しない。
画面は秘密値を表示せず、選択ファイルの本文・セッショントークンをlocalStorage/sessionStorageへ保存しない。
選択取消、ページ非活性化、コンポーネント終了、インポート試行後に本文の参照を消去する。JS実行環境の物理メモリー消去を保証するものではない。

登録済み一覧は保存日時・Firefox版・保存状態だけを表示する。保存完了は通知受信の成功を意味しない。
受信情報の保存と監視対象の登録を分ける。前者は枠を確保せず、後者は既存の個人枠・全体枠の原子的な割当を使う。
既存の割当は自動移動しない。実通知を確認するまでは、新規X監視受付の既定OFFを維持する。

## APIと保存

既存 `/api/automation/[...path]` のセッション認証、同一origin検査、fleet writer権限、操作レート制限、受信サイズ制限を再利用する。
秘密を扱う変更は設定された公開originがHTTPSであることも検査する。X設定は個人専用で、管理者でも別利用者の設定へアクセスできない。

| メソッド・パス | 動作 |
|---|---|
| GET `x-setup` | 受付状態、固定ZIP情報、本人の安全なメタデータを最大100件。`afterId`による続き |
| POST `x-setup/sessions` | 明示同意から10分のワンタイム登録セッション。本人の以前のセッションを置換 |
| POST `x-setup/validate` | 未使用セッションを確認し、JSONの形式・鍵の整合性を検証。本文は保存しない |
| POST `x-setup/import` | 再検証して暗号化保存、セッション消費、監査を同じDBトランザクションで実行 |
| DELETE `x-setup/subscriptions/{id}` | 所有者・revisionを検証し、暗号文と本人の保留セッションを削除。監査と原子的に実行 |
| GET `x-setup/download` | 認証後、固定9ファイルから再構築して既存配布版のサイズ・SHA256を検証。詳細 `x-setup-download.md` |

セッションのDB保存はSHA256だけ。使用済み・期限切れ・別ユーザー・別タブによる更新を拒否する。
検証失敗・DB障害では成功扱いにせず、トランザクションの失敗時には保存と消費を両方取り消す。
UAIDのハイフンを除いたハッシュとchannelハッシュに独立したUNIQUE制約を置き、同時インポートや別利用者への重複登録を防ぐ。
本人の同一内容の再インポートは二重保存しない。同一識別子で内容が変わった場合は自動上書きせず、明示削除後の再登録を案内する。

ファイルはUTF-8で32KiB以内。全階層の不明フィールド、重複JSONキー、Cookie等の余分な内容を拒否する。
X/Mozillaの正規HTTPS URL、空のoriginAttributes、UAID/channel形式、base64urlの正規形、P-256点・scalar範囲・公開秘密鍵の一致をサーバーで検証する。
provenanceはファイルの申告であり、専用ツールが作ったことやXが現在購読を発行済みであることを暗号学的に証明しない。
実受信による確認は別のG1工程である。

新規の2テーブルだけを追加する。購読秘密とワンタイムセッションを扱う既存テーブルがなく、アカウントごとの監視metadataへ秘密を重複保存しないための分離である。
両テーブルはInnoDB。通常通知、料金プラン、支援台帳、監視枠の既存テーブルはこの登録処理で変更しない。
監査は `x.setup.import` / `x.setup.delete` と非機密のID・revision・同意版・重複判定だけを記録する。

## 暗号化と受付設定

本番の設定値は今回追加・変更していない。次の設定が揃うまで受付はOFFで、説明と固定ZIPの取得は可能。

| 設定 | 値 |
|---|---|
| `X_NOTIFICATION_INTAKE_ENABLED` | 明示した `1` のみ受付可。既定はOFF |
| `X_NOTIFICATION_INTAKE_KEY_ID` | 公開鍵の版ID |
| `X_NOTIFICATION_INTAKE_PUBLIC_KEY` | RSA 3072〜4096bit公開鍵のSPKI DERをbase64url無paddingで表したもの |

Webへ渡すのは公開鍵のみ。受信Worker用秘密鍵をWebの環境変数、設定ファイル、配布ZIPへ渡さない。
保存時に購読ごとのAES-256鍵・96bit nonceを生成してGCM暗号化し、AES鍵をRSA-OAEP-SHA256でラップする。
暗号文・ラップ鍵は版2のenvelopeに保存し、subscription ID・owner ID・revision・key IDをGCMとOAEPの認証境界に結び付ける。
Webにはsealだけ、Worker用ライブラリにはopenだけを渡す。公開鍵だけでは保管済みデータを復号できない。
将来のWorkerは復号監査とアクセス権限の運用を別途接続する必要があり、この登録処理からWorkerを起動しない。

ローテーション時は新しい公開鍵IDを受付へ設定し、旧暗号文に対応する秘密鍵はWorker専用の鍵管理へ保持する。
ライブラリは旧IDによる復号と、旧鍵を外した後のfail-closedを検証する。既存暗号文の一括再暗号化や実鍵配備はこの変更で実行しない。
購読が残ったまま旧秘密鍵を破棄すると復旧できない。旧鍵の保存期限・バックアップの消去期限は既存運用ポリシーと照合して本番提供前に確定する。

## 移行・切り戻し

1. 承認された本番作業では先に既存DBのバックアップと復旧確認を行う。今回その操作は実行していない。
2. `migrations/20261014_add_x_notification_intake.sql` または通常のschema初期化で追加DDLを適用する。再実行可能で、既存行の書換えはない。
3. 認証済みHTTPS経路、配布ZIPハッシュ、公開鍵・Worker秘密鍵の権限分離を確認してから、別途承認した受付設定を適用する。
4. 切り戻すときは受付フラグをOFFに戻す。保存済みデータと鍵を保持し、必要なら画面から本人が削除できる状態を維持する。
5. 旧コードへ戻しても追加テーブルは残す。通常通知・料金プラン・支援履歴への巻き戻しは不要。DROPや秘密鍵破棄を自動実行しない。

Webの削除はlive DBの暗号文を消す。バックアップ中の暗号文、X/Firefox側の購読・旧端末の通知許可までは解除しない。
退会・バックアップ保持期限・Workerによる受信停止の統合は本番提供前の別受入であり、未実装の受信Workerが停止処理を実施済みとは表示しない。
