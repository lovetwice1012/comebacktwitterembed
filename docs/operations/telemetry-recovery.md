# 管理記録の転送と過去履歴の復元

管理記録はBotの待機ファイルから管理サービスへ送信し、受付確認後に
待機ファイルを解放する。管理サービスに送れない大きな過去記録は、
待機ファイルの原本をハッシュ付きファイルに保存してから、小さくした
記録を送信する。表示用の記録には省略箇所と原本の参照を残す。
過去の稼働ハートビートを再送するときは履歴として保存し、現在の
Botの稼働状態として採用しない。元の内容は保管ファイルで確認できる。

Bot側の保存済み展開履歴に記録があり、管理サービス側に対応する
処理開始記録がない場合は、`scripts/recover-expansion-traces.py`
で不足分を補える。管理サービスの受付APIを通して追加し、元DBや
既存記録を上書きしない。同じ復元を再実行してもIDで重複を防ぐ。
元の詳細がないものには復元元と詳細不足を明示し、確認できない
完了結果を成功と扱わない。

実行前に待機ファイルの原本と設定の保全、空き容量、管理APIの稼働、
対象期間を確認する。先に通常の待機記録を再送し、待機ファイルが
空になってから、固定した過去期間をdry-runで確認する。

```text
python3 scripts/recover-expansion-traces.py --from-ms 開始時刻 --until-ms 終了時刻 --max-traces 100000
```

開始・終了はUnixミリ秒で、終了は3分以上前に固定する。dry-runは
読み取りのみ。適用時は、同じ引数に `--apply` を追加する。
実行環境には既存のDB接続設定と管理サービス用トークンを用意する。
トークンをコマンド引数やログへ書かない。途中失敗時は原因を確認し、
同じ期間を再実行する。実行後に再度dry-runし、不足件数と残った
待機ファイルを確認する。
最大件数に達した場合は表示された `lastProcessedMs` を次の
開始時刻に指定する。同じミリ秒の記録は再確認され、既存の記録は
重複しない。小分けの受付結果を確認しながら処理する。

Bot側にも待機ファイルにも残っていない詳細は復元できない。省略された
大きな記録の原本は管理用ホスト上のハッシュ付き保管ファイルに残り、
一覧には容量を抑えた内容が表示される。アクセスは管理者に限定する。
