# Edge WNS receiver: recovery investigation

Status: research only. The Edge intake and worker must remain disabled in production until the setup flow, version handling, operational review and release checks are complete.

## Test scope

On Windows, a disposable Edge profile subscribed to a localhost test site. No existing browser profile, X account or X notification was used. The browser's generated subscription was transferred to a synthetic receiver; a second subscription and the receiver used the real Windows notification service. The receiver reconnected with its rotated token. No public service credentials or subscription keys were logged or retained.

Two independent test profiles were compared. Each received one test notification while connected, disconnected, received another test notification while offline, and reconnected. The first receiver closed without writing an acknowledgement for the connected notification. The second wrote the current candidate acknowledgement and waited briefly before closing. After reconnect, each was observed for 30 seconds before a new notification was sent.

## Observations and limits

- Both runs received the notification sent while disconnected and a fresh notification after the observation period.
- Neither run replayed the notification that had already arrived before disconnection during the 30-second observation period, including the run that did not send an acknowledgement.
- Writing the candidate acknowledgement did not prevent the next notification from arriving. This does not prove that WNS durably accepted the acknowledgement.
- These are two controlled observations, not a complete specification of WNS replay, browser Web Push behavior, long outages or production delivery. The experiment does not prove that a notification lost before the database commit can be recovered.
- The implementation persists an owned encrypted notification before writing an acknowledgement and recovers a committed notification after a worker takeover. That protects already committed data; it does not establish a guarantee for a process crash before commit.
- The shared worker coalesces delivery wake-ups while a previous callback is running. Each received notification is still stored separately; the existing inbox scan recovers receipts that did not get their own immediate callback. A 25-notification synthetic burst was persisted while a callback was blocked, and a live synthetic WNS capture/recovery test passed after this change. These checks do not establish a provider replay guarantee.
- The transport pauses socket reads when its bounded queue fills and resumes after the queue drains. Tests cover a multi-frame burst, real Node stream backpressure and overflow. A synthetic live WNS receive/reconnect test passed after the change. A forced close, unrecoverable overflow or crash can still lose a frame that has not reached durable storage.
- After an unexpected socket close, socket error, malformed input or queue overflow, complete frames already in the bounded queue are persisted without sending an acknowledgement, while owner authorization and the database lease remain valid. Unit tests cover disconnect, malformed input, overflow, ACK failure, cancellation and revoked access; disposable MariaDB tests verify recovery by a successor after disconnect and malformed input. The chunk causing an overflow or malformed input is discarded; incomplete frames, unread bytes, explicit shutdown, process failure and database or authorization failure remain outside this protection.
- Reopening a disposable configured Edge profile while its synthetic WNS receiver was connected caused the receiver to stop in two control runs; the subsequent test notification was observed neither by that receiver nor by the browser during the observation window. In two separate runs, starting the reopened browser with its WNS receive endpoint pointed at an unreachable loopback address kept the worker connected and receiving, while the browser retained the same subscription. One fresh-profile probe with that endpoint blocked could not create its initial subscription. The setup therefore inspects an owned stopped-profile snapshot and applies the receive block only when it finds an existing X subscription. These observations are limited to the tested Edge build and synthetic subscriptions.
- The server's WNS reconnect token can change while the blocked setup browser retains its older token. Reimporting the same cryptographic subscription therefore fences the old lease but preserves an already stored server token. A controlled WNS test confirmed that the stored token differed from the exported token, survived reimport, and received a later synthetic notification. Recovery when the stored token itself has become invalid remains to be characterized; do not silently replace it with an unverified token.
- Microsoft documents that WNS notification delivery is not guaranteed, and that a successful sender response is not proof of delivery. Its documentation also describes type-dependent offline caching; do not assume those native-app details completely describe Edge Web Push. See [WNS overview](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/push-notifications/wns-overview) and [WNS request and response headers](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/push-notifications/push-request-response-headers).

## Release follow-up

Validate the final setup flow with an explicitly approved real X test, characterize reconnect and multi-notification offline behavior for supported Edge versions, and decide how to surface and mitigate provider-side delivery gaps. Keep any replay or delivery claim within the evidence gathered. Do not silently enable a polling fallback or alter the existing notification plan without an approved design.

For a possible per-version protocol calibration, a Windows-only helper can create a short-lived localhost certificate in memory without installing it into the current user's certificate store. A disposable-profile test used its public-key pin for a local WNS relay and verified that an unrelated untrusted TLS endpoint stayed blocked. A separate process-identity helper checked the local TCP owner, browser process ancestry, executable and captured start time before forwarding. In one controlled test it allowed two test Edge connections and rejected a connection from another local process. This remains research infrastructure: the synchronous test implementation is not part of the setup package, broader race and access-permission behavior still needs review, and the result does not justify intercepting a user's browsing traffic.

The calibration relay prototype reads only bounded protocol metadata after an injected peer authorization check. A controlled test created a second disposable Edge profile solely for calibration, obtained metadata without fixed identifiers, and used it to receive a synthetic WNS notification for a separate disposable profile through the DB-backed worker. The calibration profile's test subscription was prepared through an inherited DevTools pipe, without a TCP debugger port; the target profile did not use the relay. This does not prove compatibility across Edge versions or make the relay ready for distribution; its peer authorization, asynchronous lifecycle, privilege boundaries and failure cleanup require review in the final setup integration.

A bundled calibration helper has also been exercised on Windows without installed Node modules. It checks the Edge executable's Microsoft signature, uses a marked empty profile, verifies the loopback peer through the Windows process and TCP APIs, and returns protocol metadata through standard output. An unsigned file named `msedge.exe` and a reused nonempty profile were rejected. A Windows Job wrapper starts the helper suspended, assigns it to the Job before execution, passes input through an anonymous pipe, and limits output; tests exercised explicit termination and Job-handle disposal with a child process. A PowerShell orchestration helper now creates a private marked directory, applies bounded waits, stops the job and removes the directory. A synthetic live Edge calibration and an unsigned-browser failure both completed with the temporary directory removed.

An Edge preview archive can now be built locally. Its setup validates a package manifest before loading shared code, creates a separate private Edge profile, and connects capture, calibration and manual file export. A Windows integration test used a synthetic local broker and synthetic subscription database with the real calibration helper; it produced a valid transfer and removed its scratch directories. This does not exercise the real X site, the real interactive capture flow, or WNS delivery from that particular archive. The preview has not been published or deployed.
