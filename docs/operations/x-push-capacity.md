# X通知受信の接続数と負荷

受信ワーカーは一つのNode.jsプロセスで複数の受信設定を管理します。受信設定ごとに外部Pushサーバーへの接続を一つ持ちます。同じ受信設定に複数のX監視が結び付く場合、監視件数だけ接続やプロセスが増えるわけではありません。ChromeとFirefoxはそれぞれの通知サーバーに接続します。

既定の接続上限はワーカーごとに1,000件です。`X_NOTIFICATION_MAX_CONNECTIONS` で1〜10,000の整数に変更できます。この数値は設定上の上限であり、10,000件を処理できる保証ではありません。定期的な受信記録の処理は、既定で同時16件までです。`X_NOTIFICATION_DRAIN_CONCURRENCY` で1〜100に変更できます。通知の到着を契機とした処理は定期走査を待ちません。

各接続はメモリ、TLSソケット、受信者の所有権更新、および通知の処理に応じたDBアクセスを使います。現行の既定leaseは30秒で、接続中はおよそ10秒ごとに更新します。停止中や接続不能なときは再接続待ちが発生します。数値を増やす前にCPU、メモリ、ファイルディスクリプタ、DB接続待ち、lease更新時間、受信から配信までの遅延、再接続数を測定してください。

2026-11-10の開発用Windows上のローカル試験では、1プロセス内のTLSクライアントと試験用サーバーで1,000接続を維持し、RSSは約134 MiB増加しました。試験用サーバーも同じプロセスに含みます。FCM、Mozilla、本番DB、Discord、長時間運用、障害時の一斉再接続は含まず、本番の収容能力を示しません。再現用の `experiments/chrome-push/loopback-capacity.cjs` はローカルループバックだけを使用します。

別の自動テストでは、1つのChrome受信ゲートウェイで256件の模擬接続を同時に開始し、受信情報を各登録に対応付けて処理・停止できることを確認します。ソケットと保存先は模擬実装のため、実際のネットワークやDBを含む負荷・収容能力の試験ではありません。

受信行の初回取得については、隔離MariaDBに100人分の同時要求を送り、所有者ごとの取得と解放が成功することも確認しています。試験DBの接続プールは最大8接続のため、100本のSQLが同時実行されたことや本番規模の性能を示すものではありません。

実FCMと隔離MariaDBを使う試験では、ChromeとBraveの合成購読を1つの受信ワーカープロセスで同時に接続し、2人分の受信・通知ジョブが混ざらないことを確認しました。一方の受信情報を再登録した場合も、もう一方の接続が維持され、双方の次の通知が各利用者のジョブになることを確認しています。5分間隔は試験用DBの時刻を調整して再現しています。2接続の試験であり、数百件以上の実運用時の容量を示すものではありません。

同じ試験で、ChromeのバージョンとBraveのChromiumエンジン版を合成ファイル上で変更して再登録し、更新値を使った再接続と、その後の実FCM受信を確認しています。ブラウザー本体の更新や長期的な購読維持を再現した試験ではありません。

複数の受信ワーカーが同じDBを使う場合、受信設定ごとのleaseは二重所有を防ぐためのものです。これは均等な分散やフェイルオーバー完了の証明ではありません。現状の候補走査とfleetの起動・復旧ポリシーを含め、複数プロセスの負荷と競合を検証してから構成してください。
