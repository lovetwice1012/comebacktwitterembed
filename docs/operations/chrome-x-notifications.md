# ChromeによるX通知の受信

設定用ChromeまたはBraveの専用プロファイルから、Windows用ツールで通知情報をJSONファイルに保存します。利用者が登録画面からファイルを選びます。ツール自身はファイルを送信しません。Xの投稿通知とブラウザー通知は、監視するアカウントごとに利用者がオンにします。Braveでは専用プロファイルだけでGoogleのプッシュ通知サービスを利用します。普段使いの設定には触れません。

設定用ブラウザーとの通信は、子プロセスに継承された非公開パイプを使います。ローカルの仲介窓口は専用フォルダーのアクセス権で保護された使い捨て認証情報を必要とし、任意のデバッグ操作は受け付けません。Windowsの別ユーザーによる実証試験は未実施です。

設定用Chrome・Braveの通知受信接続は、この専用プロファイルを開くときだけ停止します。受信接続先の指定と通知サーバーの名前解決制限を併用し、Chromiumの一方の設定が変更された場合にも備えます。ブラウザーで通知登録を行いながら、サーバー側で通知を受信できます。通常使用するブラウザーには影響しません。設定後にファイルを保存して再登録すると、同じ受信情報は監視・通知設定・既存の受信記録を保ったまま、該当する受信接続だけを張り直します。ブラウザーのバージョンだけが変わった場合も同じ受信情報として更新できます。

Chromeの接続情報は同一プロファイル内の通知を共用します。X以外の通知がサーバーに届く可能性があることを、ファイル作成前とアップロード前に案内します。現在は対象外の通知を復号・保存・利用せず破棄します。受信確認によってブラウザー側で同じ通知を受け取れなくなる可能性があります。

## 移行と公開

本番データ変更、マイグレーション、本番デプロイは事前承認を得てから行います。以下は手順であり、実施済みを意味しません。

1. DBバックアップの取得と復元手順を確認し、既存Firefoxの受信設定・通知件数を記録する。
2. `migrations/20261110_add_x_subscription_browser_kind.sql`、`migrations/20261110_add_chrome_mcs_pending.sql`、`migrations/20261110_add_chrome_checkin.sql`、`migrations/20261110_allow_chrome_mcs_control_pending.sql` をこの順に適用する。既存の受信設定を `firefox` として保持し、未確認の受信IDと端末確認の予定を保存する。最後の変更は通知サービスの制御メッセージにも同じ再送確認を使用するためのもの。
3. 検証済みZIP `artifacts/angelic-setup/chrome-setup-0.1.0-chrome-preview.1.zip` をダッシュボードの配布物に含め、SHA-256とバイト数が `dashboard/lib/x-chrome-setup-download.ts` の値と一致することを確認する。
4. Webと受信ワーカーの両方で `X_NOTIFICATION_CHROME_ENABLED=1` を設定する。Braveの受付は、すべてのWeb・受信ワーカーがBrave対応版へ更新されたことを確認してから、Web側で `X_NOTIFICATION_BRAVE_ENABLED=1` を設定する。既存の `X_NOTIFICATION_RECEIVER_ENABLED=1`、処理ポリシー、暗号鍵、fleet leaseも必要。支援者限定で公開する場合は `X_NOTIFICATION_ROLLOUT=supporters` を維持し、対象者以外の登録が拒否されることを確認する。
5. 利用者自身が設定した実際のX通知で、登録画面、接続状態、投稿通知、Discord配信を確認する。接続確認だけで配送成功と判断しない。

## 停止とロールバック

Braveの新規受付だけを停止するにはWeb側の `X_NOTIFICATION_BRAVE_ENABLED` を無効にします。既存のBrave接続は受信を続けます。Chrome・Braveの新規受付を停止するにはWeb側の `X_NOTIFICATION_CHROME_ENABLED` を無効にします。受信側の同設定を無効にすると既存の両ブラウザーの接続も停止するため、影響する利用者へ案内し、未処理の受信記録と未確認IDを確認します。Firefoxの設定や共有登録枠を削除してはいけません。

旧版へ戻す場合は、Chrome・Brave接続を止めてDBバックアップを保持し、`automation_x_mcs_pending`、`browser_kind`、`chrome_checkin_*` 列を残す方法を優先します。Braveを理解しない旧版はBrave登録を読み取れないため、Brave対応版を維持するか、登録データを保全したうえで復旧手順を決めてから切り戻します。未確認IDや登録が残っている状態でテーブル・列を削除すると復旧情報やブラウザー種別、端末確認の履歴が失われます。`inbox_id` を `NOT NULL` に戻す操作は、`inbox_id IS NULL` の未確認制御IDが残っていないことを確認するまでは行いません。削除が必要な場合は、影響する登録の復旧方針とバックアップを別途確認してください。マイグレーションを戻すためだけに既存登録を削除しません。

通知サービスが受信前に通知を失ったと報告した場合は、`x.push.provider.deleted_messages` を監査ログに記録し、利用者の受信設定に直近の報告日時を表示します。制御メッセージ自体は通知として配送せず、記録が確定してから受信確認します。送信エラーの制御メッセージは `x.push.provider.send_error` に記録します。

## 検証の範囲

試験サイト、実FCM、隔離MariaDB、架空のユーザーと通知を使った一連の検証は成功しています。試験専用Chromeプロファイルで端末確認、設定用Chromeを開いたままのサーバー受信とChrome側の受信イベントがないこと、Chromeを開き直した後のファイル再登録、接続の再確立と次の通知ジョブ作成を確認しました。確認時刻は受信設定の版とともに保存し、次のワーカーに引き継ぎます。認証拒否または端末情報の変更時は購読を書き換えず、再登録待ちにします。Xの実アカウント、実際のDiscord配送、Chrome更新後の接続情報の長期的な寿命、および長時間の再接続は未検証です。受信ワーカーの接続数と負荷は `docs/operations/x-push-capacity.md` を参照してください。

隔離Linuxでも試験専用の購読情報を使い、端末確認、実FCMからの暗号化通知受信、隔離MariaDBへの保存と通知ジョブ作成を確認しています。5分のまとめ処理は試験用DBの時刻を調整して再現しています。本番DBやDiscord配送の確認は含みません。

隔離MariaDBと模擬接続を使う追加テストでは、Chrome・Braveの受信確認の送信失敗後に別ワーカーへ接続を引き継ぎ、未確認IDの再送、保存済み通知の復号、通知ジョブの作成、重複受信時に記録やジョブが増えないことを確認しています。5分のまとめ処理は試験用DBの時刻を調整して再現しています。この試験は実際のネットワーク障害やDiscordへの配送を再現するものではありません。

画面の追加試験では、試験専用のChromeとBraveをそれぞれ用い、Firefox・Chrome・Braveの合成ファイルについてブラウザーの選択、ファイルの確認・保存、再読み込み後の表示を実際の登録APIと隔離MariaDBで確認しています。Chromeのデスクトップ幅と、Firefox・Braveの案内のモバイル幅を確認し、ファイルの選択・取り消し・再選択と画面上の選択状態も検証しています。Firefox本体でも、500px幅の画面でFirefox形式のファイル選択・取り消し・再選択・確認・保存と、鍵が画面やWebストレージに出ないことを確認しました。既存の利用者プロファイルや実際のXアカウントは使用していません。
