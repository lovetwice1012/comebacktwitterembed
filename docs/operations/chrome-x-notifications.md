# ChromeによるX通知の受信

設定用Chromeの専用プロファイルから、Windows用ツールで通知情報をJSONファイルに保存します。利用者が登録画面からファイルを選びます。ツール自身はファイルを送信しません。Xの投稿通知とブラウザー通知は、監視するアカウントごとに利用者がオンにします。

設定用Chromeとの通信は、そのChromeの子プロセスに継承された非公開パイプを使います。ローカルの仲介窓口は専用フォルダーのアクセス権で保護された使い捨て認証情報を必要とし、任意のデバッグ操作は受け付けません。Windowsの別ユーザーによる実証試験は未実施です。

設定用Chromeの通知受信接続は、この専用プロファイルを開くときだけ停止します。受信接続先の指定と通知サーバーの名前解決制限を併用し、Chromiumの一方の設定が変更された場合にも備えます。Chromeで通知登録を行いながら、サーバー側で通知を受信できます。通常使用するChromeには影響しません。設定後にファイルを保存して再登録すると、同じ受信情報は監視・通知設定・既存の受信記録を保ったまま、該当する受信接続だけを張り直します。Chromeのバージョンだけが変わった場合も同じ受信情報として更新できます。

Chromeの接続情報は同一プロファイル内の通知を共用します。X以外の通知がサーバーに届く可能性があることを、ファイル作成前とアップロード前に案内します。現在は対象外の通知を復号・保存・利用せず破棄します。受信確認によってブラウザー側で同じ通知を受け取れなくなる可能性があります。

## 移行と公開

本番データ変更、マイグレーション、本番デプロイは事前承認を得てから行います。以下は手順であり、実施済みを意味しません。

1. DBバックアップの取得と復元手順を確認し、既存Firefoxの受信設定・通知件数を記録する。
2. `migrations/20261110_add_x_subscription_browser_kind.sql`、`migrations/20261110_add_chrome_mcs_pending.sql`、`migrations/20261110_add_chrome_checkin.sql` を適用する。既存の受信設定を `firefox` として保持し、未確認のChrome受信IDと端末確認の予定を保存する。
3. 検証済みZIP `artifacts/angelic-setup/chrome-setup-0.1.0-chrome-preview.1.zip` をダッシュボードの配布物に含め、SHA-256とバイト数が `dashboard/lib/x-chrome-setup-download.ts` の値と一致することを確認する。
4. Webと受信ワーカーの両方で `X_NOTIFICATION_CHROME_ENABLED=1` を設定する。既存の `X_NOTIFICATION_RECEIVER_ENABLED=1`、処理ポリシー、暗号鍵、fleet leaseも必要。支援者限定で公開する場合は `X_NOTIFICATION_ROLLOUT=supporters` を維持し、対象者以外の登録が拒否されることを確認する。
5. 利用者自身が設定した実際のX通知で、登録画面、接続状態、投稿通知、Discord配信を確認する。接続確認だけで配送成功と判断しない。

## 停止とロールバック

Chromeの新規受付を停止するにはWeb側の `X_NOTIFICATION_CHROME_ENABLED` を無効にします。受信側の同設定を無効にすると既存Chrome接続も停止するため、影響する利用者へ案内し、未処理の受信記録と未確認IDを確認します。Firefoxの設定や共有登録枠を削除してはいけません。

旧版へ戻す場合は、Chrome接続を止めてDBバックアップを保持し、`automation_x_mcs_pending`、`browser_kind`、`chrome_checkin_*` 列を残す方法を優先します。未確認IDやChrome登録が残っている状態でテーブル・列を削除すると復旧情報やブラウザー種別、端末確認の履歴が失われます。削除が必要な場合は、影響するChrome登録の復旧方針とバックアップを別途確認してください。マイグレーションを戻すためだけに既存登録を削除しません。

## 検証の範囲

試験サイト、実FCM、隔離MariaDB、架空のユーザーと通知を使った一連の検証は成功しています。試験専用Chromeプロファイルで端末確認、設定用Chromeを開いたままのサーバー受信とChrome側の受信イベントがないこと、Chromeを開き直した後のファイル再登録、接続の再確立と次の通知ジョブ作成を確認しました。確認時刻は受信設定の版とともに保存し、次のワーカーに引き継ぎます。認証拒否または端末情報の変更時は購読を書き換えず、再登録待ちにします。Xの実アカウント、実際のDiscord配送、Chrome更新後の接続情報の長期的な寿命、および長時間の再接続は未検証です。受信ワーカーの接続数と負荷は `docs/operations/x-push-capacity.md` を参照してください。

隔離Linuxでも試験専用の購読情報を使い、端末確認と暗号化通知の受信を実FCMで確認しています。Linuxでのこの実接続試験はメモリ上の試験用ストアを使用しており、本番DBやDiscord配送の確認は含みません。
