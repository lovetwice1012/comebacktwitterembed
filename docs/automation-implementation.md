## 2026-09-22 監視管理・配信接続の到達点

### 追加した処理

- `destinations.js`: DM、既存Webhook検証、チャンネル一覧と専用Webhook作成/再利用。Botトークンだけを使い、利用者・Bot双方の権限を新しく取得して判定する。通常Webhook利用は所属・閲覧・送信、作成はさらにWebhook管理権限が必要。通知先の実体は不変で、名前・有効状態を編集可能。実体を変更する場合は新規通知先を作り監視に再割り当てする。
- `monitors.js`: 既存のauto_watch/price_watchテーブルを使うWeb CRUD。個人/共有のメタ情報は追加テーブルに分離し、既存登録には互換の公開範囲を適用。価格増減/価格上限/割引率を編集可能。監視の変更・停止・削除時に未送信分をキャンセル。アカウント・商品取得を既存ソースと集約し、Twitter新規登録は受け付けない。DiscordコマンドとWebで追加枠の同じトランザクションロックを使う。
- `queue.js`: 旧配信IDから重複排除キーを作り、ルール評価結果/適用版/イベント/通知先参照を永続化してから旧キューをroutedにする。下書き編集は予約済み通知を変えない。停止ルールを通常通知へ迂回させない。集約、件数制限、通知窓の再判定、期限、リース、送信ステップの確認をDBへ保存。sendingのリース切れはunknownになり自動再送しない。
- `runtime.js` / `transport.js`: readyから起動し、既存のautoWatch/priceWatchランナーを接続。復旧隔離とfleet leaseを配信前に確認。個別通知先を再認可し、Discord RESTは送信結果不明を再試行しない専用インスタンス。DMの自動展開はプロバイダーを直接利用。価格は観測時点の情報を保持。メンション無効化、テキスト/カード/展開、画像非表示・リンク、集約表示を処理。
- `history.js` / Web配信履歴: 判定経路、取得イベント、ルール版、予定・結果を閲覧できる。未送信の予約変更/キャンセル、送信実績のない失敗の再試行に対応。unknown/partialの一括再送は拒否。再判定して別のルール版に差し替える操作はまだ未実装。
- 既存ランナーの一括リース取得を、実処理直前の1件取得へ変更。早い段階で取った後続タスクのリースが待ち時間中に切れる問題を抑止。
- 自動通知の展開は4回のHTTP呼び出し（各最大1redirect）に制限し、事前に最大8単位を監視側の予算へ予約。枠待ちは送信失敗回数を消費しない。既存プロバイダーに設定されたAuthorization/Cookie/API-keyは、この処理だけ除去してゲスト範囲を保つ。通常の手動展開は変更しない。保守的な予約なので実アカウント数で遅延/枠配分の測定はさらに必要。
- WebhookトークンがAPI v10のURL・HTTPレスポンス・入力ログから漏れないように共通ログの除去も補強。
