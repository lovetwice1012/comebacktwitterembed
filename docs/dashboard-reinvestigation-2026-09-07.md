# ダッシュボード再調査と本番検証

2026-09-07 JST。更新後の本番ソース、レポートworker、MySQLを再確認し、詳細分析・サーバー分析・マーケ分析を実際に生成した。

## 再現した原因

レポートworkerがSQLへ付ける所有確認コメントに`/*cbte-report-query:<UUID>*/`というコロンを含めていた。PrismaがUUIDの一部を名前付きパラメーターとして扱い、通常の`?`パラメーターと混在したSQLとして拒否していた。これはSQLの実行時間以前の失敗だった。

また、更新後の詳細分析には、同じファセット表を全期間で何度も走査する処理が残っていた。数値メトリクスの最新観測、プロバイダーのマーケ軸、スキーマ観測数が重複していた。

## 反映した修正

- レポート識別コメントをコロンなしに変更し、`?`パラメーターと衝突しないようにした。
- 詳細分析、サーバー分析、マーケ分析は起動時・閲覧時・経過時間だけでは生成しない。ボタンの明示的なリクエストだけが生成を開始する。
- 前回成功したレポートは保持し、失敗時に空の結果へ置き換えない。
- ファセット、マーケ軸、関心、寿命、URL再利用、設定効果、信頼性の集計を、候補を先に絞ってから厳密なユーザー・サーバー数を求める形へ変更した。
- 数値メトリクスは、対象プロバイダーの登録済みキーを先に絞り、スキーマ表示だけが必要な観測数は単純な集計へ分離した。
- レポートworkerのSQL上限を120秒から300秒へ変更した。全体の生成予算は600秒のまま。明示的な生成のための上限であり、画面を開いただけではSQLを発行しない。
