# Adminサポートコンソール詳細設計案

2026-09-05。ユーザーが本方針を受け入れ、その後に実装・デプロイを依頼済み。本書は設計契約を保持する。実装済みの機能、検証した範囲、本番反映の残作業は[実装・検証状況](admin-platform-implementation-status.md)を参照。

画面の指標、集計単位、率の分母、外部サービスの数値、旧記録との比較は[指標と統計の詳細設計](admin-metrics-and-statistics-design.md)で具体化する。表示値から根拠となる要求・操作・観測へ移動できることを共通要件とする。

独立した管理・分析・障害対応基盤は[管理分析デーモン設計](admin-analysis-daemon-design.md)で具体化する。Bot停止時も利用できる管理Web、独立した障害台帳、診断・修復の実行主体は同設計に統合し、本書の調査項目・設定操作・証拠・受け入れ条件を引き継ぐ。通常ダッシュボードが稼働している場合は、そのadmin画面からも同じ管理コアの診断・調査・設定変更・修復操作を利用する。

## 1. 達成条件

ユーザーから受け取る情報は、従来どおりサーバーIDと大まかな時間帯とする。管理者はWebで対象事象を特定し、根拠を読んで原因を絞り込み、設定確認・変更を含むサポート操作を実行し、結果を検証できる。

Adminでは、実ID、名前、投稿内容、URL、入力、出力、エラー原文を照合できるようにする。匿名化、少数グループの詳細置換、列数による項目の脱落を適用しない。利用者向けプレビューとadminの返却処理を分け、admin用テストは個別事象への到達と情報の完全性を検証する。

「原因が追える」は、次の質問に証拠付きで答えられることと定義する。

1. Botは対象の入力を受信したか。受信・記録のどちらが確認できないのか。
2. どの設定・権限・対象条件で、どの処理を実行または見送ったか。
3. 実際にどの取得先へ何を送り、何が返ったか。どの再試行・切り替えを行ったか。
4. 取得、解析、出力生成、送信、後処理のどこで期待結果と異なったか。
5. その判断を支える原文・実値・コード位置はどこか。まだ確定していない点は何か。
6. Webで何を変更・再検証でき、変更後の結果はどうなったか。

## 3. 調査の単位と関連付け

一件の入力にoperation_id、内部の処理木にtrace_id、各段階にspan_idを発行する。ユーザーにこれらを求めない。

- 投稿受信、コマンド、ボタン、モーダル、自動展開ジョブ、Web管理操作を入口として登録する。
- 投稿内のURLごとに子処理を作り、同じURLが2回現れても出現位置・処理番号で区別する。
- 引用先、取得先の切り替え、添付取得、送信ステップ、再試行は子処理にする。
- ボタン操作・メディア配信は後続の別操作とし、元の出力・処理へ明示的な関連を持つ。
- 元投稿ID、Bot送信ID、interaction ID、ジョブIDを保存し、URLや時刻だけの結合に依存しない。
- admin操作の実行者と、調査対象・設定判定対象のユーザーを分けて記録する。
- メッセージ編集・再展開は入力の版を持つ新操作にし、元の記録を上書きしない。
- 旧データはID等で根拠のある関連付けを行う。時刻・URLだけの関連は「候補」とし、確定した処理木に混ぜない。

同時刻の障害は別の関連表示にする。例えばMySQL遅延が同時にあったことだけで、外部取得の失敗原因をMySQLとしない。

## 4. 必須の記録契約

### 4.1 全段階に共通する項目

`event_id / trace_id / span_id / parent_span_id / sequence / stage / kind / occurred_at / received_at / persisted_at / boot_id / build_revision / instrumentation_version`を持つ。

サーバー・チャンネル・ユーザー・元投稿・出力・interactionの実IDと、発生時点の名前を保存する。現在の名前は取得時刻を伴う別情報にする。各段階のdurationは同一プロセスの単調時計で測り、壁時計の前後だけで因果関係を決めない。

段階ごとに開始と終了を記録し、終了は成功・失敗・見送り・取消を明示する。開始だけ残ったものは未完了として扱い、成功や通常の失敗へ自動変換しない。入力イベントは重複排除キーを持ち、再取り込みしても増殖しない。

各判断は `decision_code / rule_version / evidence_event_ids / expected / observed / caused_by` を持つ。原因の連鎖は参照で表現し、単に最初・最後に発生したエラーを原因としない。

### 4.2 入力受信・待ち行列

Botが受信したメッセージの軽量な受付記録を、無視・URL検出・重複判定より前に作る。本文長、入力種別、Bot/webhookフラグ、認識結果を記録する。URLを含む展開候補やコマンド・ボタンには、正規化前の本文・引数・custom IDを保存する。通常会話の全文保存は調査の必須データに含めない。

受付ID、受信時刻、キュー投入・開始時刻、当時のactive/pending/上限、拒否理由、設定タイムアウトを記録する。受信したのにURL検出できなかった入力と、Botが受信したか不明な入力を分ける。

Gateway接続・切断・resume・無効セッション、プロセス起動と終了、最終heartbeatを時間軸へ重ねる。受信記録がないことだけで「Discordから届かなかった」と確定しない。

### 4.3 設定と権限

保存するのはDB値だけでなく、その処理が実際に使用した解決済み設定とする。

- DBの値、既定値、プロバイダー既定値、アカウント別上書き、自動判定の各出所。
- 適用した設定revision、スナップショットhash、キャッシュ取得時刻・無効化revision、実際のBot boot/build。
- 除外判定に使った投稿者ロール、対象チャンネル、NSFW・thread状態、取得元がcacheかDiscord RESTか。
- どのルールが何に一致したか。例：`disable.channel`に一致したチャンネルID、禁止ワードと一致位置、引用深度上限と現在深度。
- Botが行おうとした操作、その操作に必要な権限、対象チャンネルで評価した権限、評価時刻と取得元。
- ロールとchannel/member overwriteの入力を保存し、必要な場合に計算過程まで表示する。

Discordの50013だけでは不足する権限ビットや設定元を特定できない。失敗応答と、その時点で取得できた権限資料を両方表示する。後からRESTで取得した値を当時の権限と置き換えない。権限・API制約でBot自身が実施できない変更は、欠けている能力を具体的に表示する。

### 4.4 外部HTTP・解析

各試行にrequest_idを作り、サービスIDと実際の取得ホストを分ける。

| 分類 | 必須項目 |
| --- | --- |
| リクエスト | method、実URL・query、リダイレクト履歴、リクエストヘッダー・本文、使用した取得元・認証方式・設定版 |
| 時間 | キュー待ち、開始、応答ヘッダー受信、本文読込完了、解析終了、設定された期限。観測できないDNS/TLS等の内訳は未計測 |
| 応答 | status、response headers、Content-Type、Retry-Afterやrate-limit情報、応答本文、受信bytes、完全性 |
| 失敗 | timeout/abort/接続/本文読込/サイズ上限/HTTP/JSON/スキーマのどの段階か。例外name/message/code/stack/cause |
| 判断 | 期待した形式・必須フィールド、実際の形式・フィールド、採用した判定ルール |
| 次の処理 | 再試行番号・待機、切り替え条件、次のrequest_id、最終的に採用した応答 |

JSON・HTMLなど取得対象の本文は、正常時も保持期間内は参照可能にする。失敗した時だけ記録を始めても、直前の応答や正規化過程を復元できない。巨大な本文はストリームとして圧縮保存し、既存の取得サイズ上限に到達した場合はその事実と保存済み範囲を表示する。本文を読むために本来のstreamを二重消費しない。

`取得元が非公開等を示した`、`取得元が曖昧な展開不可応答を返した`、`Botが応答を誤分類した可能性`を区別する。曖昧な原文から「元投稿が削除済み」と断定しない。

### 4.5 取得結果と出力結果

extractorの結果を、配列の有無だけで判定しない。新しい契約に `fetch_outcome / parse_outcome / content_outcome / reason_code / evidence_refs / planned_outputs / planned_effects` を持たせる。

取得に失敗した後で案内メッセージを生成できても、取得は失敗、案内生成は成功と記録する。出力には通常コンテンツ・失敗案内・代替リンク等の役割を付ける。

正規化した取得内容、設定適用前の出力、設定適用後の出力、最終送信payloadを保持する。画像・動画・本文・ボタンが消えた場合は、削除したルールと対象要素を差分で説明する。メディアは元URL・bytes・形式・取得結果・保存先参照・hashを持ち、ログに毎回バイナリを重複格納しない。再現用のファイルが期限切れなら、再現可能範囲を表示する。

Twitter内の直接返信・削除・通知などは、明示的なeffectとして共通実行層から処理する。既存機能を維持しながら、プレビュー時にはeffectを実行しない構造へ移す。

### 4.6 Discord送信・後処理・配信

送信先、reply対象、step index、実際のpayload、添付一覧・bytes、必要権限、HTTP status、Discord code/message/errors、返された送信IDを各試行に保存する。構造化errorsは、どのpayloadのフィールドに対するエラーかリンクさせる。

初回失敗から添付を外して成功した場合は、初回の失敗も代替後のpayloadも残す。複数ステップは成功数・失敗数と各メッセージIDを持つ。元投稿削除・埋め込み抑制も別の結果を持ち、送信成功の裏に後処理失敗を隠さない。

送信後に応答の読込が失敗した場合はdelivery_unknownとする。応答がないことを未送信の証拠にしない。対応するDiscord送信ではnonceを利用し、観測した送信ID/Gatewayイベントも照合する。Discordのnonce重複抑止は短い時間窓であり、アプリ側の長期的な操作重複排除を代替しない。

ダウンロードURLは発行元trace・送信ID・取得ジョブと関連付け、自前HTTPへの要求受付、応答開始、サーバーで観測できる送出終了、stream error、切断を区別する。HTTP応答開始・ファイル読込終了・サーバーの送出終了のいずれも、端末での受信・保存・再生完了とは扱わない。リンクのアクセス者が発行時の操作ユーザーと同一だとは仮定しない。

DiscordのLinkスタイルのボタンはinteractionを送らない。翻訳・保存等のcustom_id付き非リンクボタンのinteraction受信と、URLを開いたクリックは別の事実とする。通常メッセージの閲覧・既読・本文やEmbedのURLクリックは公開Bot APIで非提供とし、計測指標に含めない。根拠は[指標設計のAPI精査](admin-metrics-and-statistics-design.md)に記載する。

### 4.7 最終結果の分類

| 表示 | 条件 |
| --- | --- |
| 完全成功 | 意図した出力のDiscord側での作成を確認し、必須後処理が完了 |
| 代替成功 | 本来の出力を変更してDiscord側の作成を確認。失敗案内だけの送信はここに含めず、取得失敗と案内結果を表示 |
| 部分成功 | 複数出力または必須後処理の一部が失敗 |
| 設定による見送り | 一致したルールと証拠が存在 |
| 取得対象の制約 | 取得元の応答に基づく制約。原文以上の理由を断定しない |
| 失敗 | 試行の失敗と因果関係が確認できる |
| 完了不明 | 開始はあるが終了がない、または配信成否が不明 |

統計用の追加情報取得が失敗しても、必要なDiscord出力の作成を確認できていれば出力成功を維持し、補助処理失敗を別表示する。成功はBotが行うべき処理の完了であり、人の閲覧・画面描画・読了を意味しない。各件数には集計単位と分母を表示し、URL・送信ステップ・入力件数を混ぜない。

## 5. Web画面の具体仕様

### 5.1 サーバーのサポート画面

上部にサーバー名・実ID・Bot参加状態と、調査時間帯を固定する。設定編集のみの場合は時間帯不要。JSTを明示し、前後30分/1時間/3時間、前後の同じ長さの範囲へ操作できる。

「事象一覧」「設定・権限」「自動展開」「保存・容量」「アクセス」「稼働状態」を同じサーバーの文脈で開く。ユーザーID等は一覧から選択可能とし、問い合わせの必須項目にしない。条件と選択事象はURLに保存し、ページ再読込・戻る操作でも維持する。

一覧列は、発生時刻、チャンネルと投稿者、入力URL/操作、最終結果、失敗段階、具体的理由、所要時間、証拠の完全性とする。異常を目立たせつつ正常な比較対象もページ送りで全件閲覧できる。生の全項目と管理者用の調査データをダウンロードできる。

### 5.2 一件の調査画面

最上部に「何が起きたか」「原因を裏付ける証拠」「未確定事項」「次にできる操作」を置く。最重要のエラー本文・取得先・対象投稿を折りたたみ内だけに置かない。

画面内の領域は、元入力、処理の経過、HTTP試行、設定と権限、出力差分、例外原文、関連障害、Web操作履歴とする。各領域から相互に該当箇所へ移動できる。

経過は一覧表で `順番 / 開始 / 所要 / 段階 / 対象 / 結果 / 判断の根拠` を表示する。引用や再試行は子行として示す。例外から対応するHTTPの原文や送信payloadへ一操作で移動する。

原文表示は全文検索、整形/原文切替、copy、保存を備える。切り詰め・欠落・未取得のフィールドには理由と元サイズを表示し、単なるハイフンにしない。情報量が多い場合の折りたたみは閲覧上の整理に限定し、取得自体を削らない。

### 5.3 原因候補と根拠

原因候補は任意のスコアだけで出さず、ルールの一致条件と証拠を示す。

| 表示する判断 | 必要な証拠 | 断定してはいけないこと | Webでの次の操作 |
| --- | --- | --- | --- |
| 取得先がrate limitを返した | 実取得先、429等の応答、本文・headers、試行履歴 | サービス全体が停止した | 取得元別の同時刻比較、現在の再取得 |
| JSON解析失敗 | 該当応答、Content-Type、parse error、実行コード版 | 元投稿が存在しない | 保存応答を再解析、現在の応答と比較 |
| チャンネル除外に一致 | 実効設定、対象ID、一致ルール | 現在の設定も同じ | 該当設定編集、変更後の判定プレビュー |
| Discordが権限不足を返した | code、実行操作、対象、当時の権限資料 | 50013だけから特定権限の不足を決める | 現在の権限再取得、設定/overwrite比較 |
| 添付を除いて代替送信した | 初回payload・失敗、代替payload・送信ID | 添付を含め完全成功 | メディア再取得、出力確認、対象ステップの再送 |
| 設定保存後も旧版で実行された | 保存revision、実処理の適用revision | 常にキャッシュ不具合が原因 | 現在の反映状況確認、再読込、再評価 |
| 実行待ちで期限切れ | 受付・キュー時刻、上限、拒否event | 外部APIがタイムアウトした | 同時刻の待ち行列確認、明示的な再実行 |
| Botプロセス終了前後で未完了 | 開始event、boot履歴、最終heartbeat/終了資料 | 必ず未送信、必ずOOM | OS/Botログ閲覧、送信結果照合、必要な復旧操作 |

事実・原因候補・未確認事項のラベルを分ける。全体比較では同じホスト、API経路、例外指紋、ビルド版、設定条件で絞り、単なる同時発生と同じ原因を分ける。

### 5.4 URL実行検証ページ

adminに「URL実行検証」を追加する。通常ダッシュボードの/admin/url-inspectorと独立管理Webの対応ページを候補とし、両方で同じ実行API・履歴・証拠を利用する。

管理者がURLを貼り付けて実行すると、実際の取得元へアクセスし、プロバイダーの解析と出力生成を行い、展開結果とAPI応答を並べて表示する。現在のsettings-preview.tsにある固定サンプルを、実際の取得結果として表示しない。

#### 入力と実行

| 入力 | 初期動作 |
| --- | --- |
| URLまたは元メッセージ本文 | 必須。Botと同じ認識・正規化で対象URLとproviderを示す。複数URLは個別の根処理として追跡 |
| サーバー | 任意。選択時はそのサーバーの実効設定を使用。サポート画面から来た場合は引き継ぐ |
| チャンネル・対象ユーザー | 条件依存の再現に使う。権限、ロール、NSFW等の資料と取得時刻を表示 |
| 設定 | 既定値、現在のサーバー設定、保存済み実行の設定から選択。今回だけの上書きは保存せず比較可能 |
| 取得方法 | 初期値は「外部APIを再取得」。アプリの取得キャッシュを使う通常動作、保存済み応答の再解析も選べる |
| 取得元 | 通常の自動選択を初期値とする。providerが対応する場合は登録済み取得元を個別指定して比較 |

サーバー未指定でも、既定設定による外部取得・解析・出力生成を利用できる。チャンネル・ユーザーがないと評価できない除外や権限は未評価と明示し、実際のサーバーでの完全再現としない。問い合わせの元事象を選ぶ場合は当時の入力・設定・対象情報を引き継ぎ、当時と現在のどちらを使うか表示する。

「外部APIを再取得」はアプリ内の対象キャッシュを使わず、新しいHTTP試行を作る。外部CDN等のキャッシュまで無効にできるとは表示せず、応答ヘッダーを記録する。URLに任意のcache-busterを加えて、元の要求内容を変えない。「通常動作」でキャッシュを利用した場合は、その由来と保存時刻を示し、新しいHTTP応答があったように表示しない。

実行はボタンを押した時に開始する。入力変更やページ再読込で勝手に外部取得を繰り返さない。実行ごとにrun_id/action_id/trace_idを発行し、入力、設定版、取得モード、workerのコード版、実行日時を保存する。

#### 結果画面

上部に入力URL、判定provider、実行条件、実行状態、取得時間、出力生成結果を固定し、左右に次の内容を表示する。

| 左：展開結果 | 右：API応答・処理の根拠 |
| --- | --- |
| 実際の取得結果から生成した本文・Embed・添付・ボタン | 実際に送ったmethod、URL、headers、body |
| 複数送信ステップを順番と返信関係付きで表示 | 各取得先のstatus、response headers、Content-Type、本文 |
| 取得した画像や動画の参照、添付名・bytes・形式 | primary/fallback、redirect、retry、引用取得等の試行一覧 |
| 設定で省略した項目と理由 | 正規化した内容と元応答の対応、解析例外・stack・cause |
| 送信前payloadの全文 | 適用設定・一致ルール・処理段階ごとの時間 |

全体の処理経過を下部で表示し、選択した出力から対応する取得/解析資料へ、選択したAPI応答から生成結果へ移動できる。補助情報取得は進捗を別に示し、未完了を空の正常結果にしない。

JSONは整形表示と原文表示、全文検索、copy、保存を備える。HTMLやテキストの応答は実行せず原文として表示する。バイナリ応答は種類・サイズ・hashと保存資料への参照を表示する。本文の途中までしか取得/保存できなければ元サイズ・保存範囲・理由を示す。

API取得に失敗した場合も、取得済みのHTTP応答と例外を表示する。展開結果が空の場合は「条件で見送り」「対象制約」「取得失敗」「解析失敗」「文脈不足」を区別する。右側の資料まで汎用エラー画面で消さない。

Webのプレビューは送信payloadを可視化した結果であり、Discordクライアントの描画と完全に同一とは扱わない。特にDiscord側の添付処理・外部メディア取得・表示制限は別に確認が必要。API応答とpayloadは実データとして閲覧可能にする。

#### 設定比較と実送信

「同じ取得結果で設定だけ変更」を用意し、外部応答を固定して出力差分と判定理由を比較する。「もう一度取得」は新しいrunを作り、前のrunとのHTTP本文・正規化データ・出力の差分を表示する。過去の証拠を上書きしない。

初期動作は外部取得・解析・出力生成まで。Discordへの投稿、元投稿の削除/抑制、保存、通知等はplanned effectとして表示し、実行しない。既存extractor内の直接返信・削除・通知・タイマーも、共通effect実行層へ分離してからこのページに接続する。

Discord側の受付まで確認したい場合は、別の「Discordへテスト送信」を利用する。サーバーIDとチャンネルIDを直接指定し、共通action APIから実行し、返されたmessage ID、REST応答、失敗原文を表示する。指定先送信は次の5.5の共通機能を使用する。元投稿への削除/抑制等はテスト送信に暗黙で含めない。送信成功を閲覧・既読として表示しない。

#### 実行主体と履歴

実行は管理デーモンの分析workerから、Botと共通のURL認識・provider・出力生成ロジックを呼ぶ。通常ダッシュボードのNextプロセスに長い取得処理を持たせない。Botが停止していても対応版workerで実行できる。Bot本体とworkerのbuildが異なる場合は、その差を表示する。

APIは既存のsupport/actionsにurl.inspect、url.reparse、url.compare、url.test_send等の型付き操作を追加し、出力、HTTP試行、artifact、実行経過を同じrunから取得する。URLが未対応なら認識段階で理由を返し、別providerの結果やサンプルで埋めない。

実行履歴をURL・サーバー・provider・日時・結果から検索し、run_id付きの管理者用リンクで再度開けるようにする。サポートの元事象・incidentへ関連付けられる。画面切断時も同じactionの状態を追い、再接続で外部要求やDiscord送信を二重実行しない。

検証runはtrigger_type=diagnosticとし、通常の利用者・要求・成功率には混ぜない。発生したHTTP要求、消費時間、資源、失敗は診断処理の技術指標として残す。実行期限、同時数、本文サイズは既存の診断予算で管理し、超過時も途中の証拠を閲覧可能にする。

### 5.5 サーバー・チャンネルIDを指定して送信

adminに「指定先へ送信」を追加する。通常ダッシュボードの/admin/send-messageと独立管理Webの対応ページを候補にする。サーバーID・チャンネルIDの直接入力を必須の操作方法として用意し、候補リストや管理者自身の参加サーバー一覧だけに依存しない。

| 項目 | 仕様 |
| --- | --- |
| サーバーID | 数字の文字列として扱う。Botが対象を取得できるか確認し、サーバー名とIDを表示 |
| チャンネルID | 数字の文字列として扱う。実際の所属guildを取得し、指定サーバーとの一致を検証。名前・種類・権限状態を表示 |
| 送信内容 | URLを取得・展開して送信、URL実行検証の保存済み出力を送信、本文・Embed・添付を指定して送信 |
| 設定 | URL展開は送信先サーバー/チャンネルの設定と条件を適用。実効値・版・未評価の条件を表示 |
| 返信先 | 任意のmessage ID。指定チャンネル内の対象として確認し、見つからなければエラーを表示 |
| 目的 | 通常のサポート送信と診断用テスト送信を区別 |

本文にURLを含めてそのまま送る場合と、URLをproviderで展開して送る場合を明示する。Bot自身の投稿が自動展開されることを前提にせず、展開モードでは送信前に共通provider処理を実行する。

画面内で「送信先を取得」「内容を作成/プレビュー」「送信」を行う。送信ボタンの近くにサーバー名/ID、チャンネル名/ID、本文、出力ステップ数、添付、返信先、実際のメンション対象を表示する。IDはJavaScriptのnumberへ変換しない。

指定サーバーとチャンネルの不一致、取得不能、権限不足、直接メッセージを送れない種類は具体的な理由を返す。thread等はその種類に必要な条件を確認する。別チャンネルへの代替、返信の通常投稿への変更、threadの作成/再開を暗黙に行わない。

URL実行検証からは「この結果を指定先へ送信」でrun_idと出力を引き継ぐ。送信先や設定を変更した場合は、元の検証条件との差を表示し、新しい条件での出力を再評価する。保存済みのpayloadそのものを検証送信するモードでは、再評価しないことと元の設定を明示する。どちらも元の検証runを上書きしない。

本文・Embed・添付は通常フォームで編集し、必要なら送信payloadのJSONも確認できる。添付ファイルの実体・期限・サイズと出力形式の条件を検証する。メンション通知は初期値で無効とし、必要な対象を指定して送る。元投稿削除・埋め込み抑制・保存等の副作用を通常送信に混ぜない。

実行結果はステップごとの受付状態、作成されたmessage ID、Discordメッセージへのリンク、送信時刻、HTTP status、Discord code/message/errors、所要時間を返す。複数メッセージの一部だけ成功した場合も、成功済みIDと未完了の対象を残す。送信成功はDiscord側の作成確認であり、閲覧・既読とは扱わない。

実行は共通action/executorから行う。稼働中Bot側の送信処理、または対応する独立REST workerを使い、認証・到達性・権限・rate limitを確認する。独立REST workerを用意した構成ではBotのGateway接続が停止中でも実行可能とする。利用できる実行経路とその状態は画面に表示する。

message.sendを共通操作とし、URL検証のテスト送信も同じ実行処理を使う。対象ID、payload、適用設定版、実行者、目的、参照run/incidentをactionへ保存する。二重クリック、通信切断、worker再起動は同じaction IDから結果を照合し、送信成否不明を未送信として盲目的に再実行しない。

サポート送信はtrigger_type=admin_operation、テスト送信はdiagnosticに分類する。どちらも一般利用者の操作件数には加えず、Discord送信の実負荷は技術指標へ残す。問題の元要求に対応する再送でも、過去の失敗結果を成功へ上書きせず、新しい対応actionとして関連付ける。

## 6. 原因を追える完成形の例

以下は画面仕様を示す架空の事例であり、本番で確認した障害ではない。

### 例A：Xのリンクに反応しない

問い合わせ入力はサーバーIDと21時ごろだけ。

1. 21:04の投稿を一覧から特定。受付済み、キュー待ち8ms、除外なしと表示。
2. 取得元Aは502とHTMLを返した。原文にgateway error。取得元Bへ切り替えた根拠も表示。
3. 取得元Bは200だがHTML。JSON解析に失敗し、エラー位置・本文・実行コード版を表示。
4. `failure_display_policy=silent`が適用され、失敗案内を送信しなかった。
5. 原因欄は「両取得元から必要なJSONを得られなかった。無反応に見えるのは失敗時のsilent設定による」とし、各根拠へリンクする。
6. Webで保存応答の再解析、取得元ごとの現在の再取得、失敗時表示設定の変更、結果プレビュー、再送まで行う。

### 例B：画像だけ表示されなかった

取得した画像4件、生成payloadの画像4件、初回添付送信の失敗を順番に表示する。原文がサイズ超過を示した場合にのみ、その原因と判定する。次に添付を外してURLへ変更した差分と、成功した送信IDを示す。

これにより、「取得できなかった」「設定で画像を除いた」「添付送信で失敗した」を区別する。Webから該当メディアの取得確認と形式変更、プレビュー、対象ステップの再送を行う。

### 例C：設定を直したのに動作が変わらない

DB保存revision 124と、問題の処理が使ったrevision 123を並べる。Botの適用ACK、cache取得時刻、boot IDを表示する。原因候補は旧設定の適用であり、無効化処理のどこが遅延・失敗したかは関連eventから追う。Webから再読込し、ACKと新しい再評価結果まで確認する。

## 7. Webでの設定・対処・再検証

既存の設定操作を維持・拡充し、全設定の通常フォームとJSON編集、既定値・実効値・版・履歴を提供する。DB変更、監査、設定revision/反映要求は同じトランザクションに置き、Botは読み直したrevision/hashとboot IDをACKする。「保存済み」「Bot反映待ち」「反映確認済み」「反映失敗」を表示する。更新には期待revisionを持たせ、古い画面からの更新で別の変更を消さない。

全サポート操作はカタログ化する。設定確認・変更・初期化・コピー・復元、対象別制御、自動展開の一覧/登録/削除/送信先/枠、保存データの一覧/表示/削除/容量/上限、委任アクセス、翻訳・保存・メディア形式変更・再展開・Bot投稿削除を含む。処理に必要な稼働状態・キャッシュ再読込・ジョブ状態確認・再実行もWebで扱う。Discordコマンド・ボタン・手作業と対応付け、未対応の操作を明示して埋める。

| 操作モード | 使用する資料 | 実行結果 |
| --- | --- | --- |
| 保存資料の再解析 | 当時の入力・HTTP応答・設定スナップショット | 現在のコードで解析・判定・生成し、当時と比較。ネットワークや投稿副作用なし |
| 設定変更のプレビュー | 保存資料と提案設定 | DBに保存せず、一致ルールと出力差分を確認 |
| 現在の状態で再取得 | 現在の外部取得元・明示した設定 | 現在の応答を新しい操作として保存。自動送信なし |
| 再送・再展開 | 指定した送信先・payload/対象URL・設定 | 実操作として実行し、送信IDと段階別結果を確認 |
| 保存済み設定の復元 | 指定revisionと現在との差分 | 新revisionとして保存。既存履歴を上書きしない |

保存資料の再解析は当時のコードそのものの再実行ではない。実行コード版を表示し、入力・設定・応答のどれを固定し、どれを変えたかが必ず分かるようにする。必要な資料や添付が残っていなければ、再解析できる範囲を明示する。

前述のextractor内副作用を分離するまで、既存extract関数をそのまま「プレビュー」に呼ばない。返信・削除・保存・通知・遅延タイマー・統計増分もeffectとして制御する。テスト用解析を通常の利用統計に混入させない。

Web操作はaction_idとidempotency keyを持ち、受付・実行中・成功・部分成功・失敗・結果不明を永続化する。HTTP応答が途切れても同じaction_idから状態を確認できる。ジョブのlease切れは外部操作失敗の証拠にしない。再送が二重投稿になり得る場合は、まず送信済みIDやnonceの照合結果を表示し、実行対象を具体化する。

## 8. Botとダッシュボードをつなぐ実装構成

Discord操作とWeb操作は共通の業務処理を呼ぶ。ダッシュボードがBotモジュールをrequireしただけで、稼働中BotのDiscord clientやキャッシュを共有できるとは扱わない。

通常の構成は `通常ダッシュボードの管理者確認済みAPIまたは独立管理Web → 管理コアの永続化したaction → 操作に対応するworker/executor → 共通業務処理 → 結果event/ACK → 両管理画面` とする。Webはユーザーになりすましたinteractionを生成せず、管理者actor、対象ユーザー、設定判定の文脈を明示する。どちらの画面から実行しても同じaction ID・排他・期待revision・履歴を使い、画面切断時に操作を二重実行しない。

DB停止やBot停止そのものの調査には、通常DBから独立して読めるローカル診断ログ・退避記録・プロセス状態を用意する。Bot停止中もダッシュボードが診断資料を読める構成にする。OSログ/サービス操作が必要な環境では、対象サービスと操作を定義した実行口を設け、操作ごとの結果・期限を返す。調査資料取得のためにSSHへ移動する導線を通常手順にしない。

新しいAdmin APIの案は以下。

- `GET /api/admin/support/search`：guild、from/to、provider/channel/user、outcome、cursor。
- `GET /api/admin/support/operations/:id`：段階、原因候補と根拠、入力/出力、snapshot、関連action。
- `GET /api/admin/support/artifacts/:id`：本文・例外・payloadの全文と完全性。
- `GET /api/admin/support/related`：同条件の成功、同取得先の失敗、同じbuildの事象。
- `GET /api/admin/support/capabilities`：全操作と対象に対する利用可否・理由。
- `POST /api/admin/support/actions`、`GET .../actions/:id`：プレビュー・変更・再取得・再送等。
- `GET /api/admin/support/recording-health`：記録遅延、退避、欠落、保持範囲。

各応答にread status、as-of、watermark、coverageを持つ。検索0件と取得失敗を同じレスポンスにしない。APIでadmin権限を確認し、識別子や少数データを隠さないadmin専用の返却契約にする。

## 9. 記録の永続化と検索性能

論理的な保存対象を、operation一覧、段階event、HTTP試行、証拠artifact、設定/権限snapshot、管理action、runtime eventに分ける。実テーブルの統合可否はマイグレーション設計時に決める。大きな本文を一覧テーブルや集計行へ埋め込まない。

一覧は `guild_id + started_at + operation_id`、詳細は `trace_id + sequence`、HTTPはrequest_id、送信はmessage_idで引く。既存のguild/time索引も確認し、重複索引は追加しない。検索結果のoperation IDへ絞って証拠を読み、全体の巨大集計と結合してから絞り込まない。

カーソルは時刻だけでなくIDとの組を使う。同時刻の事象を落とさない。発生時刻の範囲は開始を含み終了を含まない。到着が遅れたeventはwatermark更新と再検索で反映し、検索中に追記された記録の存在を表示する。

サポート検索に専用の実行枠と期限を設け、全体集計の構築キューに待たされないようにする。詳細統計は正確な件数・完全なレポートを維持し、全件COUNTや重複集計を反復しない保存・クエリ設計にする。件数から移動する実一覧と集計の時点を揃える。

記録はメモリキューだけに依存せず、追記形式のローカル退避からDBへ冪等に取り込む。DBへの取り込み成功が確認できるまで退避を消さない。部分成功後の再取り込みもevent_idで重複排除する。記録を無制限にメモリへ積まない。

プロセスクラッシュ・DB停止・ディスク満杯のテストを行い、耐久化前に失い得る時間窓を測定する。「必ず欠落ゼロ」とは表示しない。退避容量・最終同期・欠落区間は独立した記録健全性情報で表示する。既存のshiftや握りつぶしによる無通知の消失をなくす。

保持期間の初期案は、通常調査に必要な入力・HTTP応答・設定・出力・eventを同じ最低30日に揃える。問い合わせ調査として保全した操作は依存artifactも含め保持期限を延長する。実際の件数と圧縮後容量を測定し、90日等への延長は容量設計と合わせて決める。大きなメディア本体の期限と、診断資料の期限を個別に表示する。

性能の暫定受け入れ目標は、1サーバー24時間の最初の100件と一件の詳細をそれぞれP95 2秒以内。未計測の目標値であり、実データ量・同時集計・障害時の退避量を含むベンチマークで判定する。サンプル削減や少数秘匿で目標を達成したことにはしない。

## 10. 実装順序と対応範囲

1. adminの全項目表示、匿名化/少数詳細置換の解除、日時・ページ送り、取得失敗の明示、設定フォーム・履歴を先行する。既存記録を使えるようにする。
2. 受付・処理ID・永続退避・結果契約を共通基盤として実装する。XについてHTTP切り替え、展開不可、失敗案内、禁止ワード、引用、再送を一通りつなぐ。
3. 同じ記録契約を全プロバイダー、コマンド、ボタン、非同期処理、メディア配信へ展開する。プロバイダーごとに受付/判定/HTTP/解析/出力/送信/後処理の対応表を公開し、未対応を正常と表示しない。
4. Webの操作worker、設定ACK、プレビュー、再取得、再送と既存サポート操作全体を実装する。Xだけの対応で完了にしない。
5. 原因候補、同条件比較、詳細統計からの掘り下げ、記録健全性と性能を検証する。

## 11. 受け入れ試験

各試験では操作IDを管理者へ事前提示せず、サーバーIDと前後1時間程度の範囲からWebで事象を探す。期待した証拠を表示でき、対処と結果確認までたどれることを検証する。

| シナリオ | 合格条件 |
| --- | --- |
| provider無効、チャンネル/ロール除外、Bot投稿抑止 | 受付記録、実効値、一致した対象、見送りが見え、設定変更と再評価が可能 |
| URL未認識、重複、キュー満杯/期限切れ | 異なる理由として検索でき、処理されなかった場所を説明できる |
| 一次取得元HTML、二次取得元JSON異常 | 両方の実取得先・status・本文・切替条件・parse例外が表示される |
| 展開不可の曖昧な応答 | 原文と分類理由が残り、削除/非公開を根拠なく断定しない |
| 取得失敗後に失敗案内を送信 | 取得失敗と案内送信成功が別表示され、成功率の分母・分子も一致 |
| 添付送信失敗後のURL代替 | 初回失敗、payload差分、代替結果、送信IDを追える |
| 複数出力の一部失敗、元投稿削除/抑制失敗 | 各結果が残り、全体を完全成功にしない |
| 権限不足、threadの制約 | 操作対象・Discord原文・当時の資料・現在の資料を分けて表示 |
| 送信後の応答解析失敗 | 成否不明を維持し、二重送信せず照合結果を確認可能 |
| 設定保存後に旧版が適用 | 保存revisionと適用revisionの差、ACK、再読込結果が見える |
| 元投稿削除、ユーザー退会、名前変更 | 保存済み入力と当時の名前・IDから調査可能。現在のDiscord参照失敗で全体を失わない |
| ボタン失効、ダウンロード期限切れ/途中切断 | 元出力・interaction・取得ジョブへ遡れる。自前HTTPの観測状態をクリック・閲覧・端末保存の証拠にしない |
| DB停止、部分INSERT、Bot強制終了 | 退避から重複なく復元。未完了・欠落範囲を可視化 |
| 長い本文・複数cause・大きいJSON | 必要な原文を全文閲覧でき、部分保存でも構造が壊れない |
| 同時刻複数URL、遅延event、ページ送り | 別事象を混ぜず、IDで全件に到達。遅延記録を更新して確認 |
| プレビュー実行 | Twitterの直接副作用を含め、投稿・削除・保存・通知・利用統計増分が発生しない |
| 操作HTTP切断、二重クリック、worker再起動 | actionの状態と結果を再取得し、外部操作を重複実行しない |
| 管理者1人・利用者向け画面併存 | adminは実ID/全証拠を取得。利用者向けの別契約がadminへ誤適用されない |
| 実URLを貼り付けて検証 | 実際のprovider取得を実行し、その応答から生成した出力とHTTP原文を同じrunで表示 |
| HTML/429/timeout/解析失敗 | 展開できなくてもHTTP試行と失敗根拠を表示。サンプルや汎用エラーだけに置き換えない |
| サーバー未指定・対象ユーザー未指定 | 既定値と未評価の条件を明示し、実サーバーでの完全再現としない |
| 設定だけ変更・外部再取得 | 固定した資料と変更した条件を区別し、出力差分・HTTP差分を確認可能 |
| URL検証とテスト送信 | 通常の検証ではDiscord副作用を発生させず、明示した送信操作だけにmessage ID/REST結果を記録 |
| URL検証中に通常ダッシュボード停止 | 独立管理Webから同じrunと保存したAPI応答を閲覧可能 |
| サーバーID・チャンネルIDの直接指定 | 解決した対象を表示し、指定先へ送信。作成されたmessage IDとREST結果を返す |
| サーバーとチャンネルの不一致・権限不足・無効な返信先 | 指定外へ代替送信せず、失敗理由を表示 |
| 指定先を変更して展開結果を送信 | 設定・文脈の差を示し、再評価結果と保存済みpayload送信を区別 |
| 指定先送信の部分成功・通信切断 | 成功済みIDを保持し、未完了/成否不明を区別して二重送信を防ぐ |

過去の未記録データや期限切れ資料は後付けで復元できない。各証拠に「既存データ」「新記録対応後」「推定の関連」「取得不能」を表示し、新仕様の適用前から完全な証拠があるとは扱わない。
