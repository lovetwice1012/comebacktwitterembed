# 非Twitter自動監視

`/autoextract watch` は、公開プロフィールを定期確認して新しい公開コンテンツを通知します。通知先はDM、既存Discord Webhook URL、または選択チャンネルにBotが作成するWebhookから選べます。取得した新着は共通配信キューと機械チェックを通ります。既定ではタイトルとURLを投稿し、サーバー内の展開はBotの通常のURL展開機能に任せます。カスタムルールの表示形式で、通知側が展開結果を直接送る方式にも変更できます。

登録前に内容・権利・通知先を確認し、`responsibility: true`を指定してください。Botは機械的な違反検知を行いますが、適法性・安全性を認定するものではありません。確認項目が出ない古いコマンド定義は、デプロイ時のコマンド再登録が必要です。

新着自動展開の登録は寄付者限定です。DiscordとWebの両方で、利用者のDB上の`users.is_donor = 1`を確認します。追加枠の数や管理者権限だけでは登録できません。停止した監視の再開、監視対象・通知先の変更にも同じ条件を適用します。既存の登録は削除・一斉停止せず、一覧・停止・削除を維持します。寄付者の登録にも既存の登録枠上限が適用されます。

Twitter/X の自動展開は現在技術的に対応できず、`/autoextract add` 登録は停止中です。本番に残っていた旧登録は、利用者の指示に基づきバックアップして削除します。共有Webhook・利用者・寄付者情報は削除しません。

## アダプター構成

共通の登録・DB lease・レート制御・Webhook 配信は `src/providers/autoWatch/` にあります。各プロバイダーは `src/providers/<provider>/autoWatch.js` の任意アダプターです。新しい対応先には `id`、`normalizeSource`、`fetch` とレート方針を持つ同名ファイルを追加します。

| Provider | ゲスト取得経路 | 通常の最短確認 | 全体の最短間隔 |
| --- | --- | ---: | ---: |
| YouTube | 公開 Atom feed / 所有者確認済み uploads 一覧 | 30 分 | 5 秒 |
| GitHub | 未認証の public account events API | 6 時間 | 2 分 |
| Twitch | ゲスト表示の公開チャンネル状態 | 15 分 | 5 秒 |
| Spotify | ゲスト表示の artist discography | 2 時間 | 5 秒 |
| Pixiv | 公開プロフィールの作品一覧 | 30 分 | 2 秒 |
| BOOTH | 公開ショップの商品一覧 | 30 分 | 2 秒 |

GitHub の未認証 REST API は 60 requests/hour なので、本機能は 30 requests/hour しか予約しません。ユーザー指定の 6 時間遅延もこの最短値です。GitHub が返す残量ヘッダーを見て、残量が半分以下になった時点で reset 時刻までこの機能からの呼び出しを停止します。

YouTube の Atom feed、Twitch/Spotify のゲスト表示、Pixiv/BOOTH の公開ページには、この用途に対応するアプリ単位の公開数値枠がありません。そのため API key や OAuth token を要求せず、上表の共有ペーシング、ETag/Last-Modified、初回ジッター、単一ワーカー、429 の `Retry-After`、指数バックオフを併用します。公開ページ側の仕様変更や WAF による 429 を数学的に完全排除できるものではありませんが、同一アカウントを購読者ごとに取り直す設計にはしません。

## 取得と解析の分離

公開ページ全体への固定容量制限はありません。全6プロバイダーの正常応答をストリームで読み、投稿の判定・通知に必要な情報を保持し、不要な画像データ・script・JSONフィールドを読み捨てます。必要なリリース本文などを容量の都合で黙って省略しません。

本番の取得・解析はBot本体と別のプロセスで実行します。Linuxではsystemdの専用サービスに
RAM 512MiB、CPU 1コア相当、プロセス数・実行期限・書き込み制限を設定し、
アドレス空間も2GiBに制限します。古いcgroupでswapの計数が使えない場合も
アドレス空間制限を確認してから取得します。WindowsではPython経由でJob Objectを設定し、
取得プロセスのメモリ・CPU・実行時間を制限します。

接続先は対応サービスのHTTPSに限定し、リダイレクトごとに再確認します。DNSで得たアドレスを検査して同じアドレスへ接続し、プライベートIP・localhost・クラウドのメタデータ宛てには接続しません。HTTPの期限と既存の取得間隔・レート制御も維持します。

必要メタデータにも有限の処理資源があります。隔離処理の資源不足や過大な構造では、
監視・通知先を無効にせず再試行します。成功するまで保存済みカーソルと初回基準を更新せず、
過去投稿の再通知や部分的な基準保存を防ぎます。カスタムHTTP期限を使う場合は、
その期限に応じてsource leaseを延長します。

## 動作上の境界

- 最初の確認では現在見えている ID をカーソルに保存するだけで、過去分を投稿しません。大量の Pixiv/BOOTH 履歴では数値 ID の初回 high-water mark も保存し、カーソル窓の外にある古い ID も履歴として抑止します。
- 同じ `provider_id + source_key` は全購読者で共有し、上流リクエストは一度だけです。
- URL の発見、Webhook ごとの配信、配信済み判定は別テーブルで永続化します。再起動時も重複送信を避けます。
- 送信前の429は待機後に再試行します。一部送信済み・送信結果不明の通知は、一括の再送で重複させません。
- フェイルオーバー復旧中は復旧前の未送信配信を quarantine し、外部送信しません。

`config.json` へプロバイダーの OAuth token、API key、client secret を追加する必要はありません。必要なら公開クロールを一時停止するためだけに次を設定できます。

```json
{
  "autoWatch": {
    "enableGuestCrawls": false,
    "httpTimeoutMs": 20000
  }
}
```

`enableGuestCrawls` を `false` にすると Pixiv/BOOTH の公開クロールのみ停止します。YouTube、GitHub、Twitch、Spotify の既存登録は削除されず、再度 `true` にした後に再開します。

Webhookを自動作成するチャンネル方式では、押した人とBotの双方に対象チャンネルの「Webhookの管理」権限が必要です。既存Webhook URLは、登録したサーバーに属するものだけを受け入れます。

審査の保留・管理者承認はありません。機械チェックの違反は除外、検査処理の故障は失敗として履歴に記録します。静穏時間・指定時刻・レート制御による配信待ちは維持します。詳細は[機械判定方針](automation-mechanical-policy.md)。

## 展開方法の選択

カスタムルールの「文章・表示」で展開方法を選べます。
ルール未適用の監視、新しいルール、表示指定のないルールは `normal` が既定です。
保存済みの `expanded` など、明示された表示形式は維持します。

| 表示形式 | 自動通知の投稿 | Botの通常展開 |
| --- | --- | --- |
| 通常機能に任せる（`normal`） | タイトル＋URL。カスタム文面も利用可能 | サーバー内のWebhook投稿を通常処理で展開 |
| 展開結果を直接送る（`expanded`） | 通知側で生成した展開結果＋文面 | 同じ通知の再展開を抑止 |
| カード／文章／URLだけ | 指定された表示 | 同じ通知の再展開を抑止 |

通常機能に任せる場合、展開の有効・無効、画像の表示、送信方法などは
サーバーの通常のプロバイダー設定に従います。
通知ルールの画像設定は通常展開へ引き継ぎません。
DMは通常のURL展開の対象外なので、タイトル＋URLだけを送ります。
DMで展開結果も受け取りたい場合は、カスタムルールで「展開結果を直接送る」を選びます。
価格通知で文面を変換していない場合は、観測価格を含む既存の通知文を保持します。

通常機能に任せるまとめ通知も、まとめた文面とURLを投稿し、通常のURL認識処理へ渡します。
「展開結果を直接送る」のまとめ通知は、検知時の保存情報をカード化し、
通知側で全件を再取得しません。

通知履歴の送信成功はタイトル＋URLの投稿成功を表します。
その後の通常展開の結果は展開履歴で別に確認します。
通常展開の失敗を理由に通知文を再投稿しません。

送信/Gateway照合は同じBotプロセス内で行います。
GatewayイベントがWebhookのHTTP応答より先に届いても、送信結果を待って
通常展開へ渡すか、再展開を抑止するかを判断します。
送信結果不明の `normal` は通常展開へ渡し、
直接送信した形式は二重展開を防ぐため抑止します。
同じWebhook・同じ内容の別投稿が直接送信の結果不明と重なる場合は、
保守的に抑止することがあります。
複数の独立Gatewayプロセスへ分離する構成は追加の共有照合設計が必要です。
