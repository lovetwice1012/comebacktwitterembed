# 自動通知の検証・移行チェックリスト

この文書は手順であり、本番移行済み・実通知確認済みという記録ではない。現行の仕様は[機械判定方針](automation-mechanical-policy.md)。

## ローカルで確認する範囲

1. `npm test`で一般試験を実行する。このランナーは`NODE_ENV=test`を設定する。試験ファイルを個別実行する場合も同じ環境を明示する。
2. rootとDashboardの型検査、変更対象のlintを実行する。
3. 専用のローカルMariaDBを確認し、`AUTOMATION_TEST_DB_PORT`へ非3306のループバックポートを指定してSQL統合試験を実行する。テストヘルパーはランダムな`cbte_automation_test_<20hex>`スキーマのみを作成・破棄する。本番の接続設定を流用しない。
4. `scripts/automation-ui-harness.js`を同じ専用DBで起動し、表示された127.0.0.1のURLを`AUTOMATION_AUDIT_UI_URL`として`scripts/verify_automation_ui.cjs`を実行する。架空ユーザー・模擬Discordの試験であり、本番認証は別検証。バックエンドを変更した後はハーネスを再起動してから統合試験をする。
5. ハーネスへ`stop`を送って終了する。確認なしに別のDB・プロセスや広いフォルダを削除しない。

## 本番作業前の条件

- 作業直前に、対象ホスト、配置リビジョン、DB、変更範囲、実通知の宛先・上限件数について利用者から明示的な許可を得る。
- BotとDashboardが同じ自動化スキーマ・ポリシーを使うこと、バックアップの取得と復元可否を確認する。無関係な作業差分を一括で配布しない。
- `src/db_schema.js`による起動時マイグレーションも書込みを伴う。起動すれば自動で適用してよいとは解釈しない。既存の適用履歴と未適用SQLを確認してから進める。
- 初期作成SQL、旧版からのアップグレード、監視対象別基準点のマイグレーションを照合する。ローカルの冪等性試験は、本番のバックアップや実スキーマ確認の代わりにはならない。
- Twitterの既存登録を削除・無効化しない。新規登録のみ停止した状態と、list/deleteの継続を確認する。
- 古い安全保留は新方針で終了する。過去の通知を無断で一斉送信しない。送信済み・一部送信・結果不明の実績を保持する。
- `/autoextract watch`の`responsibility`確認項目を含めてコマンド定義を更新する必要がある。古い定義からの要求は登録前に説明付きで拒否される。

## 許可後に実Discordで確認すること

- 利用者本人のDM、明示された既存Webhook、作成を許可されたチャンネルのBot Webhookを各1件ずつ試す。作成前にユーザー・Bot双方の権限を確認する。
- 通常展開／カード／文章／URLだけを選び、文面・画像設定が維持されることと、通知が通常のURL展開へ戻って二重投稿されないことを確認する。
- まとめ通知の展開表示は検知時の保存情報をカード化する。送信時の全件再取得や未取得メディアの補完は行わない。カード数・文字数上限による分割と、本文・URLのみ指定の再展開抑止を確認する。
- 別サービスの通常Webhook投稿は、既存の展開設定どおり処理されることを確認する。
- 指定時刻・静穏時間、停止・削除、権限失効、価格増減・再到達、再起動後の予約を確認する。既存ユーザーの設定を検証用に変更しない。
- 実通信では結果不明が起こり得る。一括再送で確認するのではなく、履歴とDiscord側のメッセージIDを照合する。
- 現行のWebhook送信/Gateway照合は同一Botプロセスを前提とする。独立したGatewayプロセスを複数稼働させる場合は共有照合の設計・検証が必要。

## 切り戻し

送信を止める必要がある場合は、まず通知・ランナーを停止する。DBを古い状態へ上書きして送信実績を消す切り戻しはしない。互換スキーマを維持し、`unknown`／`partial`の自動再送を禁止した状態で原因を確認する。
