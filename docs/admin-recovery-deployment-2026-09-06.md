## 実機の停止期限検証

本体Ubuntu 20.04 / systemd 245 / cgroup v1に、一時的な専用unitと偽のローカル許可サーバーを作成した。本番のBot・権限サーバー・DBから隔離して、配備対象と同じguardianを使用。

- 90秒の起動許可を1回だけ発行し、更新先を停止。
- guardian、ダミー子プロセス、別セッションを作った孫プロセスが **58.111秒**で全て停止。
- 内部停止期限70秒と許可期限90秒より前に停止し、対象cgroupが空になった。
- 本番 `cbte.service` は検証前後ともPID `2386418` のまま稼働。
- 検証用unit・一時実行ディレクトリは撤去。

[実測の検証記録](evidence/primary-guardian-fence-2026-09-06.json)。本番を意図的に停止してOCIへ切り替えた検証ではない。

## OCIでの取り扱い

- 旧savedataは移行しない。OCIで新しく作られる保存メディアには、専用の公開ディレクトリを使用する。
- 復元時点の古い未送信通知は隔離し、送信し直さない。
- OCI Botの従来のgzipダンプは無効にし、暗号化してNASへ送る専用バックアップ処理を使用する。
- バックアップの日次timerと転送再試行timerを有効化。稼働グループは自動起動を登録したが、現在は未起動。OCI Botの本番ログインは行っていない。
- 子プロセスのログは各16MiB×4世代、書き込みが追いつかない場合の欠落量も記録する。緊急画面には認証付きで最大256KiB・1000行の末尾を表示する。
- 保存・一覧・表示・削除・使用量計算の保存先を統一。`SAVES_DIR`を使うOCIでも新しい保存データを扱えるようにした。旧ファイルの移動は行っていない。
- `mysql@2.18.1`に合わせ、復旧用DBユーザーは固定したMySQL 8.0の `mysql_native_password` で作成・再確認する。
- 独立した一時MySQL 8.0.42で、実際のmysql 2.18.1ドライバーの接続・SELECTを検証した。一時コンテナ・データは撤去し、稼働DBには変更していない。
- WebからのBot操作は起動許可を検証するunit経由。OCIのworkerとDBは本体の個別systemd unitと異なるため、未対応の単独操作を画面とAPIに明示する。
- 公開経路の検証リクエストには `CBTE-Recovery/1.0` を付ける。無指定のPython urllibはCloudflareの1010で拒否されたが、専用識別名で200を確認した。

新しい詳細イベントは新コードの起動以降に記録される。過去に記録していなかったAPI応答・クリック・閲覧を取得済みとして扱わない。

本体の保存領域への権限設定は途中。I/O停止に伴って停止要求を送信しており、復旧後に処理状況を確認する。デプロイ作業の最終完了とはしていない。

## 本体復旧後に反映する追加修正

今回、通信が生きたままBotがI/O待ちになる状態では、従来のguardianは許可更新を続けることが判明した。そのため `f178dcc` / `01869ca` で、既定無効の `primaryIoWatch` と、通常の許可更新に付随する最終観測のOCI保存・Web表示を実装した。関連189テストとGo/UI検証は成功したが、稼働中のauthority・guardian・登録ハッシュには反映していない。

本体の実デバイス構成を再確認したうえで、起動猶予300秒、継続判定180秒を使う予定。本人PIDのD状態、物理・論理の書き込み完了停止、物理inflight 0、論理・WBTの滞留が揃い続けた場合だけ、更新を止めて既存の停止処理へ移る。不明な観測や進捗回復は判定をリセットする。最終観測は現在の状態と区別し、最後の停止確定通知が必ず配送されるとは扱わない。

詳細は [I/O停止監視の仕様](../recovery/PRIMARY-IO-WATCH.md)。反映にはguardianの配布物・設置証明・authorityの許可ハッシュの整合と再登録が必要。OSの書き込みが停止している間は、この変更を本体へ適用しない。
