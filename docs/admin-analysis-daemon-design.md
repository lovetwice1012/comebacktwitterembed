# 管理分析デーモン設計

2026-09-05。採用済みの[Adminサポートコンソール方針](admin-support-console-design.md)を実現する独立運用基盤の設計。実装・デプロイの追加依頼を受けた後の実施内容と、稼働確認できた範囲は[実装・検証状況](admin-platform-implementation-status.md)を参照。

指標・集計・画面の意味は[指標と統計の詳細設計](admin-metrics-and-statistics-design.md)に従う。通常ダッシュボード、独立管理Web、分析worker、自動診断ルールで同じ指標ID・定義版・対象集合を使う。

同設計のDiscord API精査に従い、通常メッセージの閲覧・既読・URL/Linkボタンのクリックを取得対象に含めない。custom_id付き非リンクボタンのinteraction、Botの送信結果、自前HTTPの転送状態、外部サービスの数値をそれぞれ区別する。Bot出力の成功やサーバー側の送出終了は、人の閲覧や端末への保存を示さない。

## 1. 目的と採用する構成

サーバーIDと大まかな時間帯だけで問い合わせを調べる運用を維持する。管理者1人がWebで全サポート操作を行い、同じ証拠と操作を使ってデーモンが監視・障害検知・専門的な調査・原因候補の整理・通知・条件付き修復・復旧確認を自動化する。

LLMは使用しない。自動診断・追加調査・対処の選択は、版管理した診断ルール、証拠の照合、定義済みの調査手順で実行する。説明文は判定根拠を埋め込むテンプレートから作成する。

独立性は、プロセス、起動条件、管理Web、認証、保存先、通知経路、配布物まで含める。BotやNext.jsを停止した状態でも管理Webを開き、障害前後の証拠を読み、利用可能な操作を実行できることを要件とする。

構成案は、Go製の軽量な管理コア、別プロセスの分析worker、必要な特権操作を行うexecutor、別ホストの監視役とする。Goの採用理由は、BotのNode環境・npm依存・Nextビルドから切り離して配布・起動できるため。プロバイダー再解析など既存JSロジックの利用部分は、版を固定した専用workerとして分離する。

以下は採用したサービス構成である。配備された場所と現在の稼働状態は実装・検証状況で区別する。

~~~mermaid

  User["管理者のブラウザー"] --> Core["cbte-admin.service\n独立管理Web / API / 監視 / 障害台帳"]
  User --> Dash["通常ダッシュボードのadmin画面"]
  Dash -->|"管理者確認済みAPI / 操作 / 更新通知"| Core
  Core --> Store["専用ローカル保存\nSQLite / 証拠ファイル / 通知待ち"]
  Bot["cbte.service\nBot + 通常ダッシュボード"] -->|"処理証拠 / heartbeat / 操作ACK"| Core
  Core -->|"共通サポート操作"| Bot
  Core -->|"調査・レポート生成"| Worker["cbte-admin-analysis.service\n隔離した分析worker"]
~~~

既存の一般ユーザー向けダッシュボードは従来の起動構成を維持できる。管理者向け機能には、通常ダッシュボードの/adminと独立管理Webの二つの正式な入口を用意する。通常ダッシュボードが動いているときは、その画面内で診断・調査・設定変更・修復・結果確認まで完了できる。両画面は同じ管理コアのAPI、障害台帳、操作カタログと表示部品を共有する。

## 2. 現在の構成から変更する点

| 現在のコードで確認したこと | 新構成での扱い |
| --- | --- |
| index.jsはMySQL初期化の後にダッシュボードを準備・起動し、Discordへログインする | 管理デーモンはそれらの準備・成功を待たずに起動 |
| SIGINT/SIGTERMでdashboardServer.stopを呼ぶ | 管理デーモンをBotの子プロセス・同じサービスの管理範囲に含めない |
| ready.jsから性能記録・異常通知を開始する | 外形監視・OS記録・障害台帳・通知はDiscord Ready以前から稼働 |
| errorRateNotifierは15分間隔、直近1時間と過去の集計を比較する | 即時の停止監視、短期の機能監視、長期の傾向分析を別の頻度と根拠で実行 |
| errorRateNotifierはMySQLから判定材料と障害状態を読み書きする | 障害台帳・通知待ち・操作履歴の正本を管理デーモンの専用保存へ |
| 現在の解消判定は「今回の警報候補に含まれない」を使う | 低トラフィック、基準未達、観測不能を復旧としない。肯定的な復旧確認を要求 |
| 通知の埋め込みに「開発者連携: 共有済み」が固定表示される | 実際の送信結果・外部メッセージIDを記録し、受信サービスの受付と管理者の確認を区別 |
| 配布済みcbte.service案はRestart=on-failure、RestartSec=5s、StartLimitIntervalSec=0 | 再起動の主体を整理し、無制限の再起動とデーモンの重複操作を解消 |
| 重い統計はダッシュボード側で構築する | 分析workerへ移し、管理Webと監視コアから独立して生成 |

これはローカルコードの確認結果。本番のサービス設定・プロセス・OS版が同一かは、実装後の導入時に再確認する。

## 3. 障害ごとの利用可能範囲

| 障害 | 継続する機能 | その時点でできる対処 |
| --- | --- | --- |
| Botが終了 | 管理Web、OS監視、既存証拠、診断、通知、設定資料、操作履歴 | 終了原因調査、適用可能な設定変更、Bot起動/復旧。送信操作は実行可能条件を確認 |
| Botがハング | 外部からの進捗監視、プロセス情報、独立UI、保存済み証拠 | ハング前資料の保全、原因別の追加調査、条件成立時の限定再起動 |
| 通常ダッシュボードが終了 | 全管理機能、Botの監視・操作 | ビルド・起動・HTTP経路の調査。現構成で再起動がBotに及ぼす範囲も表示 |
| MySQL停止・過負荷 | 独立UI、専用障害台帳、ローカル証拠、OS診断、通知 | 接続/ロック/I/O切り分け、修復提案、復旧確認。DBへの設定変更は準備・待機状態 |
| 分析worker停止 | 収集、ルール診断、通知、管理操作、既存レポート閲覧 | workerの限定再起動、未完了ジョブの状態整理。軽量なルール診断は継続 |
| Discord側障害 | 管理Web、ローカル認証、OS/DB/取得元診断、別系統通知 | Discord依存操作を待機させ、復帰を観測。Bot再起動を繰り返さない |
| 同一ホスト全体が停止・通信断 | 別ホストの監視と通知、複製済み障害要約 | 到達不能の通知。復旧後にbootをまたいで調査。電源復旧等は別の管理経路の能力に依存 |
| 管理デーモン自体が停止 | systemdによる監視、別ホストの監視、Bot側の退避 | デーモン再起動と退避再取り込み |
| 管理用ディスクが満杯・I/O停止 | 専用保存も影響を受ける。別ホスト側の最終状態は残る | 予約領域・容量制御・外部通知を使い、記録不能を明示 |

同一ホスト上の別デーモンは、ホスト全体の停止からは独立しない。別ホストの監視役を構成に含める。配置先は別VM/NAS等を候補とし、実機は未選定。外部から到達できない事実だけで、電源断・回線断・トンネル障害を決めつけない。

## 4. プロセスと保存先

| コンポーネント | 責務 | 主な依存 |
| --- | --- | --- |
| cbte-admin.service | 軽量収集、独立管理Web/API、ルール、障害状態、操作調停、通知 | ローカルOSと専用状態ディレクトリ |
| cbte-admin-analysis.service | 定義済みの詳細調査、レポート、保存応答再解析、証拠と既知障害の照合 | 管理コアの証拠API、必要な場合だけMySQL |
| cbte-admin-executor.socket/service | 定義済みのsystemd・OS操作と実行結果の保存 | Unix socketとOS。BotやMySQLに依存しない |
| 外部監視役 | heartbeat欠落と外部到達性の監視、独立通知 | 別ホスト・別保存・独立した通知資格情報 |

管理コアは専用ユーザーと専用sliceで起動する。Bot・MySQLへのRequires/BindsTo/PartOfや、それらの正常性を起動条件に置かない。ネットワーク未接続でもローカルUIと記録を開始し、外部接続は後から回復させる。サービス依存関係の意味は[systemd公式資料](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.unit.xml)に従う。

配布物は/opt/cbte-admin/releases等、状態は/var/lib/cbte-admin、socketは/run/cbte-admin等の独立した場所を候補とする。Botのcheckout、node_modules、.next-builds、起動時ビルドを管理コアの前提にしない。管理コア更新時にBotを再起動する構造にしない。

管理コアの初期予算案はMemoryHigh 192MiB、MemoryMax 384MiB、CPUQuota 25%、重いworkerは512MiB、CPUQuota 50%、同時実行1とする。いずれも未計測の開始値。cgroup版、systemd版、実効設定、I/O特性を確認して変更する。重いworkerが上限に達しても監視コアを同時に終了させない。資源制御の機能差は[systemd公式資料](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.resource-control.xml)で確認する。

管理コア自身はType=notifyとwatchdogに対応させる。watchdogへの応答は単なるタイマーではなく、制御ループと状態保存の進行を確認して出す。MySQL/Discordが利用不能という理由では応答を止めない。core自身の再起動にも上限を置き、繰り返す場合は外部監視へ通知する。[systemd watchdog仕様](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.service.xml)

## 5. 独立した管理Webと認証

管理Webは管理コアが配信する事前ビルド済みの静的UIとする。主要なJS・CSS・フォントを同梱し、Next.js、MySQL、Discord OAuth、外部CDNの可用性をログインと資料閲覧の前提にしない。

管理者は1人。独立したローカル管理者アカウントを持ち、事前登録したpasskeyと保管した回復用の認証手段を用意する。資格情報・セッションは専用保存で管理する。普段のDiscordログインとの連携を付ける場合も、障害時の唯一の認証経路にはしない。passkeyはoriginに依存するため、代替アクセス経路でも使える管理originまたは別の回復手段を導入時に検証する。

公開URL経由と管理用VPN等の直接経路を用意し、トンネル/プロキシの障害時も到達できる構成を確認する。外部認証サービスに全面依存する構成は避け、インターネットから切り離した試験でもログイン・証拠閲覧・ローカル操作を検証する。

採用済み設計のサーバー設定、対象別設定、自動展開、保存データ、容量、委任アクセス、再解析、プレビュー、再送、稼働操作を独立管理Webへ揃える。サーバーID・時間帯・対象事象を引き継いだまま操作できる。

DB停止中は最終確認済み設定を取得時刻付きで表示し、変更案を作成できる。DB未保存の案を「適用済み」と表示しない。実行期限を過ぎた待機操作や期待revisionが変わった操作は自動適用せず、差分を再評価する。

### 5.1 通常ダッシュボードとの連携

通常ダッシュボードのadmin画面に管理デーモンの状態、進行中の障害、調査、修復操作を統合する。独立管理Webと同じ機能を画面内で操作でき、普段のサポートのたびに別画面へ移る必要がない構成とする。

| 既存画面 | 連携内容 |
| --- | --- |
| 管理概要 | デーモンの接続状態、監視対象の状態、進行中incident、調査/修復の進行、記録遅延 |
| 詳細統計 | デーモンの完成レポートと生成状態。同じ期間・集計条件の元事象や関連incidentへ移動 |
| サポート | サーバーIDと時間帯を引き継いだ事象一覧、根拠、当時/現在の設定、診断・変更・再検証 |
| 設定編集 | 共通操作APIから変更。DB保存revision、Bot反映ACK、履歴、差分を両画面へ反映 |
| ログ | 原文・HTTP・例外からtrace、incident、管理actionへ移動 |
| URL実行検証 | URLを貼り付け、実際のprovider取得による展開結果とHTTP応答を左右に表示。設定比較、再取得、履歴、明示的なテスト送信 |
| 指定先へ送信 | サーバーID・チャンネルIDを直接指定し、URL展開結果または本文・Embed・添付を送信。対象確認、作成ID、REST応答、部分成功を共通actionで追跡 |
| 障害対応 | 追加調査、保存資料再解析、許可された修復、確認済み、保守、操作policy、通知結果を操作 |

既存/adminを単なる転送リンクに置き換えず、サポートの作業画面として維持する。設定・資料・診断・操作の表示は同じ契約と部品を利用し、原文や実IDの表示範囲も揃える。

### 5.2 接続・認証・更新通知

ブラウザーから通常ダッシュボードの管理APIを呼び、同APIが既存のrequireAdminSessionで管理者を確認してから、Unix socket等のローカル接続で管理コアへ中継する。管理コアは登録した接続元と管理者principalを検証する。ブラウザーが申告するactor IDだけで操作を受け付けない。

独立管理Webのローカル管理者と通常ダッシュボードの管理者を、設定済みの同じprincipalへ対応付ける。操作履歴には同じ実行者に加えてinitiated_via=dashboard/standalone/automationを残す。通常ダッシュボード内では既存の管理者ログインで連携操作を行え、独立Webの利用時は独立した認証手段を使用する。

中継APIには接続・応答期限を設け、管理コアが停止しても通常ダッシュボード全体を待たせない。Bot/ダッシュボードの起動はデーモンとの接続完了を待たず、接続はbackoff付きで復旧する。通常のユーザー向けAPIへ管理権限を広げない。

incident、action、設定反映、report jobの更新は、管理コアのevent cursor付き通知を中継する。SSE等が使えない経路では差分ポーリングに切り替える。再接続時はcursorから再取得し、保持範囲外なら現在のsnapshotとrevisionを読み直す。接続状態と最終同期時刻を表示し、古い画面を最新として扱わない。

通常ダッシュボード側からも、管理操作、起動/build、API失敗、レポート要求、接続状態をcomponentとboot/build付きで記録する。管理コアが停止中は退避して再送し、後からBotの処理と区別して関連付ける。監視用HTTPは小さい専用health APIとし、プローブで詳細統計の再生成を起動しない。

### 5.3 二つの入口で操作を整合させる

管理対象の変更はどちらの入口も同じaction APIへ送り、action ID、重複排除、排他、期待revision、policy、検証結果を共有する。自動修復も同じ経路に入る。画面ごとに別の修復workerを動かさない。

現在のadmin設定APIの直接書き込みは、対象操作を管理コアへ移す際に共通action経路へ切り替える。移行中は機能ごとの対応表に実行主体を明示し、同じ送信要求を旧処理と新処理の双方へ送らない。一般ユーザーからの設定変更等は同じ設定revision/監査契約を通じて反映し、管理画面で作成中の変更との競合を検出する。

通常ダッシュボードで開始した調査や修復は、ブラウザーを閉じたりダッシュボードが停止したりしても管理コアで継続する。独立管理Webから同じaction IDで進行と結果を確認できる。画面切断を契機に再実行しない。

同じサーバーを両画面で編集中に片方が保存した場合、もう片方の未保存入力を保持して変更差分を表示する。古いrevisionのまま上書きしない。障害の確認済み状態や保守設定も同じrevisionを共有する。

### 5.4 障害時の切り替え

| 状態 | 管理者の操作経路 |
| --- | --- |
| 両方稼働 | 通常ダッシュボード内または独立管理Webから同じ診断・操作を利用 |
| 通常ダッシュボード停止 | 独立管理Webで同じincident/trace/actionを開き、調査・操作を継続 |
| 管理コア停止、通常ダッシュボード稼働 | 接続不能と最終同期時刻を表示。利用可能な既存機能・現在値の閲覧を維持し、未同期の情報は明示 |
| 送信後に連携が切断 | actionの受付・実行状況を再照合。未実行と決めて別の経路で再送しない |

管理コア停止時の通常ダッシュボードには、必要な場合に管理コア自身の復旧をexecutorへ要求する限定操作を用意する。対象は管理コアのunitに固定し、executorの台帳・排他・状態確認を使用する。一般の修復や設定書き込みを、接続失敗時に無条件で別経路へ流すfallbackは作らない。

独立管理Webへのリンクは常に表示し、サーバーID、時間帯、incident/operation/action IDを引き継ぐ。同じ条件を両画面で表すURL契約を決める。通常ダッシュボード自体が応答しなくてもアクセスできるよう、独立URLを通知と管理者のブックマークからも利用可能にする。

## 6. 証拠収集

### 6.1 収集対象

| 対象 | 収集するもの | 診断上の使い道 |
| --- | --- | --- |
| Bot内の処理 | 採用済み設計の受付・判定・HTTP・解析・出力・送信・後処理event | ユーザーの事象を根拠まで追う |
| Bot進捗 | boot/build、event loop、Gateway、queue、最終処理時刻、成功/失敗/受付累計、適用設定revision | プロセス生存と機能停止の区別 |
| systemd | unit状態、job、MainPID、InvocationID、起動時刻、終了理由、NRestarts | 停止・再起動ループ・計画停止の区別 |
| journal | unit別のcursor、boot ID、PID、monotonic時刻、原文 | 再起動前・前回bootまで含む調査 |
| OS | RSS、swap、page fault、CPU、event loop、FD、thread、空き容量/inode、disk I/O、PSI、OOM資料 | CPU/メモリ/I/O/資源上限の切り分け |
| MySQL | 接続と小さい読み取り、実行中statement、ロック待ち、エラー、接続/バッファ/一時領域の状態 | SQL待ち・接続・ディスク待ちの区別 |
| HTTP経路 | localhost、通常公開URL、管理公開URL、DNS/TLS/HTTP、取得元の限定プローブ | アプリ・プロキシ・回線・外部サービスの区別 |
| 変更履歴 | code/build、設定revision、デプロイ、再起動、ジョブ投入、管理操作 | 発生直前に変わった条件との比較 |
| 記録機構 | producer sequence、取込watermark、遅延、退避量、欠落、worker状態 | 観測できない時間帯を正常と誤判定しない |

PSIはCPU・メモリ・I/Oの資源待ちを観測する補助情報として利用する。PSIやRSSだけからOOMやディスク故障を断定しない。[Linux kernelのPSI説明](https://docs.kernel.org/accounting/psi.html)

Botがまだ実装していないeventや、OS/DB権限により取得できない項目はcapabilityとcoverageで明示する。初期導入時の外部監視だけで、Bot内部の個別判断が追えるようになったとは扱わない。

API自体が提供しない項目と、取得可能だが収集を実装していない項目は別状態にする。非提供の閲覧・クリック数を0へ変換して、異常検知や復旧確認の入力にしない。独立した管理デーモンを追加してもDiscord APIの観測範囲は変わらない。

### 6.2 収集頻度と上限の初期案

- journal/eventはcursorを維持して継続取得。Bot heartbeatは5秒、OSの軽量状態は10秒、ローカルHTTPは15秒。
- MySQLの接続/小さい読み取りは15秒、診断接続は最大1、通常プローブ期限は1〜2秒。
- 外部取得元の能動プローブは必要な取得元に限定して60〜180秒、失敗時はbackoff。実トラフィックの証拠を優先する。
- 精密調査はincident単位で起動し、通常同時実行1、最初の証拠採取は30秒以内、追加調査は120秒等の予算を持つ。
- SQLはサーバー側の実行期限、件数、対象時間帯も制限する。クライアントの待機打ち切りだけでSQLが止まったと判断しない。
- 全件COUNT、大規模なEXPLAIN ANALYZE、全プロセスのheap dumpを定期監視の既定動作にしない。

閾値・頻度は設定として版管理し、実データで校正する。大量イベントの際にも管理Webと監視判定を進められるよう、収集・索引・分析の実行枠を分ける。

### 6.3 永続化と独立性

障害台帳、操作、通知待ち、取込cursorはローカルSQLiteを正本にする。証拠の大きい本文は圧縮ファイルとmanifest、hash、完全性情報で保存する。全本文をSQLiteの一覧行に繰り返し格納しない。

SQLiteはローカルfilesystem上のWALを候補とし、writerは管理コアに集約する。workerはAPI経由で書き込み、長いread transactionでcheckpointを止めない。operation/incident/action/outboxは短い同一DB transactionで更新する。WALとshared-memoryは同一ホスト前提で、ネットワーク共有上へ置かない。バックアップは整合したsnapshot/APIを使う。[SQLite公式資料](https://www.sqlite.org/wal.html)

Botはローカル退避したeventをsequence付きで送信し、管理コアは耐久化後にACKする。ACK後に再送されてもevent_idで重複排除する。管理デーモン停止中もBot側退避は残す。片方が落ちたためもう片方が停止する待ち方をしない。退避不能時は欠落区間を記録し、事象そのものの成功判定と混同しない。

Bot/MySQL既存データは取込元の一つとし、採用済み設計のtraceと関連付ける。集計用のMySQL書き戻しや外部への複製が止まっても、管理台帳と通知は動く。取り込み済み証拠をMySQLから毎回引き直して表示しない。

同一物理ディスクであればI/O障害の影響は共有する。専用の容量枠と緊急用の予約領域を確保し、可能なら証拠保存を別volumeへ置く。外部監視側にはheartbeatと障害要約を継続複製する。どこまで複製済みかをwatermarkで示す。

保持は採用済み方針の最低30日を引き継ぎ、incident保全時は関連する入力・HTTP・設定・出力・OS記録をまとめて保全する。管理操作と障害台帳は初期案90日。容量は実測し、上限に近づいた時点で非必須分析を止めて通知する。調査対象の証拠を無言で削除しない。

## 7. 自動診断の処理

処理順は、観測、疑いの検出、証拠の保全、追加調査、原因候補と反証の整理、対応選択、実行、復旧確認とする。調査前の再起動で重要な状態を消さない。

### 7.1 検出

| 症状 | 初期の検出条件案 | 追加で確認すること |
| --- | --- | --- |
| 異常終了 | systemd/journalの終了event | 計画停止、現在のrestart job、exit code/signal、boot |
| 生存しているが停止 | heartbeat3回欠落、またはpending>0なのに処理完了が60秒進まない | OS生存、event loop、外部依存、DB、queue、単に処理が長いケース |
| 個別機能の失敗増加 | 短期の連続失敗、十分な母数での失敗率上昇、確認用プローブ失敗 | provider/取得先/設定/build/影響サーバー別の偏り |
| DB応答悪化 | 小さい読み取りの遅延や失敗が複数回 | 接続、statement、lock、I/O、swap、権限不足 |
| 公開経路障害 | 公開HTTP失敗かつローカルHTTP成功 | DNS、TLS、proxy/tunnel、外部監視からの観測 |
| 設定反映遅延 | 保存revisionとBot ACKの差が期限超過 | invalidation、Bot状態、DB接続、cache、処理の適用revision |
| 記録障害 | ACK/水位が進まない、退避増加、保存失敗 | 保存先容量・I/O・DB、取込worker、記録権限 |

数が少ない単発の問い合わせもサポート一覧には残す。全体障害の通知閾値を満たさないからといって、事象を削ったり検索不能にしない。

平常時の母数がない、新しいprovider、トラフィック0件、観測が遅れている状態は「判定資料不足」を持つ。平常baselineには進行中障害・保守・デプロイ直後等を混入させず、同曜日/時間帯の比較は追加根拠として扱う。

### 7.2 障害状態

incidentはSuspected、Investigating、Confirmed、Mitigating、Verifying、Resolvedを主状態とし、観測不能と判断待ちは別の状態理由として保持する。手動確認済み、保守中、通知の扱いも別項目にする。

原因候補は「主張」「支持する証拠ID」「反する証拠ID」「未観測項目」「次の検証」「推定影響範囲」を必須とする。時刻が近いだけのeventを原因の証明にしない。関連エラーは同じincidentへまとめ、異なる根拠の障害を無理に一つへ統合しない。

復旧は、対象プローブの連続成功、queueの進行、実処理または診断用の処理結果と、観測が新しいことから判定する。初期案は2分間に3回の正常確認。トラフィックがない場合は、どの機能までプローブで確認できたかを表示する。PID再生成、HTTP 200、警報閾値を下回ったことだけでは全機能復旧にしない。

### 7.3 専門的な診断手順

| 手順 | 自動で集める証拠 | 到達する判断・次の行動 |
| --- | --- | --- |
| プロセス異常終了 | systemd終了理由、kernel/journal、cgroup、boot/build、直前の資源と処理 | OOM kill、signal、明示停止等を区別。被害プロセスのPID/cgroupを照合 |
| Nodeのハング | event loop、queue進捗、FD/thread、直前の処理、設定期限、採取可能な診断report | 実行待ち、外部待ち、event loop停止、資源枯渇を絞る |
| MySQLの遅延 | 軽量query、実行statement、lock wait、I/O・swap・PSI、jobとの対応 | query形状、lock、接続待ち、ストレージ待ちを区別。原因別に対応を選択 |
| 外部provider異常 | 試行別status/本文/headers、fallback、parse例外、同条件成功例 | サービス全体、特定取得元、特定投稿、解析コードの問題を区別 |
| Discord送信不調 | REST原文、実payload、権限資料、rate-limit、送信ID/nonce | 拒否、制限、payload不正、送信成否不明を区別 |
| 設定変更後の不調 | 当時/現在の実効設定、適用revision、rule、code版 | 設定の影響と未反映、コード変更の影響を比較 |
| 配信・ダッシュボード障害 | local/public HTTP、Next起動/build、媒体stream、proxy/tunnel | アプリ、媒体取得、公開経路のどこが壊れているか特定 |
| 再発・長期劣化 | 同じ指紋の履歴、RSS/FD/queue/SQLの推移、修復後の経過 | 再起動で一時的に戻る問題と恒久修正が必要な問題を区別 |

heap snapshotや大きいcoreの展開は、負荷・空き容量・対象PIDを評価した個別の調査actionにする。自動で収集する小さい診断資料と同じ予算で無制限に起動しない。

コードとの対応はbuild_revision、設定schema、計測版で固定する。スタックから当時のソース位置へ移動できるよう、配布時のmanifestと該当ソース/マップを保管する。現在のcheckoutの行番号だけで過去の原因を説明しない。

## 8. 自動調査の例：統計が止まり、Botも遅い

既存の調査文書にあるMySQL/I/Oの事例は、診断手順を作る材料にする。過去の観測値を現在の状態とみなさない。

1. 統計workerの進捗停止とBotのDB待ち増加を検出し、前後の記録を保全する。
2. Bot、通常ダッシュボード、管理コア、MySQLの生存と現在のjobを確認する。
3. 少量のstatement/lock資料、MySQLのRSS/VmSwap、swap-in、disk待ち、I/O PSIを同じ区間で取得する。
4. 「lock待ちあり」「appの接続待ち」「大きい読み取りとI/O待ち」「資料不足」に分岐する。
5. I/O待ちが根拠付きで有力なら、管理分析の新規重処理を期限付きで抑制し、既存レポートの時点を明示する。BotやMySQLの再起動を一律に選択しない。
6. 実行中の読み取りが管理worker自身のものなら、action ID・DB接続・statementを再照合して、そのqueryだけを中止できる。アプリの更新transactionや他者のqueryは同じ条件で止めない。
7. DB待ちとBotの進捗が戻るかを測定し、戻らなければ影響と未確認事項を更新する。
8. 完全なレポートを再生成し、登録済みの対処手順から該当するquery/索引/集計保存の改善候補と、その適用条件・検証結果を残す。未対応の原因は証拠一式と未確認事項を残す。

症状が消えたことと恒久原因の解消を別に記録する。資源圧迫が繰り返す場合は、同じ応急処置を無制限に反復しない。

## 9. 診断ルールと定義済みの調査手順

分析workerは[サポート設計のURL実行検証ページ](admin-support-console-design.md)も実行する。実URLの取得と保存応答の再解析を区別し、同じrunに生成payload・HTTP試行・判定根拠を紐付ける。両管理画面から利用でき、通常の検証はDiscord副作用を実行しない。

技術支援は、既知の障害条件を検証するルール、条件に応じて追加資料を集める調査手順、保存資料の再解析、対処手順のカタログで構成する。スタックはbuild版に対応するソース位置へ紐付け、HTTP本文はstatus・Content-Type・構造・既知のエラー形式を検査する。

各ルールはrule_id、version、対応する計測/schema/build範囲、必要な証拠、成立条件、反証条件、追加調査、説明テンプレート、対応する修復actionを持つ。評価結果は成立・不成立・資料不足の3状態とし、証拠ID、評価した実値、閾値、判定時刻を保存する。同じ証拠とルール版を使えば判定を再現できる。

| ルール例 | 成立させる根拠 | 資料不足時の次の調査 |
| --- | --- | --- |
| OSによるBotのOOM終了 | kernel/cgroupのOOM資料とBotのPID・起動時刻・所属の一致 | 同一bootのkernel記録と対象cgroupを取得。RSS増加だけなら確定しない |
| 設定の未反映 | 確定した保存revisionと問題処理の適用revisionが異なり、反映期限を超過 | Bot ACK・cache時刻・反映要求の状態を取得 |
| 外部応答の解析失敗 | 対応するHTTP応答、解析例外、期待形式と実際の形式の不一致 | 保存応答を対応版のparserで再解析 |
| 公開経路の障害 | 同区間でローカルHTTPは成功し、公開HTTPは繰り返し失敗 | DNS・TLS・proxy/tunnelと別ホストからの到達性を確認 |
| 管理queryとI/O待ちの関連 | 対象queryの実行区間とI/O待ちの増加が一致 | 所有するqueryの状態と比較期間を取得。相関だけで原因確定にせず、policy内の停止後も比較 |

調査手順は、実行可能なactionを節点とする分岐として実装する。各節点に必要な証拠、対象、成功/失敗/資料不足の分岐、期限、負荷上限を持たせる。初期案は1incidentあたり2分、追加調査5回、同時実行1。同じ観測状態で同じ調査を無限に繰り返さず、予算超過時は集めた証拠と未確認事項を残す。

原因説明・技術レポート・通知は、評価結果をテンプレートに埋め込んで作る。根拠のない原因名や、実行していない試験結果を補完しない。外部応答に含まれる文字列は検査対象のデータとし、操作定義として使用しない。

どのルールにも一致しない障害は「原因未分類」とし、受付から失敗までの経過、例外原文、HTTP応答、当時の設定・コード版、比較対象、未確認事項をまとめる。Webでは原文検索、同じ指紋の事象比較、保存資料の再解析、対応する診断actionの手動実行を提供する。未知の障害を既知の原因へ無理に分類しない。

修復は登録済みの手順と対応表から選ぶ。コード修正が必要なら、ソース位置・入力・期待値・実際の値・再現結果を調査資料としてまとめる。登録済み修復パッチを扱う場合は、対象版・適用条件・検証手順・差分をWebで確認できるようにする。採用済みのeffect分離に従い、プレビューや再解析で返信・削除・通知を発生させない。

ルール・調査手順・説明テンプレートは版管理し、既知の成功例、故障注入例、反例、証拠欠落例で検証する。過去incidentの再評価は当時の判定を上書きせず、新しいルール版による別結果として保存する。

## 10. 自動修復policy

自動化の範囲は設定画面で明示し、policyに許可した操作は毎回の承認待ちにせず実行する。今回の設計依頼を、今この環境でのサービス再起動やDB変更の実行とは扱わない。

初期導入では観測のみの期間を置いて誤判定を測り、その後、同じpolicy定義を使って自動修復を有効にする。操作ごとの自動/提案/手動をWebから変更できる。

| 操作 | 初期policy案 | 実行条件・制限 |
| --- | --- | --- |
| 証拠収集、保存資料の再解析、原因説明 | 自動 | 時間・件数・CPU/I/O予算内 |
| 失敗した管理分析workerの再起動 | 自動 | 管理workerだけ、記録保全、回数制限 |
| 管理分析の新規重処理を一時停止・再開 | 自動 | 資源圧迫の根拠あり、期限付き、レポート機能/正確性は維持 |
| 管理worker自身の期限超過queryを中止 | 自動 | 実接続とstatementの所有・同一性を実行直前に確認 |
| Bot設定cacheの再読込 | 自動 | DBの期待revision/hashが確定。永続設定を変更しない |
| 事前登録した取得先への一時切り替え | policyで自動化可能 | 対象providerが対応、確認用取得に成功、TTL・元値・復帰条件あり |
| Botのハングからの再起動 | policyで自動化可能 | 複数の独立した停止根拠、保守外、DB等の原因を確認、証拠保全、回数上限 |
| Botの異常終了後の通常再起動 | systemdが実施 | デーモンは既存jobを監視。重ねてrestartを発行しない |
| サーバーの永続設定、自動展開枠、保存容量の変更 | Web操作/具体案提示 | 対象・差分・影響・期待revisionを明示 |
| MySQL再起動、他のquery/transaction中止、DB復元、DDL | Webで具体案を確認して実行 | 影響と復旧手順を添え、初期の無人修復には含めない |
| OS再起動、swap操作、依存更新、コード配布、データ削除 | Webで具体案を確認して実行 | 対象、事前資料、戻せる範囲、検証条件を具体化 |

取得先や一時設定の切り替えは、現実にそのproviderが対応している場合だけ利用可能とする。コード内に埋め込まれている挙動をpolicyだけで変更できるとは扱わない。必要なadapter実装を対応表に含める。

### 10.1 再起動競合とループの防止

systemdはプロセス終了後の再起動を担当し、デーモンは生存中の機能停止などを扱う。現在のStartLimitIntervalSec=0は運用policyと整合する有限値へ変更する設計とし、候補は5分間に3回。実際の起動時間・既存運用を測って決定する。

デーモン自身が発行するBot再起動は初期案15分に1回、1日に3回。既存のsystemd job、直近再起動、startup grace、保守、管理者の停止意図を確認する。自動でreset-failedを繰り返して上限を無効化しない。

desired_stateはrunning/stopped/maintenanceを明示し、手動停止は記録する。外部からの停止で理由を判別できない場合、直ちに自動起動せず状態を通知する。保守期限切れは監視の再開であり、必ずBotを起動する命令とはしない。

1対象の変更操作は一度に1つ。既存cbteManager等の別操作口が実際にある場合は同じexecutorへ統合し、統合前は重複した自動修復を有効にしない。既存managerの配備状況は未確認。

### 10.2 すべての修復actionが持つ情報

action_id、incident_id、policy_revision、操作種別、対象unit/boot/PID-start-time、期待設定revision、理由と証拠、実行期限、重複排除キー、影響範囲、事前資料、実行結果、検証、補償操作を持つ。

実行直前に前提を再確認する。PID再利用・新しいbuild・設定変更後に、古い計画をそのまま適用しない。排他leaseとfencing世代をexecutor側でも検査する。core再起動で古い実行要求が再送されても、executorの台帳から同じactionの結果を返す。

期限超過やHTTP/IPC切断は「操作が行われなかった」と同義にしない。systemdのjob IDや対象状態を再照合し、部分的に停止・起動したケースを結果不明として扱う。再起動は以前のプロセスを復元するロールバックができないので、再起動を補償操作として連鎖させない。

復旧検証が通らない場合は元の証拠と実施済み操作を保持し、自動操作を停止して具体的な次案を表示する。一時設定は元のrevisionとTTLを保持し、別の手動変更を上書きする形で戻さない。

## 11. executorとサポート操作の実装

通常の設定・Bot操作は採用済みの共通業務処理を使う。管理コアがGoであることを理由に設定の既定値・検証・書込ロジックを別実装しない。

Bot稼働中の操作はversion付きlocal RPCまたは操作worker経由で実行する。Bot停止中の設定変更・保存資料再解析は、対応する版の共通ロジックを含む独立workerで実行できるようにする。DBが停止している場合は準備・待機までを表示する。実際のDiscord投稿等には、その操作に必要な到達性と権限を確認する。

MySQLの設定更新、監査、反映要求、action receiptは同じtransactionに置く。管理コア側のaction台帳とは二つのDBになるため、分散transactionがある前提にしない。再接続時にreceiptを照合し、期待revisionとaction IDで重複更新を防ぐ。Discordの副作用は送信ID/nonce等を利用し、成否不明を盲目的に再実行しない。

特権操作は別のexecutorに集約する。root所有の実行物とUnix socketのpeer認証を使い、対象unitと操作を型付きで受け取る。対象サービス名・ファイル・時間範囲・操作上限をexecutor自身が検証し、実行側でもdeadlineと子プロセスの終了を管理する。

管理コアにはNoNewPrivilegesを適用できる構成とし、そこからsudoで昇格する設計に依存しない。systemd jobはD-Busのjob ID等で追い、呼出元のタイムアウトだけで完了扱いにしない。

Webには必要な全操作を操作カタログとして出し、利用可能な操作、前提が足りない操作、未実装を区別する。自由入力のコマンド文字列だけを渡す画面を通常のサポート導線にしない。新しい専門調査は、対象・引数・出力・期限を持つactionとして追加する。

サーバーID・チャンネルID指定のmessage.sendも同じカタログへ登録する。URL検証からの送信、通常のサポート送信、診断送信の実行基盤を共有し、目的と参照runを記録する。Bot停止時に利用する独立REST workerも同じaction台帳・排他・送信結果照合を使い、別経路で同じ投稿を重複送信しない。

## 12. 通知

管理コアはBotのDiscord clientやReadyに依存しない独立した送信adapterを持つ。初期構成は管理者向けDiscord webhookと、Discord以外の経路1つを想定する。後者はSMTPや別push基盤等から導入時に選定する。外部監視役は独自の送信資格情報と通知待ち保存を持つ。

通知は障害発生、影響拡大、診断根拠の重要な更新、自動修復の実施/失敗、管理者の操作が必要になった時、確認済みの復旧に限定する。通常の監視tickや変化のない状態を毎回通知しない。

通知内容はincident ID、発生時刻/継続時間、影響する機能とサーバー数、確認できた事実、原因候補と確度、実施済みの調査/修復、未確定事項、独立管理Webへのリンクとする。個別の本文・ID・原文は管理Webからすべて閲覧できる。

通知outboxは状態変更と同じSQLite transactionで作る。外部のmessage ID、送信回数、最終エラー、次回時刻を保存する。宛先の成功応答は受付成功であり、管理者が読んだ証拠とは分ける。APIの応答が不明な場合の重複可能性も扱い、送信側で利用できる重複排除/更新を使用する。

同じ障害の大量通知はincident指紋と状態revisionでまとめる。複数障害の連鎖は親incidentへ関連付ける。外部監視が通知した管理デーモン不通と、復帰後のローカル障害はID/期間を照合して統合する。

通知先への疎通と認証は独立した自己監視対象とする。全通知経路が使えない場合はoutboxとWeb上へ残し、回復後に発生/復旧の要約を届ける。通知できなかったことを通知済みと表示しない。

## 13. 管理分析と専門レポート

集計の単位、結果分類、分母、外部指標の観測、cohort、前後比較、旧データ移行は[指標と統計の詳細設計](admin-metrics-and-statistics-design.md)を共通契約とする。独自の健康度・価値・機会・リスクの合成値は通常分析から外し、根拠となる実数・率・期間を保持する。既存スコアを新しい自動修復の判定条件に引き継がない。

現在の詳細統計の生成を分析workerに移し、UIは生成済みの完全なレポートと更新状態を取得する。デーモンを起動しただけで同一MySQLのI/O負荷が減るとは扱わず、query・集計保存・索引・重複実行をあわせて改善する。

正確な件数、provider・サーバー・ユーザー・URL・設定・処理段階の分析軸を維持する。サポートの単発事象は集計母数の条件で秘匿しない。統計のセルから、その時点・条件の元処理一覧へたどれるようにする。

処理eventから増分更新できる集計は取り込み時または専用jobで維持する。複雑な分析は入力watermarkとquery版を持つjobとし、同じjobを重複起動しない。重いSQLは管理コアの監視接続を使わない。

レポートは生成時刻、対象期間、入力の完全性、処理済みwatermark、query版、失敗理由を持つ。更新中・停止中は最後の完成版とその時点を表示し、空の表を最新結果として返さない。

障害時の負荷抑制は期限付きの運用対処とし、通常の分析項目を削除する変更に置き換えない。継続的な分析負荷が本番DBと競合する場合は、専用の分析保存先/複製先へ移す設計を追加する。必要容量と同期遅延は実測する。

定期的な専門レポートでは、再発障害、応急処置の回数、設定変更の効果、未解決の原因、証拠欠落、修復の成功/失敗、資源の増加傾向をまとめる。通常通知は状態変化中心とし、定期レポート送信は別の設定にする。

## 14. 外部監視と管理基盤自身の監視

別ホストの監視役は、管理コアからのheartbeatと、外部から見た到達性を別々に持つ。初期案は15秒heartbeat、60秒欠落で疑い、複数回の外部確認を経て通知。boot IDとsequenceで遅延・再送・再起動を区別する。

heartbeatにはcoreの生存だけでなく、最終収集、最終保存、通知outboxの状態、最新のincident revisionを含める。生存pingだけ進んで記録が止まっている状態を見逃さない。

外部監視役は通常は通知と複製済み資料の提供を担当する。到達不能という理由だけで別経路から自動修復を同時実行する構成にはしない。OS/ハイパーバイザーの復旧操作を付ける場合は、別途能力・排他・操作policyを定義する。

core停止、worker停止、SQLite busy/破損、WAL肥大、証拠保存容量、取込遅延、時計ずれ、通知失敗、管理UI到達性を自己監視する。回復不能な保存障害では自動の変更操作を止め、資料閲覧と状態の表示を可能な範囲で維持する。

## 15. APIと永続モデル

採用済みのsupport APIに加え、以下を独立管理APIで提供する。通常ダッシュボードは管理者確認済みの中継APIから同じ契約を利用する。

- incidentsの一覧・詳細・経過・関連事象・確認済み操作。
- investigationsの起動・追加資料・分析結果・予算・未確認事項。
- actionsの計画・差分・実行・結果・検証・補償状況。
- policiesの操作別設定・有効期間・変更履歴。
- desired-state/maintenanceの設定と期限。
- notification outbox、送信結果、宛先状態。
- collector capabilities、coverage、watermark、spool、health。
- reportsの生成・状態・完成版・元の処理への掘り下げ。
- 接続のcapabilities/API版、差分event stream、再接続用snapshot、画面間で共通の参照ID。

永続モデルはincident、observation、evidence artifact、hypothesis、investigation step、action、action receipt、verification、notification outbox、policy revision、maintenance、collector cursor、report job/snapshotを中心とする。

各資料にsource/boot/build/schema/version/occurred-at/observed-at/persisted-atを持つ。現在の観測と過去のsnapshotを分け、時刻だけで同一処理を決めない。未観測の値を0や正常に変換しない。

## 16. 導入順序

1. 独立コア、専用保存、ローカル認証、独立UI、OS/systemd/HTTP収集、外部監視を先に実装する。Bot・MySQLを停止しても管理機能が動くことを確認する。
2. 採用済みの処理証拠をBotに追加し、sequence/ACK/退避を接続する。全provider・コマンド・ボタン・配信へ対応表を広げる。
3. 診断手順、incident状態、根拠付き原因候補、独立通知を導入する。現在の通知機能と照合してから通知主体を切り替え、二重通知をなくす。
4. 全Webサポート操作、共通worker、設定反映ACK、修復executorを接続する。通常ダッシュボードのadminにも同じ操作・診断部品と中継APIを統合する。
5. 観測だけの期間に、自動修復なら何をしたかを台帳へ記録して評価する。受け入れ試験を通った操作からpolicyに従って自動化する。
6. 分析workerへ詳細統計を移し、診断ルール・調査手順・既知障害との照合・再発分析を拡充する。

対応するschema/event/APIは版を持ち、旧Botとの互換期間を用意する。取り込み済み証拠と設定履歴を移行で失わない。更新は事前に作った配布物を切り替え、障害中に依存取得やビルドを始めない。

## 17. 受け入れ試験と初期目標

下記は設計上の目標であり、実測結果ではない。ローカル単体試験、Linux上の統合試験、導入先での限定試験を分けて記録する。

| 試験 | 合格条件 |
| --- | --- |
| Botと通常ダッシュボードを停止 | 独立Webへログインし、資料閲覧・原因調査・対応する復旧操作ができる |
| 通常ダッシュボードが稼働 | admin画面内で事象検索、根拠閲覧、追加調査、設定変更、修復、結果確認まで完了できる |
| 両管理画面で同じ設定・incidentを開く | 同じID/revisionと進行を表示し、変更競合・自動修復との競合を検出 |
| 通常ダッシュボードから実行後に停止 | 独立Webから同じactionの結果を確認し、二重実行しない |
| 連携の切断・再接続・event欠落 | 最終同期と接続状態を表示し、cursor/snapshotで整合を回復 |
| 管理コアだけが停止 | 通常ダッシュボードの利用可能な機能を維持し、限定した管理コア復旧操作を追跡できる |
| 一般ユーザーが管理用中継APIを呼ぶ | 管理操作を受け付けず、既存のユーザー向け権限と混同しない |
| MySQL停止 | 独立Web、台帳、通知が動き、未適用の設定操作を適用済みとしない |
| 起動前のDB/Discord障害 | Bot Ready以前からOS/起動ログを収集し、原因資料と通知を提供 |
| Botのevent loop停止 | プロセス生存と処理停止を区別し、事前資料を保全してpolicyどおり対応 |
| systemdの再起動ループ | 既存jobと競合せず、上限超過を通知。reset-failed反復を行わない |
| 計画停止・外部からの手動停止 | 自動修復で管理者の停止意図を打ち消さない |
| OOMと単なる高RSS | kernel/cgroupの根拠から被害プロセスを照合し、RSSだけでOOMとしない |
| MySQLのlock待ち/I/O待ち/接続待ち | 異なる証拠で分岐し、調査queryが負荷を増幅しない |
| 失敗した管理queryの中止 | 自身のstatementだけを照合して中止し、別の更新transactionに触れない |
| 低トラフィック・観測不能 | 警報候補から消えたことを復旧と誤認しない |
| provider異常・部分送信・設定未反映 | 元処理から原文・設定・送信結果へたどり、具体的な対処をWebで行える |
| 分析worker強制終了 | 収集・軽量ルール・通知・Webが継続し、未完了分析を正常扱いしない |
| 特権action中にcore停止 | executor側の期限が有効で、再接続後に実結果を照合。重複実行しない |
| 二つの操作口・期限切れ計画 | 排他・世代・期待revisionを検証し、古い計画を実行しない |
| プレビュー・定義済み追加調査 | 保存/投稿/削除等の副作用を発生させず、証拠と実行結果を区別 |
| ルールに必要な証拠が欠落・古い・反証あり | 資料不足または不成立とし、その原因を前提にした自動修復を実行しない |
| 同一証拠の再評価・ルール更新 | 同一版で同じ判定を再現し、版変更後の結果を当時の判定と区別 |
| 未分類の障害 | 原文・経過・比較資料・追加調査をWebから確認でき、既知の原因を作り上げない |
| 通知経路の片方/両方停止 | 別経路/外部監視とoutboxを確認。未送信を送信済みにしない |
| 管理daemon/ホストを停止 | 外部監視から不通を通知し、復帰後に同一障害の資料へつながる |
| ディスク満杯・部分保存・再送 | 欠落・保全・ACKを整合させ、復旧時に証拠やactionを増殖させない |
| インターネット/Discord認証停止 | 事前に用意した経路で独立管理Webへログインできる |
| 同時に重い分析を実行 | 監視遅延・UI・Botへの影響が予算内。重いworkerの停止でcoreが落ちない |

初期目標は、異常終了の検知15秒以内、機能停止の疑い検出60秒程度、最初の診断資料30秒以内、利用可能な通知経路への初報60秒以内、1サーバー24時間の最初の100件と一件の詳細がP95 2秒以内。通知先の停止やホスト停止は別の外部監視目標として測る。

自動修復率だけでなく、誤診断、不要な操作、二重操作、証拠欠落、再発率、復旧確認の誤判定を測る。管理者がサーバーIDと時間帯だけから、根拠・対処・結果までWebで確認できることを最終条件とする。

## 18. 導入前に確定・確認する項目

外部監視役の配置先、Discord以外の通知先は未選定。OS/systemd/cgroup版、保存用volume、管理originと直接経路、実際のunitとプロキシ構成、DB診断権限、既存managerの有無、Botの起動時間と実負荷を確認する。

これらは実装と導入時に具体値を設定する項目であり、現在の稼働状態や権限が確認済みという意味ではない。今回、新しい通知・監視・再起動設定は有効にしていない。
